# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Verify Predicate-Window Continuity for duration-constrained queries. Accept only those trajectories where the agent has successfully verified that the required condition (e.g., 'no rain') holds true for every single sub-interval across the entire duration Δt. If the agent finds one 'clear' point but ignores the rest of a 4-hour window, the selection is rejected for lack of continuity proof. For instance, a 2-hour Sydney trip must have all four 30-minute slots checked and logged as 'cloudy'.
  - Confirm minimum of two distinct anchor comparisons for iterative search. Irrevocably accept solely those trajectories forcing the agent into comparing the initial (invalid) anchor against at least one improved alternative. Revert queries where the very first result satisfies the condition back to simple retrieval classes; the iterative search capability is only proven when the agent bypasses a 'violation' to find a 'success'. A valid sample shows the agent rejecting the 07:00 and 08:00 traffic slots before selecting 09:00.
  - Ensure total absolute verifiability of all underlying utilized chronometric strings. Every localized time variable leveraged inside the sorting or searching algorithm must be explicitly recoverable from the provided corpus without generating gaps via internal memory. Any undocumented chronological shift or 'gap-filling' based on general world knowledge violates the read-only environmental constraint. A reviewer must be able to trace exactly which document provided the '13:30 rain' fact that triggered the postponement.
  - Maintain sharply scorable constraint metrics for final answer derivation. Despite the sprawling nature of searching through hours of time-series data, the intended output must culminate in a precise timestamp, a binary label, or a hyper-focused trend vector. Prohibit sweeping, subjective essays that describe the 'feeling' of a timeline without stating the exact moment of a transition. A perfect acceptable target is a strict '2024-12-05T16:30:00' start time for a rescheduled event.
* **Rejection Criteria**:
  - Reject isolated single-document point-in-time extraction operations. Utterly discard configurations wherein reading exactly one text block satisfies the chronological inquiry without subsequent comparisons or window-checks. Real temporal reasoning disappears the moment the need for multi-source comparative timing or sequential scanning is removed. For example, simply asking 'what was the rainfall at 13:00' is a lookup task, not a reasoning task.
  - Discard sample sets suffering from inherently unresolvable chronometric ambiguities. Fundamentally reject corpora scenarios deploying wildly conflicting calendar paradigms or vastly underspecified relative phase shifts that fail to grant a baseline temporal mapping bridge. Ensuring objective human-level chronological resolution is the highest standard for valid training data. If one document uses 'UTC' and another uses 'Local' without a conversion factor, the sample is unstable and must be purged.
  - Eliminate permutations heavily relying on math disguised as sequence analysis. Discard contexts effectively behaving as isolated complex calculus equations loosely stapled onto arbitrary dates. Ensure the challenge is software version evolution, timeline navigation, or interval search rather than generic numeric filtering (e.g., naming 'the highest number' regardless of its date). The time component must be the functional driver of most of the reasoning steps.
  - Reject trajectories that skip violating events to find an 'imperfect' answer. If the prompt asks for a 'rain-free' window and the agent returns a window that includes a 30-minute rain shower because it 'looked the best', the sample represents a precision failure. The selection phase must verify that the answer is perfectly consistent with the negative constraints defined in the query. An agent that 'guesses' 15:00 when 15:30 clearly shows rain must be rejected during the quality check.
