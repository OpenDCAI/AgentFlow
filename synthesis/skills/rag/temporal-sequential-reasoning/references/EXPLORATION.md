# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Implement Temporal Radius Expansion starting from the user's defined anchor point. Upon receiving a time-sensitive query, the agent should first retrieve facts for the exact time t requested to establish a baseline. If the condition is unsatisfied, it must progressively expand the search radius in both directions (t - radius, t + radius) to discover alternative intervals. For example, if a 13:00 flight is cancelled, the agent scans forward to 14:00, 15:00, and so on, until a viable flight appears in the logs.
  - Deploy Cadence-Aware Sequence Alignment based on the corpus's sample frequency. The agent must identify the temporal resolution of the environment (e.g., 30-minute weather slots or 1-hour traffic logs) and structure its retrieval steps to match this granularity. It systematically probes each discrete slot to ensure no high-frequency violations are skipped between start and end times. A concrete edge case is checking a 'rain-free' 2-hour window in 30-minute data, which requires verifying exactly four consecutive and successful data points.
  - Execute Discontinuous Violation Identification to prune invalid search horizons. This strategy involves marking the specific timestamp of a 'failure' (e.g., a rain event or a high-traffic spike) and immediately jumping the retrieval anchor to the first slot appearing after that failure. Instead of checking every second, the agent uses the knowledge of a violation's end-time to skip ahead in the sequence. For instance, if a storm ends at 16:00, the agent correctly resets its search start-point to 16:01 to find the next available dry window.
  - Apply Chronocentric Anchor Propagation for multi-city or multi-stop trajectories. For travel planning queries, the agent must update the temporal anchor (t) for each subsequent location (l) by adding the estimated duration of previous activities. It logs each step's arrival time based on the previous step's departure and travel delta to ensure the entire chain stays synchronized. A clear example is adjusting the 'weather check' for the second stop of a tour because the first stop took 45 minutes longer than initially planned.
* **Target Trajectory Profile**:
  - Mandate chronometric standardization of relative phrases and seasonal markers. An exceptional trajectory unfailingly converts phrases like 'two hours later', 'the following afternoon', or 'next quarter' into absolute, universally comparable timestamps. Systematically failing to normalize these relative cues into a fixed axis leads to sequential hallucinations and is a primary cause of ordering errors. For example, explicitly recording 'Found rain at 13:30 (start+30 mins); shifting window' ensures the reasoning remains anchored in hard data.
  - Enforce strict per-timepoint discrete evidentiary capture ledgers for interval verification. The internal generative scratchpad must comprehensively archive the status (e.g., [14:00, OK], [14:30, OK]) for every sub-interval within a targeted time window. This explicit itemization is vital when certifying a 'clear' window; simply stating 'the window is clear' is insufficient without a log of the constituent checks. A perfect example is listing all four 30-minute slots that confirm a rain-free two-hour period as identified in the Australian weather dataset.
  - Require explicit algorithmic computation logs for temporal offsets and shifts. The visible trace must categorically itemize the applied chronological sort or shift mechanism, directly typing out intermediate logic like 'Step 1: Found violation at 13:30; Step 2: Earliest possible start is now 14:00'. Such raw explicitness elevates the underlying inference process out of opaque leaps and reveals how the agent navigated to the 'optimal' answer. This prevents the agent from guessing a time-slot without proving its feasibility.
  - Maintain a 'Recency Survival' ledger to handle factual evolution and deprecations. The trajectory must observably scan for the most recent document iteration or version tag to ensure legacy data does not override currently active facts. It should distinctly log: 'Document A (2022) says X; Document B (2024) says Y; prioritizing Y as the latest stabilized truth' to prevent obsolete information from being used in final synthesis. An edge case is retrieving a 2024 weather update that contradicts a 2023 climate report for a specific day.
