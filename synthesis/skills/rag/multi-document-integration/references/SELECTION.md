# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Verify that 'Stitched Discontinuity' is functionally necessary for the answer. Accept only if the query specifically targets details that are physically separated across different documents, sections, or repository files, making a single-document answer impossible. This ensures the benchmark measures integration rather than simple extraction. A valid sample requires integrating the 'risk' section of one file with the 'performance' section of another to satisfy a 'qualified' query.
  - Confirm high Intersection-around-Anchor nodes for multi-file contexts. Accept only trajectories where different documents contribute unique, necessary slots (e.g., one file provides the 'method signature' and the other provides the 'utility logic') centered around a single target entity. This ensures the retrieved 'noise' is actually 'context' that changes the meaning of the answer. For example, a code summary must be significantly different (e.g., more precise regarding dependencies) when the repository chunks are included versus when they are absent.
  - Validate that the support documents exhibit 'Logical Synergy' rather than redundancy. The selected context must provide fragments that, when combined, create a more accurate or restricted interpretation of the facts (e.g., Fact A states a general rule, Fact B states a specific exception for this case). If Document A already contains the exception mentioned in Document B, the integration task becomes trivial. A high-quality sample depends on the agent 'synthesizing' a qualification that is not explicitly pre-written in any single chunk.
  - Ensure the presence of a 'Structural Map' or 'Anchor' for large-scale data. Accept samples only if the environment provides a clear pointer (like a class header or a TOC) that allows the agent to verify the relationship between distant fragments. This anchor must be used in the trajectory to justify why these specific fragments were chosen for integration. An acceptable case uses the 'Class Skeleton' to prove that the three retrieved helper functions truly belong to the target class being summarized.
* **Rejection Criteria**:
  - Reject samples suffering from 'Information Leakage' in Master Summaries. Eliminate any case where the final aggregated answer already appears in a pre-written executive summary, README file, or introductory paragraph. If the agent can provide the integration result by reading the first 500 tokens of the first document, the 'multi-document' constraint is violated. Always manually verify that 'Abstract' or 'Executive Summary' sections are either removed or neutralized to force fragments-based synthesis.
  - Discard cases with 'One-Document Shortcut' convenience. Reject if the 'separated' fragments are merely placed adjacent to each other in the same physical paragraph without any structural or semantic barrier that requires active navigation. The goal is to test the agent's ability to 'bridge' gaps, so if the chunks were never truly fragmented in the first place, the trial is invalid. A rejected case is finding the 'Revenue' and 'Risk' for a company in the same single-row table entry.
  - Eliminate 'Estimation or Hallucination' used to bypass integration gabs. Reject any trajectory where the agent finds the first half of a comparison and 'fills in' the second half using its pre-trained knowledge without actually retrieving the second document. This is common with famous entities like 'What is the revenue difference between Apple and Microsoft?' where a model might guestimate. All legs of the integration must be strictly anchored to the provided bounded corpus.
  - Reject samples where the 'Integration' is purely decorative or interpretive. If the additional documents (like repository chunks) provide 'interesting but unnecessary' background that doesn't change the factual answer to the query, the sample provides zero signal for integration capability. The query must be designed so that ignoring the integrated fragments results in a measurably incorrect or significantly less accurate answer. For example, a function summary that misses a critical external dependency revealed only in the RAG chunks.
