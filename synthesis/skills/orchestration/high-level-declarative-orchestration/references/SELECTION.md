# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Evaluate the 'Abstraction Efficiency Ratio' to verify the LLM issues fewer than 5 declarative tasks to achieve a composite goal normally requiring dozens of low-level API or shell integrations. You must confirm the orchestrator genuinely delegated implementation burdens, such as formatting syntax or looping logic, to the underlying framework layer. A robust case demonstrates an orchestrator deploying a single `Configure_Cluster` instruction that successfully initiates and validates a dense, multi-server distributed environment.
  - Selected traces must exhibit 'Auxiliary Service Grounding,' ensuring the orchestrator's ongoing strategic decisions unequivocally trace back to the macro-summaries provided by the external state tracker. The log must verify the system relies on physical environment topology updates rather than injecting hallucinated templates generalized from its pre-training domain. A solid edge case highlights the agent discovering a highly irregular subsystem naming convention entirely through the state mapping and seamlessly incorporating it into subsequent declarative workflows.
  - The trajectory must enforce 'Logical Persistence' guaranteeing that critical keys, paths, or architectural parameters stay fully accessible via query mechanisms regardless of the operational timeline. You must prove the orchestrator reliably queries the state database for historical identifiers rather than blindly prompting the user to re-supply the information. This metric ensures the system decisively solves the context-loss dilemma standard agents face when tackling environments requiring extended, multi-phase navigation loops.
  - The trace must portray 'Strategic Resilience' where the agent dynamically redirects its high-level strategy upon encountering a failure within a specific declarative branch. If a `Deploy_Application` macro fails due to detected resource conflicts, the orchestrator should gracefully observe the blocked state, prune the intent, and instantly map an alternative structural path. High-quality interactions display the agent acknowledging the dead end and strategically pivoting without collapsing the overarching mission objective.
* **Rejection Criteria**:
  - Reject immediately any trajectory where the commanding orchestrator attempts to write raw foundational execution logic (e.g., complex SQL strings, deep API request headers, or intricate Bash combinations) within its distinct action field. This fundamentally breaches the core intent of decoupling strategic intent from localized implementation realities. If the system micromanages technical parameters instead of leveraging the macro framework, it ceases to demonstrate true high-level declarative orchestration.
  - Discard environments producing 'Context Bloat Failures' where the system blindly ingests all background execution or terminal logs directly into its active conversational prompt window. This showcases a complete bypass of the required 'Summary and Parse' filtration boundary, rendering the overarching architectural setup functionally useless. Valid synthetic generation strictly requires the orchestrator to operate using tiered information management that actively suppresses unneeded digital noise.
  - Reject scenarios where the orchestrator executes a 'Magic Navigational Leap', perfectly targeting a hidden downstream node or complex architectural piece without issuing preliminary discovery tasks. Every substantial milestone achieved must be securely anchored to a declarative reconnaissance step that logically justifies its integration into the workflow. If an agent automatically maps instructions to Server B without the state tracker verifying Server B exists, it is an irredeemable synthetic data leak.
  - Reject shallow pseudo-orchestration instances where the provided declarative tasks merely act as transparent wrappers over low-level execution engines. If the orchestrator commands `Execute_String("rm -rf folder")` it entirely circumvents the philosophical goal of operating strictly via intent-based API models. Meaningful capability representation requires the commands to be inherently process-oriented—like `Remove_Temporary_Assets`—putting the strategic onus on the planner and technical burden on the subordinate framework.
