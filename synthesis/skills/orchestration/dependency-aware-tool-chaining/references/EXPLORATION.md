# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform 'Claim-Based Fact Partitioning' at the start of the interaction to decompose the user's high-level goal into atomic, verifiable facts. You should determine exactly what data points (e.g., a specific abstract, a demographic threshold) are required and which tools are capable of providing them before taking action. For example, if a user asks for a comparison, identify that you need two distinct lookup calls and one comparison call as three separate logical subgoals.
  - Establish 'Conditional Sequence Mapping' by identifying points where the output of one server will dictate the branching logic of the next phase. You must flag potential 'pivot points'—such as an external search that yields a numeric threshold—as mandatory prerequisites that must be solved before the downstream query can be formed. An important instance is when you prepare to find 'high-risk' items; you must first query the definition of 'high-risk' before defining the search parameters.
  - Map Logical Research Edges to deal with HCSPs (Hierarchical Constraint Satisfaction Problems). During tree construction, define explicit relationships between entities (e.g., 'graduated from,' 'capital of'). You must log cases where a parent node (the person) is obscured by child attributes (the city stats). This forces the orchestrator to solve the local child constraint before retrieving the parent node, embedding dependency directly into knowledge extraction.
  - Implement 'Distractor-Aware Discovery' by auditing the complete set of available tools without being influenced by the literal names used in the prompt. You must inspect tool descriptions and parameter schemas to ensure the selected tool matches the *functional* need. A concrete edge case is choosing a 'Notion Query' tool over a 'General Search' tool even if the prompt uses the word 'search' but the data resides in a structured database.
* **Target Trajectory Profile**:
  - The trajectory must explicitly demonstrate a 'Compositional Multi-Hop Loop' where at least two distinct servers or research layers are successfully coordinated to produce a unified factual answer. This is verified by checking that the final answer contains grounded facts from both sources (e.g., a paper abstract from Arxiv AND engagement rates from Notion). A trajectory that solves only half of the user's prompt or uses only one available server to 'guess' the rest is a failure.
  - The trace includes a 'Parallel-to-Sequential Constraint Interplay' where the agent dispatches multiple filters for one node (parallel) before using the result for the next node (sequential). The trace is excellent if it shows a 'Research Step' that resolves two distinct sub-constraints concurrently (e.g., population and language), deduces 'London', and fuses it into a single, high-fidelity parameter for the subsequent bio-search step.
  - A successful profile involves 'Conditional Fallback Resilience' where the agent adaptively switches servers or tools if the primary attempt returns a null or insufficient result. The log should show a pattern like 'Observation: No results found in Database A; Action: Triggering Search Engine B to find the definition.' This 'Branching' behavior demonstrates the orchestrator's ability to navigate execution uncertainty.
  - The trajectory should capture 'Strict Parameter Grounding' where values found in the observation of Step 1 are explicitly used to populate the JSON arguments of Step 2. You must see the exact values (e.g., a Paper Title, a Database ID, or a matched City name) being passed without modification or hallucination into the subsequent tool call.
