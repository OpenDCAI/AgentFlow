# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - The trajectory is acceptable only if the generated plan is a valid Directed Acyclic Graph (DAG) with zero circular dependencies. You must verify this by performing a topological scan of the predicted edges; if any node serves as both a prerequisite and a descendant of another node in a loop, the selection must fail. For example, if 'Search A' depends on 'Filter B', which in turn depends on 'Search A', the trajectory is logically invalid and cannot be used for synthesis.
  - Selected traces must exhibit 'Node-Level Selection Precision,' where every tool included in the DAG is functionally necessary to resolve at least one branch of the user's query. You must cross-reference the nodes against the tool library to ensure no 'Distractor Tools' with similar names but irrelevant schemas were included. A strong trace demonstrates the orchestrator picking the 'Numerical Solver' over the 'Text Summarizer' when the specific dependency in that branch requires a float calculation.
  - The trajectory must demonstrate 'Edge-Level Dependency Grounding,' where every link between two tools in the DAG corresponds to a real-world data handoff (e.g., a shared ID or timestamp). Reviewers must verify that the output schema of the 'Parent' node is compatible with the input requirements of the 'Child' node. An edge case is a trajectory where a 'Paper ID' is correctly passed from a search tool to a citation tool, while a 'Generic Title' is rejected as a weak dependency link.
  - The final plan must satisfy the 'Connectivity Metric,' meaning there are no isolated nodes that are disconnected from the user's goal or the final answer node. In a multi-tool task, every selected vertex must have at least one incoming edge (unless it's a seed search) and contribute to at least one outgoing edge (unless it's the final output). This ensures the synthetic data represents high-utility orchestration rather than fragmented or redundant tool-calling.
  - The interaction must maintain 'Syntactic Integrity' by outputting the DAG in a strictly formatted structure (like JSON or a specific schema) that an executor can parse. You are mandated to observe the orchestrator using a formal syntax to define edges (e.g., 'dependencies': [1, 2]) rather than just describing the relationship in prose. Identifying the explicit use of structured schema identifiers for nodes ensures the planning is 'machine-executable' and provides high-fidelity training data.
* **Rejection Criteria**:
  - Reject any trajectory where the agent falls into the 'Local Optimization Trap' by planning only the first step and ignoring the subsequent dependency structure. The purpose of this capability is global foresight; if the agent says 'I will search first and then see what happens,' it is a standard ReAct case and provides no value for DAG planning. Synthesis must prioritize tasks where the *entire* sequence is defined upfront in the first assistant turn.
  - Discard traces that exhibit 'Cycle Hallucination,' where the agent creates edges that form an infinite loop within the plan. This includes 'Refinement Loops' that are not represented by a finite DAG structure, where internal logic gets stuck between two nodes repeatedly. For instance, if an agent links 'Self-Correction' back to the 'Original Input' in a way that suggests an infinite series of tool calls without a clear exit node, the trace is broken.
  - Reject trajectories where the 'Edge Set' is empty despite the task requiring multiple tools to work together. If the agent selects 5 tools but provides zero links between them, it assumes the executor can 'guess' the data flow, which violates the requirement for explicit dependency modeling. High-quality data requires the agent to be the 'architect' of the data flow, not just a 'librarian' of the tools.
  - Reject any trace where the 'Node Set' contains tools that are documented as 'Stale' or 'Incompatible' with the current environment state discovered in exploration. If the orchestrator selects a V1 API when the environment only hosts V2, it demonstrates a failure to ground the plan in the available toolkit. Every node in the DAG must map to a physically accessible and logically relevant tool presented in the discovery session.
  - Reject traces where the solution depends on 'Hidden Pathing'—parameters that appear in the final answer but were never modeled as an edge or observed in any intermediate node. This signifies an 'Ungrounded Leap' where the agent used internal memory to fill in the blanks of the execution graph. Every piece of data used in the final step must have a clear 'Topological Heritage' traceable back through the DAG's edge set.
