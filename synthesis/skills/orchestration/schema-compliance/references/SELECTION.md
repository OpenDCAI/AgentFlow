# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  * The trajectory is acceptable only if the central failure boundary for **Schema Compliance** is objectively testable from the recorded artifacts. There must be enough information to determine whether the agent made the right orchestration decision without appealing to hidden intentions or unverifiable human judgment. A strong example is a trace where the chosen path can be audited against the tool schema, dependency graph, evidence record, or security policy.
  * The trajectory must include at least one non-trivial alternative that would have looked reasonable to a weaker agent. This condition ensures that the example is diagnostic rather than ceremonial. For example, if a user request could have triggered two similar tools, the trace is only useful when the accepted path and the rejected path can be distinguished by real constraints rather than arbitrary labeling.
  * The recorded observations must support direct reconstruction of the final answer or final state. A reviewer should be able to point to the exact returned values, state mutations, or rejection events that justify the outcome for **Schema Compliance**. If the answer depends on an unlogged assumption, hidden state, or manual interpolation, the trajectory should not pass selection.
  * The trajectory should be neither too easy nor too noisy. Reject trivial one-step cases unless the essence of **Schema Compliance** truly appears in that single step, and reject overgrown cases where unrelated subproblems dominate the reasoning budget. A good edge case is a medium-complexity trace whose difficulty arises from one sharp coordination decision rather than from a large pile of incidental facts.
* **Rejection Criteria**:
  * Reject any trajectory where success is possible without exercising **Schema Compliance**. If an agent could answer from memorized knowledge, by random guessing, or by a single obvious tool call, then the example does not isolate the intended orchestration behavior. A common edge case is a prompt that mentions the exact tool name or the exact execution order in the question itself; those should usually be discarded or rewritten.
  * Reject trajectories whose critical evidence is missing, contradictory, or only visible after external interpretation. The point of the synthetic data is to train and test an agent against observable execution structure, not against hidden author intent. For example, if the trace says a step was necessary but never logs the returned artifact that enabled the next step, the case is too weak to keep.
  * Reject trajectories where another capability dominates the difficulty more than **Schema Compliance** does. A case may be superficially relevant yet actually hinge on domain knowledge, OCR, long-document reading, or raw arithmetic instead of the orchestration skill we want. An edge case is a highly specialized domain prompt where the agent fails because it does not know the subject matter, even though the coordination pattern itself is simple.
  * Reject traces that contain preventable environment artifacts which make the item ambiguous. Duplicate entities, stale records, inconsistent schemas, or attacker content that is not clearly tied to the user path can all blur evaluation. If such ambiguity cannot be removed while preserving the original structure, discard the seed and search for a cleaner one.
