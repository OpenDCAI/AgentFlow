# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - The corrective action taken by the agent must be 'Diagnostic-Grounded,' meaning the fix (e.g., a fixed port, a changed table name, or a modified convergence parameter) must be exactly the one indicated by the combination of the machine output and the researcher's discovery. You must verify that the information required to fix the error was present in the prior step's discovery observation. For example, if the agent fixes a column name, the prior exploration trace must show the Knowledge Graph or documentation return that specific valid string. This ensures the data represents grounding rather than pre-training hallucination.
  - Selected traces must exhibit 'Closed-Loop Verification Fidelity,' where the success of the correction is confirmed by a final 'Runner' or 'Validator' call that returns a 100% correct environment state. You must be able to point to a 'Before' (Error) and 'After' (Success) state that is explicitly observable in the tool logs. Any trajectory where the agent 'guesses' a fix and then moves immediately to the final answer without re-executing the tool to verify the repair must be rejected. This mandates that the synthetic training requires the agent to 'prove its work' after a self-correction event.
  - The trajectory must demonstrate 'Rollback and Resumption Accuracy' in long-horizon workflows. You must verify that after a 'Review' agent flags a failure in a massive log, the Planning agent correctly identifies the exact prerequisite state to return to (e.g., the 'Input Preparation' node) and preserves the unaffected artifacts. A strong case involves an agent that detects an error at T=10, rolls back to T=5, applies a fix, and resumes the sequence without re-doing the successful work from T=1 to T=4. This validates the efficiency of the hierarchical state machine.
  - The interaction must maintain 'Syntactic and Schema Integrity' by outputting the final corrected action in a strictly formatted structure (like JSON) that is compatible with the target environment's technical requirements. You are mandated to observe the orchestrator using a formal syntax to define parameters rather than just describing the fix in prose. Identifying the explicit use of structured identifiers for nodes and parameters ensures the planning is 'machine-executable' and provides high-fidelity training data for industrial-grade orchestration.
* **Rejection Criteria**:
  - Reject any trajectory where the 'Self-Correction' is triggered by a human user telling the agent it was wrong or providing the fix in a follow-up turn. The recovery must be entirely 'Autonomous,' meaning the agent identifies and repairs the issue by reading its own tool tracebacks, environment manuals, or machine logs. Human-in-the-loop assistance is a separate coordination skill; this specific capability evaluates the system's ability to be a self-healing 'Trustworthy Execution' layer. If the user provides the fix, it is a simple instruction-following case.
  - Discard any trace where the solution to the technical error depends on 'Hidden Pathing'—parameters that were never observed in a log or documentation file during the trajectory. This signifies an 'Ungrounded Leap' where the agent used internal memory to 'magically' know a missing backend flag or a secret API token without discovery. High-quality synthetic data for this skill requires that every corrective parameter is logically derivable from the available diagnostic evidence. If the agent 'just knows' the off-by-one fix without checking a manual, it is a synthetic failure.
  - Reject trajectories where the failure is 'Opaque' or 'Catastrophic'—meaning the tool provides zero feedback, a blank crash log, or a generic 'Unknown Error' that offers no diagnostic signal. If the agent makes a pure guess in the dark after a silent failure, it is not demonstrating the feedback-based reasoning we aim to measure. The essence of this capability is the capacity to 'listen' to the machine's feedback and adapt the orchestration plan accordingly. Silent failures are unsuitable for training this skill.
  - Reject traces characterized by 'Context Exhaustion Loops', where the agent repeatedly fetches giant, unrefined telemetry dumps (e.g., 10,000 lines of logs) without using its researcher agents to perform 'Targeted Extraction' or 'Grep-based Parsing'. Professional self-correction requires the coordinator to use query-based tools to find the 'Needle in the Haystack' fix. Traces where the context window is flooded by irrelevant logs, leading to a degraded reasoning performance, are negative examples of orchestration hygiene.
