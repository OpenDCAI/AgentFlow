# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Identify 'Traceback-Rich' task configurations where tool calls are likely to return informative machine logs or stack traces rather than simple binary failures. You must verify that the environment provides a 'Diagnostic Stream' (e.g., Python stderr or SQL EXPLAIN) that the orchestrator can ingest alongside raw status codes. A concrete edge case is a tool that requires a specific absolute path; skip the path prefix to force a traceable 'File Not Found' error that serves as a seed for testing the recovery loop. This guarantees that the exploration produces a high-fidelity 'Failure Signature' for calibration.
  - Harvest 'Technical Invariants' from a domain-specific modeling manual or meta-prompt to identify traps like indexing conventions, unit requirements, or specific computational markers (e.g., checking for the 'Normal termination' string in VASP logs). You should compare the user's plain language intent against these rigid technical rules to find 'Misalignment Points' that would trigger an error. An important example is discovering that a simulator's internal indices start at 1 while its Python wrapper is 0-indexed; record this as a mandatory 'Sanity Check' for every synthesized plan. This separates shallow tool calls from logic-grounded orchestration.
  - Map 'Agent-to-Agent Handoff Signatures' to identify the specific naming conventions and argument structures used when one sub-agent (e.g., a Generator) passes a code block to another (e.g., an Evaluator). You must verify if the environment uses fixed schemas or requires the agents to 'guess' function names, which creates the opportunity for 'Signature Mismatch' errors. A robust edge case involves a Generator naming a function `calculate_x` while the Evaluator calls `get_x`; logging this allows you to synthesize tasks where the orchestrator must reconcile these internal specification drifts. This addresses the common failure mode in multi-agent pipelines.
  - Audit 'Long-Horizon Batch Terminations' by identifying the markers that signify a successful vs. failed completion within massive output logs. You must query the environment documentation to find the exact strings or status codes that define 'Convergence,' 'Matrix Singularity,' or 'Abnormal Termination' in scientific simulations. A useful edge case is finding a log file that is 50MB in size but where a failure is only visible in the last 10 lines; recording this ensures the synthetic agent is tested on deep-log parsing rather than just status-code checking.
  - Log 'State-Aware Detection Triggers' that pivot the orchestrator from its primary 'Action' mode back into a 'Research/Debug' or 'Rollback' mode based on specific log patterns. You should monitor the environment results to see if the system can distinguish between a fatal environment crash and a fixable technical deviation. An important example is a workflow where the orchestrator pauses a simulation and dispatches a sub-agent to find the correct database column from a metadata wiki when the first tool call results in a divergence error. This ensures the agent is trained on reading literal failure diagnostics.
* **Target Trajectory Profile**:
  - The trajectory must explicitly contain a 'Multi-Round Feedback Arc' where a failure in Step N is followed by a deliberate, successful correction turn that uses the error log or convergence status as its primary input. A high-quality profile features a moment where the agent’s first attempt fails (e.g., a syntax error or an SCF convergence failure) and is followed by a deliberate lookup or a state-machine rollback. A trajectory that fails and then simply guesses a random fix without citing the traceback or log marker is considered a negative anti-pattern. This ensures the synthetic data captures the 'Reflect -> Research/Rollback -> Repair' cycle.
  - Successful profiles include 'Traceback-Centric Reasoning' in the assistant's internal thoughts, where the agent explicitly points to a line in the observation to justify its next move. The agent must state something like: 'The OUTCAR shows the SCF cycle did not converge, revealing a logical failure in the computation; I will now rollback to the input phase and adjust the parameters.' An edge case is a trajectory where multiple errors are present, and the agent chooses to fix them sequentially rather than all at once, showing a structured debugging process. This provides a transparent audit trail of the orchestrator acting as a technical supervisor.
  - The trajectory must demonstrate 'Technical Invariant Alignment,' where the final successful action satisfies a non-obvious domain rule (like an off-by-one index fix or an adjusted mixing scheme) that was explicitly violated in the first attempt. The trace is excellent if it shows the agent receiving a 'Bad Logic' error and then applying a specific mathematical or parameter adjustment derived from a technical guideline. This proves the orchestrator is coordinating specialized knowledge discovery rather than just performing self-reflection on its own internal parameters. It demonstrates resilience against the context-window limitations of complex scientific environments.
  - High-quality trajectories for this skill focus on 'Diagnostic Efficiency' by resolving the underlying fault within 2 to 5 targeted correction rounds rather than exhaustive brute-force guessing. If the trace becomes an endless loop of failures without information gain, it is a negative example. A useful edge case is a 'divergent' success where the agent fixes one syntax error only to discover a second, deeper domain-logic error in the next round, resolving both before finishing. This ensures the data represents an efficient orchestrator rather than a blind generator.
