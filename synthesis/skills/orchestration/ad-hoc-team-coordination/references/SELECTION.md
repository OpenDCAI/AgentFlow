# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - The final answer must be 'Preference-Grounded,' meaning the balance between cost, speed, and quality in the final deliverables aligns with the most recent weights ($U$) provided by the stakeholder. You must verify that the manager cited the stakeholder's preferences in its action rationale when choosing between expensive/fast or cheap/slow workers. For example, if the 'Compliance' metric is weighted highest, the final state must show that the 'Audit' tasks were prioritized and completed with high-fidelity evidence. This confirms the system successfully addressed the non-stationary preference challenge.
  - Selected traces must exhibit 'Ad-Hoc Teammate Correctness,' where every task assignment is physically compatible with the skills and types (Human/AI) of the workers available at that specific timestep. You are mandated to check the timestamps of 'Assign' actions against the 'Team Churn' logs (Join/Leave) to ensure the agent did not assign a task to a worker who had already left or wasn't yet in the pool. A strong case involves an agent correctly identifying that a 'SaaS negotiation' task requires the 'Legal Counsel' expert who joined at $T=25$. This validates the team-discovery logic.
  - The trajectory must provide a clean 'Dependency Integrity' audit, proving that no task was assigned or executed before its prerequisites ($E_T$) were marked successfully completed in the state ($s$). This is verified by checking that the 'Ready Set' of tasks was followed strictly by the manager's scheduler. An edge case is an agent recognizing that a 'Resource Failure' at a root node invalidated the entire branch, leading to a surgical pruning of the now-useless downstream tasks. This represents high-order graph coordination rather than mindless activity.
  - Selected interactions must display 'Constraint Adherence Resilience' where the agent blocks any worker from taking an action that would violate the hard constraints (H) defined in the workflow. You must be able to point to at least one turn where the manager rejected a 'shortcut' (e.g., skipping a sign-off) because the hard constraint demanded evidence preservation. A trajectory that completes the goal but fails the 'Safety Compliance' or 'Regulatory Completeness' validator must be rejected to ensure the synthetic data trains for governance-by-design.
* **Rejection Criteria**:
  - Reject any trajectory where the agent's 'Team Management' is purely coincidental, such as the manager happening to pick the right worker by name without ever reading their metadata or communicating with them. The orchestrator's capability must be grounded in an explicit, observable discovery event (e.g., get_available_agents). If the agent 'magically' knows a new teammate's skills without any investigative tool call, it is a synthetic failure. Ad-hoc coordination requires explicit inference from limited initial interactions.
  - Discard traces where the manager agent experiences 'Strategic Neglect,' failing to identify and resolve a visible bottleneck in the task graph (G). If a critical-path human worker is idle while multiple ready tasks are unassigned, the orchestration logic is broken. A high-quality trace requires the agent to be seen actively managing the queue to minimize 'Workflow Completion Time'. Any trace that hits the 100-step cap without completing a single major deliverable despite available resources should be rejected.
  - Reject any trajectory where the 'Communication' with the stakeholder is non-existent or purely generic (e.g., 'I am working on it'). The management challenge requires 'Transparent Stakeholder Communication' about trade-offs, progress, and impediments. If the agent makes a major pivot in the task graph structure without notifying the stakeholder, it fails the 'Human-on-the-Loop' governance requirement. This confirms the data represents professional orchestration rather than a silent, black-box agent.
  - Reject traces where the solution depends on 'Hidden Estimates' for task complexity or worker speed that were never queried or provided in the environment metadata. If the agent calculates that a task will take '5 hours' when the metadata said '10 hours,' and it uses this false estimate to claim an optimization, it is a halluncinatory synthetic failure. Every parameter in the manager's plan must be derived from the combination of the 'Task Metadata' and the 'Resource States' provided in the exploration phase.
