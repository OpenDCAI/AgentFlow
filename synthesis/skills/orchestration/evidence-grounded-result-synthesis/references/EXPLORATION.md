# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Begin by harvesting candidate situations where Evidence-Grounded Result Synthesis is the true bottleneck rather than a side effect of another failure. Inspect tool documentation, worker descriptions, and environment affordances before writing any question so that the future task is anchored in real operational constraints. For example, if several tools look similar but only one accepts the needed output shape, keep that contrast explicit because it is exactly what makes the seed useful for this capability.
  - Force the exploration process to expose at least one concrete decision point where the agent could plausibly make the wrong routing or control choice for Evidence-Grounded Result Synthesis. Record what information was available before the decision, what hidden trap existed, and what observable signals would let a strong orchestrator choose correctly. A good edge case is a situation in which a superficially reasonable shortcut would fail only after execution, because such cases separate shallow heuristics from real orchestration competence.
  - Prefer environments where the relevant information is distributed across tool descriptions, intermediate outputs, or state transitions, since Evidence-Grounded Result Synthesis should be tested under realistic coordination pressure. Do not rely on toy tasks whose answer can be guessed from world knowledge without touching the environment. A concrete example is a request that sounds simple in prose but becomes non-trivial once the agent must inspect schema details, dependency structure, or trust boundaries.
  - During exploration, log the exact observations that make the target behavior verifiable for Evidence-Grounded Result Synthesis. These observations should include the alternatives the agent could have chosen, the moment the correct path became identifiable, and the artifact that proves success. An important edge case is a trajectory where the early observations are ambiguous, but a later tool card or response clearly disambiguates the right move; keep such trajectories because they produce strong synthesis prompts.
  - Incorporate an explicit inter-agent review structure during the discovery phase, setting up scenarios where a Generator agent is pushed to fabricate facts about obscure subjects. Observe how a subsequently invoked Reviewer agent accesses fact-check databases to audit the initial claims. An edge case involves tasking the initial agent to 'describe the biography of a fictional King using historical tools', allowing the orchestration to trigger a grounding rejection loop.
* **Target Trajectory Profile**:
  - A good trajectory for Evidence-Grounded Result Synthesis must contain a decisive branching point rather than a straight-line, obvious solution. The branch should be understandable from the recorded observations, so that later reviewers can verify why the accepted path is correct and why the rejected path would fail. For instance, a trajectory is weak if every tool choice is unique and obvious from the first line, because then the capability is not truly under test.
  - The trajectory must remain compact enough that the capability signal is not drowned out by unrelated complexity. In practice, target 2 to 6 critical actions unless the environment itself makes shorter traces impossible, and ensure that every recorded step contributes to the target coordination decision. A useful edge case is a long environment interaction in which only one or two steps actually matter; reject those unless you can trim the irrelevant steps without losing coherence.
  - The intermediate observations must preserve the evidence needed to reconstruct why the final answer or final action is valid for Evidence-Grounded Result Synthesis. Each major action should leave behind an observable artifact such as a returned identifier, a validated field set, a dependency resolution, or a rejected malicious instruction. If the environment hides the key evidence and only exposes a final success flag, the trajectory is usually too opaque for synthesis and should be downgraded.
  - The trajectory should admit a clear contrast between success and a plausible near-miss. A near-miss could be a wrong tool with similar semantics, a valid tool invoked with the wrong payload, a safe action replaced by a hostile one, or a serial schedule where parallel work was available. This contrast matters because high-quality synthetic data for Evidence-Grounded Result Synthesis should teach the agent exactly what subtle mistake to avoid.
  - The trajectory must demonstrate a verifiable 'Mitigation Delta', where high-confidence ungrounded text undergoes significant refinement based on evidence-checking. A high-quality profile includes the exchange of structured meta-information (e.g., 'Whisper: Fact X is totally unsupported by Source Y') between the verifying step and the final output step. Rejected trajectories are those where the refining step merely appends a generic footer without fixing the core fabricated text.
