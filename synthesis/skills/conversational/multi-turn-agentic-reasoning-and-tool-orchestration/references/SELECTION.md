# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Verify 'Goal Completion Alignment' by checking if the final assistant turn successfully delivers the end-deliverable defined in the user's initial request. You must confirm that if a user asked for a 3-part update, the agent didn't terminate the conversation after completing only 2 parts. A successful case will show the progress rate reaching 100% on the internal milestone graph before the 'Final Answer' action is taken.
  - Demand 'Logical Plan Revision Fidelity' where the agent's 'Next Steps' list is updated in response to every observation. The selector must verify that the plan doesn't just repeat the same steps over and over; it must concretely remove completed items and add new recovery items based on tool feedback. For instance, if a tool returns 'User not found', the next plan step must be 'Clarify username with user' rather than 'Create account'.
  - Confirm 'Non-Mechanical Thought Reasoning' where the Reasoning (Thought) block contains at least 3 sentences explaining the choice of tool and parameters. We reject samples where the thought is just a copy-paste of the tool name (e.g., 'Thought: Use tool X'). The reasoning must justify *why* the tool is the current priority and how it helps achieve the overarching 'Next Steps' plan described in the Pre-Act logic.
  - Assess 'Action Parameter Precision' by matching the predicted JSON blob against the ground-truth schema for the targeted MCP tool. The trajectory is accepted only if the parameters (types and required fields) are 100% compliant with the tool's definition in the environment. An edge case to watch for is 'type-shifting', where the model provides a string for a field that requires an integer; these must be rejected to maintain operational reliability.
  - Check for 'Cumulative Context Use' where the agent retrieves a fact from Turn 1 to populate a tool call in Turn 5. The selection phase must verify that the agent didn't 'forget' the earlier constraint when reaching the end of a long-horizon plan. This is essential for distinguishing 'Long-Term Planning' from 'Step-by-Step Guessing', ensuring the agent treats the conversation as a single coherent session.
* **Rejection Criteria**:
  - Reject 'Single-Step Myopia' samples where the agent's thought block only mentions the immediate next action and fails to acknowledge the remaining workflow. Even for simple tasks, the Pre-Act architecture requires a multi-step plan (at least 2 steps: Act + Respond). If the 'Next Steps' field is a single line without a numbered list for a multi-faceted request, the sample belongs in a basic ReAct skill, not this one.
  - Discard 'Hallucination-First' trajectories where the model provides a plausible final answer without calling a tool that is clearly needed for grounding. If a user asks 'What is my status?' and the agent guesses 'Shipped' without calling the 'get_status' API, it is a hard rejection. This 'Short-Circuiting' behavior is the primary failure mode the Pre-Act approach is designed to prevent in agentic systems.
  - Eliminate 'Trace-Plan Contradiction' where the agent's 'Next Steps' list says it will do X, but the 'Action' field executes Y. This inconsistency indicates a breakdown in the agent's internal reasoning-to-action alignment. A representative failure is an agent planning to 'search' but then immediately 'deleting' something in the JSON blob, which would result in catastrophic tool use if not filtered out.
  - Refuse 'Looping Redundancy' samples where the agent repeatedly calls the same tool with identical parameters despite getting the same observation. The agent must show 'Progressive Movement' through the plan. If the plan remains static across three turns while the tool keeps failing with the same error, the agent is stuck in a loop and the sample must be discarded for poor dialogue control.
  - Reject 'Raw JSON Leakage' in the final response where the agent simply echoes the tool observation back to the user without summarizing it. The system response must be conversational and natural ('I've looked that up for you...') rather than technical ('Status: 200 OK, Body: {...}'). Any trace of technical protocol strings in the 'action_input' for the 'Final Answer' results in a rejection for FANC integrity violations.
