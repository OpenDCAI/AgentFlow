# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Implement 'Step-Aware Goal Decomposition' by using a secondary orchestrator model to break down complex user intents into a DAG (Directed Acyclic Graph) of tool calls. You must identify tasks that require at least 3-5 distinct tool invocations where the output of the first tool is a necessary parameter for the third. For example, in a travel scenario, the agent must find a flight (Tool 1), then Use the arrival time to find a shuttle (Tool 2), and then confirm hotel check-in based on shuttle timing (Tool 3).
  - Utilize 'Multi-Sampling Trace Generation' across different LLM backends to gather a diverse array of linguistic phrasings for the 'Plan' field. You should rotate between models to see how they differently phrase 'Previous Steps' and 'Next Steps' for the same tool-use trajectory. This ensures the synthetic data covers both professional planning lingo ('Phase 1: Retrieval initiated') and casual planning lingo ('First, I'm going to look this up').
  - Apply 'Dynamic Observation Perturbation' to create plan-revision scenarios where the initial tool call fails or returns ambiguous results. You must simulate tool errors like '404 Not Found' or 'Insufficient Data' to observe how the agent updates its 'Next Steps' list to include recovery actions. An edge case is a tool returning a 'Partial Success', where the agent must plan to retry the specific failed component rather than restarting the entire workflow.
  - Incorporate 'Irrelevance and Boundary Shuffling' by providing a toolset that is slightly mismatched with the user's ultimate goal. You should seed the exploration with queries that sound valid for an AI (e.g., 'Book a ride') but only provide tools for a different domain (e.g., 'Weather' and 'Math'). To execute this, verify that the logged reasoning trace explicitly identifies the 'Missing Capability' and plans an informative refusal instead of attempting a blind tool call.
  - Execute 'Contextual Intent Scaling' by expanding single-turn requests into multi-turn conversations where constraints are 'drip-fed' by a simulated user. You should start with a broad goal like 'Plan a trip' and introduce specific constraints like 'budget under $1000' and 'only non-stop flights' in turns 3 and 5. This forces the exploration to document how the 'Next Steps' plan is iteratively constrained and narrowed as the conversational memory grows.
* **Target Trajectory Profile**:
  - The trajectory MUST follow the 'Pre-Act' format: [User Prompt] -> [Thought: Previous Steps + Next Steps] -> [Action] -> [Observation] -> [Thought: Revised Plan] -> [System Response]. To satisfy this rule, every internal thought block must include a numbered list of future actions the agent intends to take to reach the goal. A high-quality profile will show the agent saying: 'Next Steps: 1. Retrieval of doc X. 2. Extraction of dates. 3. Verification of policy.'
  - Require 'Plan-to-Observation Adaptation' where the reasoning strings in later turns specifically reference data returned in earlier tool calls. To achieve this, the 'Previous Steps' section of the thought block must not be an empty string; it must contain a summary of the facts obtained so far. An edge case is a trajectory where an earlier observation changes the priority of the remaining steps (e.g., a flight is sold out, so the agent skips the hotel step).
  - Feature 'Action Recall Density' where the agent correctly identifies 100% of the ground-truth tools required for a complex task from the provided server list. The log should show the agent evaluating the 'Function Name' and 'Description' of multiple candidates before selecting the correct action_input. If the agent calls a tool that logically cannot solve the user's intent based on the metadata, the trajectory is invalid and must be discarded during the profiling stage.
  - Demonstrate 'Zero-Hallucination Parameter Grounding' where every value in the action JSON corresponds to a fact extracted from either the user's text or a previous tool observation. The trajectory must record the agent identifying the specific user turn where a parameter (like a 'booking_id' or 'zip_code') was provided. A failed profile is one where the agent 'guesses' a default value (like '90210') when the user has not specified a location, which should be tagged as a negative learning pattern.
