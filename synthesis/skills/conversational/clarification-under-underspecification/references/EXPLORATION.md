# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - **Start from capability-bearing situations.** Prioritize exploration states centered on sharded instructions, tempting partial specifications, and early-answer failure cases. The agent should search for naturally occurring dialogue moments where this pattern is necessary rather than fabricating an artificial test from scratch. For example, keep a case only when the surrounding context makes the capability matter to task success rather than to cosmetic style.
  - **Collect evidence before shaping the question.** First inspect the environment, dialogue history, and any tool-visible state to identify the exact evidence that will later support the final item. Only after the evidence is stable should the agent decide what the final user question ought to ask. An important edge case is a promising conversation whose target fact later turns out to be locally available, because that should be discarded before synthesis.
  - **Preserve the non-trivial part of the interaction.** During exploration, keep the aspect that makes clarification under underspecification hard, such as hidden constraints, distributed evidence, conflicting states, or perspective boundaries. Do not simplify the trajectory so much that a weak model could solve it by surface matching or recency alone. A useful practical check is whether removing one key turn would collapse the item into a much easier generic chat task.
  - **Record the trajectory in reusable operational detail.** The agent should log a trajectory consistent with progressive user reveals where the best first assistant move is a focused clarification rather than a full answer. Each logged step should tie an observation to an action so the later JSON output can be reconstructed without hallucination. If a candidate trajectory requires undocumented leaps or hidden assumptions, reject it during exploration instead of patching it later.
* **Target Trajectory Profile**:
  - **Require genuine dependence on conversation state.** A good trajectory should only be solvable when the agent really uses progressive user reveals where the best first assistant move is a focused clarification rather than a full answer. This prevents the skill from degenerating into a single-turn prompt hidden inside a longer transcript. If the same answer could be produced correctly after reading only the last user turn, the trajectory is too weak.
  - **Keep the ground truth auditable.** The trajectory should contain enough explicit evidence that another evaluator can reconstruct why the final answer or refusal is correct. Auditability matters because the later selection stage should verify the example with logical checks rather than taste alone. A common edge case is a plausible-looking trajectory whose gold answer depends on an unstated inference that no visible step actually supports.
  - **Include realistic distractors.** High-quality trajectories include nearby but wrong alternatives, stale facts, tempting guesses, or incomplete hints that make shallow retrieval fail. These distractors should be realistic enough to occur in ordinary chat, not cartoonishly adversarial. If no plausible distractor exists, the resulting synthetic item is often too easy to separate strong and weak agents.
  - **Preserve natural dialogue flow.** The turns should read like an ordinary user interaction for the target agent type rather than like a benchmark checklist. Naturalness matters because the whole purpose of the skill is to bridge casual user language to rigorous capability supervision. Reject trajectories that rely on meta-language such as naming the capability, citing the benchmark, or giving the agent grading instructions in the user turn.
