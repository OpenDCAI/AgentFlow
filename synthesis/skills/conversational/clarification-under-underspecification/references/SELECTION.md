# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - **Verify that the key difficulty is indispensable.** Accept a trajectory only when clarification under underspecification is necessary for success and not merely incidental. The evaluator should be able to point to one or more turns whose omission would destroy the capability signal. If the task remains equally solvable after removing the critical turn, the candidate should fail acceptance.
  - **Check objective support for the expected outcome.** The final answer, refusal, or action plan must be recoverable from the logged evidence and environment state. This rule is what keeps the dataset high precision even when the user wording remains casual and open-ended. An edge case to reject is a polished response whose correctness cannot be grounded in any specific observation from the trajectory.
  - **Demand visible separation power.** The accepted trajectory should create a plausible failure mode for weak systems in exactly the area covered by clarification under underspecification. This can be forgetting, stale-memory use, policy violation, premature commitment, perspective collapse, or another capability-specific error. If both strong and weak agents would likely behave the same way, the sample is not selective enough.
  - **Require concise final supervision targets.** Whenever possible, the selected item should end in a crisp answer, short rubric, or clearly checkable action sequence. Concise targets reduce evaluator disagreement and make the later synthesized JSON cleaner. If the only possible gold answer is a long vague essay with no checkable structure, the example should be downgraded or rejected.
* **Rejection Criteria**:
  - **Reject capability-lookalikes that do not truly test the skill.** Many conversations resemble clarification under underspecification on the surface while actually testing a simpler ability. Discard any candidate whose difficulty comes mainly from general writing fluency, generic world knowledge, or local paraphrase rather than the intended conversational capability. This filter is essential for keeping Level 3 dimensions clean and non-overlapping.
  - **Reject ambiguous or weak gold labels.** Do not keep trajectories when two careful evaluators could reasonably disagree about the correct answer, refusal, or action path. Ambiguity is especially harmful in synthetic data because the downstream model may learn instability rather than capability. A common example is a case with contradictory evidence but no timestamp or preference cue to resolve it.
  - **Reject examples that are too easy after local context compression.** If a candidate can be solved from one recent turn or one isolated snippet, it should not be used for a more demanding conversational capability. The trajectory should force the agent to use the broader interaction structure that the skill is meant to supervise. When in doubt, simulate a short-window baseline and remove the item if that baseline would almost certainly pass.
  - **Reject examples that import hidden state from outside the trajectory.** The agent should never need unavailable files, unstated schemas, or private annotator assumptions to solve the item correctly. Everything necessary for judging should be in the environment, the logged trajectory, or the explicit benchmark setup. If the candidate only works because the author knows extra facts not present in the trace, discard it.
