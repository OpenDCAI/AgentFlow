# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Decompose the answer into checkable atomic claims. Before deciding whether an output is grounded, split it into atomic or sentence-level propositions that can each be compared against the source. This reduces the chance that one unsupported clause hides inside an otherwise correct paragraph. An edge case is a response that mixes a supported fact with an unsupported causal explanation in the same sentence.
  - Execute entity-aware recursive decontextualization. Resolve all pronouns, unresolved entities, and context-dependent phrases into standalone statements before mapping claims to source evidence. A fact-checker must know that 'they deserve to know' evaluates to 'consumers deserve to know' prior to querying context. An edge case is an ambiguous pronoun that could refer to either the plaintiff or the defendant, requiring careful reading of the preceding paragraph.
  - Trace every claim to an exact localized evidence span. For each proposition, locate the exact, minimized passage that is supposed to support it, rather than citing an entire page. This turns citation checking into a precise alignment task that reduces cognitive load during verification. A practical example is a medical claim where the supportive span is merely a five-word parenthetical in the text.
  - Scan for intra-document structural and factual consistency. Explicitly track definite noun phrases (like 'the display') to ensure they have an indefinite antecedent (like 'a display') if testing formal structural logic. This applies primarily to legal, patent, or highly formal technical documents where grammar dictates factuality. A common edge case is a clause that references 'the aforementioned fee' when no fee was actually defined earlier in the document.
  - Audit document authenticity and stylometric integrity. Actively check domain metadata and scan text regions for abrupt drops in semantic diversity that indicate machine generation or spoofing. A source cannot ground a claim safely if the source itself is a phishing site or an unverified AI hallucination. An edge case is a seemingly official software manual hosted on a slightly misspelled domain name, which should be flagged before verifying any of the instructions inside it.
* **Target Trajectory Profile**:
  - A good trajectory resolves referential ambiguity explicitly. The path must demonstrate that a pronoun or vague reference was correctly expanded using the preceding text before the factual check occurred. If the claim is verified while still containing 'it' or 'they,' the trajectory is too shallow. An example is rejecting a path that tries to fact-check 'the measure failed' without first defining what the measure actually was.
  - A good trajectory aligns claims and evidence one by one with minimal span lengths. The path should make it easy for a reviewer to see which specific, minimal source span was used to evaluate each proposition. This proves the system is localizing support accurately. If the path only cited a whole document or page without proposition-level matching, it is considered too coarse.
  - A good trajectory demonstrates structured syntax linkage. It should actively trace grammatical/structural linkages, confirming antecedent logic or highlighting clear punctuation logic missing from high-stakes definitions. If evaluating a legal document, it explicitly names the missing referent. A strong edge case flags an error when 'the tenant' is used in page 3 but the contract only defines 'the leaseholder' on page 1.
  - A good trajectory ends in an auditable support judgment combining safety, structure, and factuality. The final label and explanation should be reproducible from the evidence path without requiring unstated assumptions. This keeps the synthetic corpus verifiable. If two different reviewers would need to invent missing reasoning to justify the same label, or if the agent ignored an obvious phishing URL, the trajectory is underspecified.
