# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - **Start from a clean source-text pool.** Begin with source texts that are fully understandable before you introduce repeated terms and entities whose translation should remain stable across the document. First collect texts whose gold translation objective is already unambiguous, then confirm that the target language, required output scope, and protected literals are all known. For example, use a clean announcement, dialogue, or short technical paragraph first, and only then inject the capability-specific stressor.
  - **Introduce only one primary challenge at a time.** Construct the exploration environment so that terminology consistency across documents is the dominant reason the item is hard, rather than mixing several unrelated difficulties in one sample. First write a clean base task, then add exactly one main perturbation family, and finally verify that the task would become easy again if that perturbation were removed. As an edge case, if a sample also contains rare jargon, long-document coreference, and strict formatting rules, discard it unless those elements are essential to this capability.
  - **Expose enough surrounding context to make the capability solvable.** The environment must contain the minimal discourse, glossary, or instruction evidence needed for a careful agent to succeed on terminology consistency across documents. First identify what hidden information the agent will need, then make sure that information is actually present in nearby text, metadata, or constraints, and finally record where it appears. For example, when a dropped subject can only be recovered from the previous sentence, include that sentence in the environment instead of forcing the agent to guess.
  - **Log the full discovery path, not just the final answer.** During exploration, record every observation that materially changes the translation decision, because later phases depend on real trajectory evidence rather than imagined steps. First save the raw prompt or source text, then note the exact cue that activates terminology consistency across documents, and finally record the action that resolves it. As an example, do not merely say "the agent translated successfully"; explicitly log that it spotted a repeated term, a typo cluster, a hidden rule, or an omitted referent and then acted on it.
* **Target Trajectory Profile**:
  - **Capability-first rather than corpus-first.** A good trajectory is one where the central bottleneck is terminology consistency across documents, not just generic translation difficulty. First inspect whether the item would still be hard for the same reason after replacing the topic with another topic, then keep it only if the answer remains yes, and finally annotate that core reason in the trace. For instance, a biomedical sentence with one obscure acronym is not automatically a good sample unless the crucial challenge is actually the intended capability.
  - **Short enough to audit, rich enough to verify.** Prefer trajectories that are compact enough for a reviewer to inspect step by step, but still dense enough to prove that the agent truly handled global lexical planning before sentence-level rendering. First cap the number of relevant clues to a manageable set, then ensure each clue has a visible effect on the translation, and finally check that a human can verify the chain without outside knowledge. A good edge case is a two-paragraph sample with one decisive cross-sentence clue; a bad one is a ten-page document where the signal is buried and unverifiable.
  - **Single dominant success path.** Keep trajectories where one clear sequence of observations leads to a uniquely justifiable translation choice, rather than many equally plausible paths. First identify the crucial observation, then verify that the translation would measurably degrade without it, and finally document the exact dependency. For example, if five different translations could all be defended and none is anchored to the trace, the trajectory is too weak for synthesis.
  - **Visible failure mode.** A good trajectory should make the wrong behavior easy to describe, because the later synthetic question should discriminate sharply between a capable and an incapable agent. First define the likely naive failure, then confirm that the approved trajectory avoids it for the right reason, and finally keep only examples where the difference is externally observable. Here the canonical trap is locally acceptable synonyms that are globally inconsistent; if a weaker system could fail silently with no clear output difference, the example is not selective enough.
