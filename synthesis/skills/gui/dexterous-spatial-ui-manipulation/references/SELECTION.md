# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Pixel-Perfect Target Grounding. Accept only trajectories where the drag start/end points are within a narrow pixel threshold of the ground-truth boundaries or satisfy text-snapping logic. You should verify that the coordinates fall within the active bounding box of the intended text span or widget. For example, if a drag ends in the empty space between two folders or inside the wrong word, the trajectory is invalid and must be discarded.
  - Geometric Constraint Satisfaction. Accept trajectories where mathematical relationships (containment, adjacency, centering) are strictly observed in the pixel metadata of the drawn or moved objects. Calculate the bounding boxes to confirm 'Circle inside Square' has 100% overlap with the circle being smaller. If a circle edge bleeds out of the square by 1 pixel, the trajectory is deemed a spatial planning failure.
  - Bbox-Level Index Alignment. For text-dragging, accept only if the mapped OCR IDs for the predicted start and end points match the actual text ground truth sequence. Calculate the index difference and ensure it accurately captures the semantic beginning and end of the requested sequence without unintended clipping. A valid case should perfectly map semantic bounds to corresponding visual pixel ranges.
  - Axis-Aligned Movement Integrity. For sliders or scrollbars, accept only actions where the mouse movement aligns with the primary orientation of the widget. Check the coordinate delta to ensure the agent didn't perform a diagonal swipe for a strict linear control. A valid case should show at least 90% alignment with the horizontal or vertical axis of the intended manipulation.
  - Stable Visual Persistence. Accept only trajectories where the result of a drag, draw, or selection is a stable, persistent UI update like highlighted text, a newly generated 3x3 grid, or a relocated file. Verify that the moved object exists in the destination or the text range remains 'blue-boxed' in the post-action screenshot. If a file is snapped back to the main folder due to an invalid drop zone hit, reject the seed.
* **Rejection Criteria**:
  - Coordinate Hallucinations. Reject trajectories where the mouse position jumps from A to B without a causal 'Drag' link, 'Hold' event, or 'MouseUp/Down' pairing in the action metadata. Ensure the 'MouseDown' and 'MouseUp' events are part of a continuous session for range-based tasks. If a file or selection suddenly appears in the destination without a trajectory trace, the seed is discarded.
  - Single-State No-Op Actions. Reject all cases where the agent simply clicks but does not move for a task that explicitly requires a range or geometric drawing. This indicates a failure to understand the dexterity required, as a simple click doesn't fulfill a drag-and-drop or text selection constraint. Clicking a folder without dragging the intended file into it constitutes an incomplete action.
  - Grid/Text Alignment Skew. Reject any case where the agent clicks outside the intended target bounds or draws geometric layouts that bleed over specified boundary rules. This ensures the synthetic data tests 'precision' rather than 'approximate clicking' in dense layouts. If a row of drawn check-boxes overlaps rather than remaining geometrically adjacent, the case is too sloppy.
  - State-Action Protocol Violation. Reject traces where the agent claims to be drawing or dragging, but fails to activate the required precursor tools (e.g., clicking on the Canvas without first selecting the 'Circle Tool' or 'Pen'). This demonstrates blatant state tracking failure. Drawing with a text cursor rather than a shape tool renders the dexterity attempt broken.
  - Ambiguous End-State Identification. Reject trajectories whose success depends on a 'guess' about whether a selection or drag-drop occurred. If there is no highlight, snap metadata, visible geometric rendering, or movement noticeable in the post-action screenshot, the trajectory should be removed. Dragging a file behind another rigid window where it becomes invisible is not a verifiable dexterous task.
