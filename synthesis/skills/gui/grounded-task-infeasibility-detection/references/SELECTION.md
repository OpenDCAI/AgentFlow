# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Grounded Refusal Requirement: Accept only trajectories where the agent's refusal is causally linked to a specific observed UI state or missing widget. You should verify that the 'Action Thought' refers directly to the screen content (e.g., 'The File menu does not contain an Export option'). For example, reject any path that simply says 'FAIL' without an associated observation of the absence of the target.
  - Exhaustive Search Documentation: Accept only traces that show the agent checking more than one logical UI location before declaring a task impossible. You must verify that the agent demonstrated 'due diligence' by exploring relevant submenus or using the application's internal search. A trace that declares infeasibility immediately upon seeing the home screen is only acceptable if the request is for a whole missing application.
  - Non-Hacking Success Pattern: Accept only cases where the agent's behavior cannot be replicated by a 'blind' FAIL-outputting model; the rationale must be task-specific. You should perform a cross-check to ensure the refusal logic matches the technical reality of the software (e.g., matching the refusal to a known deprecation in Windows 11). For instance, if the agent claims a feature is missing that is actually visible in the screenshot, the trace is rejected.
  - Verified Version Alignment: Accept only trajectories where the agent correctly identifies the OS or application version if the infeasibility is version-dependent. You should ensure the agent visited an 'About' or 'Properties' screen if the refusal reason cites a version limitation. A concrete example is a trace where the agent proves 'Smart App Control' is unavailable by opening the Security Center and showing it's disabled by the system.
* **Rejection Criteria**:
  - Generic/Blind Failure Code: Reject any trajectory where the agent outputs 'FAIL' or 'finish' without providing a natural language rationalization for the infeasibility. This prevents 'infeasible hacking' where models achieve high scores by guessing the fail-state without understanding. For example, a trace with only 'Observation: Home screen; Action: FAIL' is too thin for synthesis and must be discarded.
  - Hallucinated Blocker Claims: Reject cases where the agent claims a feature is missing when it is actually visible in the current or previous screenshots. You must perform a pixel-level check of the agent's 'absence' claims against the recorded UI tree metadata. If the agent says 'The Save button is gone' but the button is clearly in the top-left toolbar, the seed is rejected as a hallucination.
  - Transient Connectivity No-Ops: Reject trajectories where the 'infeasibility' is just a temporary system lag, network timeout, or loading animation that could be resolved with a 'WAIT' action. The agent must prove the blocker is durable and systemic rather than transient. For example, if the page is still loading and the agent says 'The website is empty,' it is an exploration error, not a grounded infeasibility detection.
  - Logic-Bypass Shortcuts: Reject cases where the agent declares a task impossible because it doesn't want to perform a long sequence of steps. You must ensure the task is truly impossible for *any* human user, not just tedious for the agent. For example, if a user asks to 'Check 100 emails for a code' and the agent says 'Too many emails, task impossible,' this is a planning failure, not an infeasibility.
