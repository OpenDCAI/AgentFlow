# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Functional Boundary Sweeping: When a task appears suspect, the agent must perform a comprehensive scan of all top-level menus and submenus to verify the absence of the target feature. You should explicitly record the elements present in the UI tree for each visited pane to create an 'Exclusion Log' of where the feature was not found. For example, if looking for an 'Export to Legacy' button, the agent should check File, Share, and Advanced settings before declaring it infeasible.
  - Feature Deprecation Probing: The agent should utilize the search box within the Settings or Help menus of an application to look for keywords associated with the user's request. You must document if the search results return 'No results found' or suggest more modern alternatives to the requested legacy command. A concrete edge case involves searching for 'IE Compatibility Mode' and noting that the system only points to 'Edge Enterprise Mode,' proving the original request is deprecated.
  - State-Dependent Availability Audit: Explore the GUI for 'greyed-out' or disabled widgets that might be the target of the user's request but are currently non-functional. You should record the 'Enabled' attribute in the accessibility tree and note the presence of tooltips or labels that explain why the widget is locked (e.g., 'Requires Admin' or 'File is Read-only'). For instance, if the user wants to 'Edit' a locked PDF, the agent must find the disabled edit button and explain that the file status is the blocker.
  - Cross-Version Comparison Search: If the environment appears to be an older or newer version than expected, the agent should find the 'About' section to confirm the software build. You must explicitly link the software version to any missing features requested by the user to provide a context-rich refusal. For example, if a user asks for 'Focus Mode' in an old version of Word, the agent should verify the version number before stating the feature is missing.
* **Target Trajectory Profile**:
  - Verification of Absence: A high-quality trajectory for infeasibility must include at least 3 distinct observations of the agent checking different logical locations for the requested feature. You should ensure the trace documentation includes the specific UI paths explored and the final thought summarizing why the search was exhaustive. For example, a trace should show the agent checking the context menu, the main ribbon, and the settings search bar.
  - Evidence-Based Reasoning Trace: The trajectory must feature an explicit thought process that reconstructs the latent intent of the user and logically contradicts it with the environmental state. You should provide a step-by-step rationalization of *why* the task is impossible, using 'Thought Completion' to fill in the gaps between observations. A valid trace would state: 'The user wants a Clear History button, but I am on a guest account where browsing data is not stored.'
  - Clean Termination Signature: The end of the trajectory must culminate in a formal refusal action (FAIL) that is accompanied by the specific observation-based reason. You should record the final screenshot where the lack of the requested widget is most evident (e.g., a blank search result page). For example, if the user asks for a non-existent file, the final observation should be the '0 items found' status in the file manager.
  - Resistance to Hallucinated Actions: The trajectory should demonstrate the agent's refusal to click on 'plausible but incorrect' elements that might share similar names but different functions. You must document any 'distractor' elements that were identified and dismissed during the feasibility check to prove a high trust boundary. An example involves the agent seeing a 'Settings' button but correctly noting it does not contain the specific 'Admin' sub-setting requested.
