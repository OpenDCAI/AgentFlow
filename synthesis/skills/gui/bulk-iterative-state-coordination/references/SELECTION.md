# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Set Completeness Verification: Accept only trajectories where the final count of extracted or processed items matches the ground-truth total found in the initial environment. You must perform a cross-check between the agent's output and the application state to ensure zero omissions. For example, if the table has 136 tasks, the agent's final answer must contain all 136 unique identifiers to be accepted as a success.
  - Zero-Redundancy Audit: Accept only those traces where no individual item ID or UI target was processed more than once, verifying the agent's deduplication logic. You should audit the action log for 'Double-Clicks' on the same coordinate or 'Repeated Entry' of the same data. A valid case proves that the agent successfully avoided the 'looping trap' by correctly identifying items it had already interacted with.
  - State-Sync Accuracy: Accept trajectories exclusively where the agent correctly identified the 'Refreshed' state of the UI after a navigation action like 'Next Page'. You must verify that the screenshots for Step N and Step N+1 are semantically different and that the agent acknowledged this change. For instance, if the agent clicks 'Next' but the first row hasn't changed, and it proceeds to re-process the old row, the trace must be rejected.
  - Operational Efficiency Ratio: Accept only trajectories that maintain a 'Step-per-Item' ratio within 1.2x of the human benchmark for that specific interface. You should penalize traces that take 10 steps to process a single row when a direct interaction is possible. A baseline example is accepting a 55-step trace for a 50-item list, allowing for initial setup but requiring streamlined iteration thereafter.
* **Rejection Criteria**:
  - Item Omission Failure: Reject any trajectory where the agent skips a visible item or a whole page of data without a grounded technical reason (like an error popup). This is a terminal failure in bulk processing and indicates a breakdown in iteration coordination. For example, if an agent processes items 1-10 and then jumps to 21-30, the seed is discarded.
  - Indiscriminate Data Duplication: Reject any case where the agent repetitively outputs the same result for different items or processes the same row twice. This often happens due to 'Perception Drift' where the agent thinks it is on a new page but is actually looking at a stale screenshot. If the final list contains duplicate entries from the same source row, the trajectory is a failure.
  - Unverified Sentinel Hallucination: Reject traces where the agent claims the task is 'finished' because it reached the bottom of a scroll area, while the 'Total Items' count in the header indicates more items are pending. The agent must verify its completion against all available environmental cues. For instance, stopping at 40 items when the UI clearly says 'Items Found: 50' is a rejection condition.
  - Inaccurate Iteration Logic: Reject cases where the agent attempts to use a 'Shortcut' that results in data corruption, such as trying to select all items via a header checkbox that only selects the current page instead of the whole set. You must ensure the agent understands the scope of its actions. If the user asked for all 50 and the agent only processed the first 10 on screen, it is Rejected.
