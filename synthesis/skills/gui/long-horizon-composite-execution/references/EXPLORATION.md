# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Knowledge-Augmented Sequence Mapping: When provided with a complex or messy user goal, you must first perform retrieval-augmented generation (RAG) against available technical wikis, manuals, or help documents. You should evaluate the technical entities mentioned (e.g., specific software versions, item tags, or hidden settings) to identify prerequisite states that the user might have omitted. For example, if a user wants to test a 'rendering bug,' use the wiki to find the exact commands for lighting or effects that accelerate the setup phase.
  - Reliability-First Command Substitution: Prioritize discovering if the target environment supports a command-line, console, or secondary interface that can bypass complex physical UI navigation. You must systematically check if actions like 'moving to a specific location' or 'spawning an entity' can be executed via a typed command instead of imprecise mouse-aiming or keyboard-navigation. A concrete case is using a `/setblock` or `/tp` command in a 3D environment to instantly achieve a state that would normally take 20 prone-to-error manual movements.
  - Hierarchical Step-Clustering Logic: Organize the long-horizon plan into 2 to 4 logical 'Clusters' (e.g., Setup, Preparation, Trigger, Observation) to maintain internal state focus. You should create a descriptive title for each cluster and group atomic actions within them to prevent the agent from becoming 'lost' in a flat list of 50 steps. For instance, cluster all 'world creation' steps together so the agent knows it is essentially 'bootstrapping' before moving to the 'triggering' phase.
  - Version-Specific Affordance Auditing: If the task involves software with a long update history, you must explicitly check the 'About' or 'Version' screen to align your plan with the environment's current capabilities. You should cross-reference the identified version against technical changelogs to ensure you don't attempt to use a command or button that was deprecated or not yet introduced. For example, verifying if the 'Bundle' experiment is enabled in a specific beta build before attempting to interact with it, as per high-fidelity bug reproduction rules.
  - Environmental Consistency Polling: Throughout long sequences, you must periodically stop and 'poll' the screen for environmental changes that signal progress or failure, such as progress bars or error toasts. You should compare the current visual state against the 'Expected Result' of each step cluster to identify 'Stuck in Loop' scenarios before they exhaust your iteration limit. A concrete edge case involves detecting a 'Menu Loop' where a click triggers a page reload rather than a navigation, requiring a plan-pivot.
* **Target Trajectory Profile**:
  - Direct-Path Efficiency with Shortcut Integration: A high-quality trajectory must demonstrate the use of programmatic shortcuts (commands or hotkeys) that quantifiably reduce the number of clicks required to reach the goal. You should verify that the agent chose a 1-step command over a 5-step manual GUI navigation for technical setups. For instance, a trace that types a command to set the weather to 'Rain' is superior to one that wanders through weather menus for 3 turns.
  - Unidirectional Progress with Cluster Transitions: The trace should show the agent successfully transitioning between 2-4 distinct logical clusters in a linear, purposeful fashion. You should monitor the 'Internal Thinking' logs to confirm the agent acknowledged the completion of one phase (e.g., 'Setup Complete') before engaging with the next (e.g., 'Applying Effects'). A gold trace should avoid 'backtracking' between clusters unless a specific environmental crash resets the session.
  - Technical Entity Accuracy: For tasks involving complex strings (like Part IDs, Commands, or JSON configurations), the trajectory must show 100% character-level fidelity. You should check the action logs to ensure that commands like `/effect give @p invisibility` were typed exactly as required by the system's syntax. A failure in a 30-step path often stems from a single typo in a command, so the trace must demonstrate rigorous character verification.
  - Stable Milestone Anchoring: The trajectory must record a verifiable success indicator at the conclusion of each step cluster, proving the milestone was actually reached. You should provide a screenshot or accessibility tree snapshot that clearly shows the intended UI modification (e.g., the 'Invisibility' status icon appearing). A trajectory that clicks blindly through steps without confirming the result of each 'Block' is considered unverified and noisy.
  - Causal reasoning and Reflection: Every major interaction in the trajectory must be justified by an internal thought process that links the action to a milestone in the step cluster. You should ensure the reasoning block explains *why* a specific shortcut was taken and how it serves the terminal goal. For example, the trace should state: 'Using setblock command to place water accurately, avoiding the unreliability of bucket-aiming in this version.'
