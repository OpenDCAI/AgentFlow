# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - **Seed screens first.** Start exploration from database-backed forms, file saves, debugger events, and persistent configuration changes where success depends on the task's underlying state change rather than on generic background context. First enumerate the immediately actionable regions, then note which local cues point out that the UI could look correct before the true state is committed.
  - **Ambiguity harvesting.** Prefer seeds where the distinction between transient visual cues and durable state changes is the real source of difficulty. Walk the interface until you can state exactly which UI element is insufficient on its own (like a disappearing success toast) and which additional clue resolves the target (like a persistent ID assignment), then save both in the trajectory notes.
  - **Business Logic Path Auditing.** Identify and document strict procedural dependencies where a terminal action, such as 'Post Invoice', is constrained by a prerequisite state like 'Manager Approval'. You should probe the UI to see if certain essential buttons are disabled unless a specific data field or status tag is populated and committed.
  - **Transactional Anchor Probing.** Identify the specific GUI widgets that trigger a database or persistent transaction (e.g., 'Save', 'Commit', 'Post Journal') and map their causal relationship to the target state change. Verify whether a successful transaction allows for a visible, long-term state shift across other application panes or dashboard counters.
  - **Shortcut rejection rehearsal.** Before accepting a seed, try the most tempting shortcut and confirm that it fails to establish that system or app state is actually changed. Document the failed shortcut attempt as a negative branch, then continue with the capability-relevant path so the final data explicitly separates naive visuals from proper backend-consistent results.
* **Target Trajectory Profile**:
  - **Minimum meaningful horizon.** A good trajectory should contain at least 3 meaningful state-changing actions. Count only actions that reveal new evidence or advance the state toward definitive backend system or app state modification.
  - **Schema-Grounded State Persistence.** The trajectory must show the agent holding specific identifiers, like an 'Asset Tag' or a 'File Location', through multiple navigation steps until the state change is confirmed. Verifiably extract the ID from the terminal screen to cross-reference it with the initial input parameter.
  - **Stable stop condition.** The trajectory must have a crisp stopping point anchored to a durable confirmation signal. Explicitly write down the first screen or internal state at which the new entry or saved variable survives persistent inspection, marking everything after that as noise.
  - **State-Agnostic Recovery Logic.** The trajectory should demonstrate the ability to verify completion even if a system reset or pop-up occurs midway. Ensure the agent re-navigates to the required view simply to audit the status of the persistent variable.
  - **Transferable structure.** The trajectory should embody a pattern that can be reused to synthesize instances without rote templating. Abstract the interaction into a schema—such as 'input block, commit trigger, durable verify action'—so similar data objects can be predictably validated.
