# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final imputation achieves a Distribution Invariant match where the mean and variance of the imputed data remain within 5% of the original non-missing data. The verification process must confirm from terminal logs that the agent ran a summary statistics comparison between the 'Pre-Imputation' and 'Post-Imputation' states. If a diffusion-based imputation introduces large outliers or shifts the median incorrectly, the solution is considered a failure as it will poison downstream models.
  - Accept only if the weak labeling logic accurately reflects the semantic rules provided in the project's evidence files. The selection check must verify that the labels produced (e.g., 'Normal' vs 'Arrhythmia') were derived from the specific thresholds found in the repository's documentation. An agent that 'guesses' labels based on an external pre-trained model when the task required rule-based supervision is disqualified for lack of fidelity. This ensures the data captured reflects the 'alignment' aspect of industrial data curation.
  - Accept only if the trajectory demonstrates a 'Fail-to-Pass' transition through at least one diagnostic verification turn. This means the agent must have observed a data quality failure (e.g., 'high null count' or 'low label coverage') and shown how its code resolved it. Selection favors agents that use the 'Error Metric' as a precise guide for their next architectural edit. A trace that correctly cleans the data on the first try without identifying the initial flaw is lower quality for training iterative reasoning.
  - Accept only if the final dataset follows the strict format and schema requirements of the project. The verification must confirm that if the training script expects a 'label' column as an integer, the weak supervision script produced integers and not strings. A specific check involves confirming that missing values were correctly cast to the destination type (e.g., float32) before being saved to the final H5 or CSV file.
* **Rejection Criteria**:
  - Reject trajectories that achieve 'Success' by hallucinating or inventing data points not justified by the environment's statistical seed. For instance, if an agent fills a column with random numbers to satisfy a 'Zero Null' check without using a valid imputation model or logic, it represents an engineering failure. Professional stewardship requires filling gaps with evidence-based estimates, not arbitrary noise. Any trace that 'invents' labels to bypass a count check must be discarded.
  - Reject traces characterized by 'Greedy Line-by-Line Scanning' of large data files without a hierarchical summary plan. An agent that simply prints a 1-million row CSV to the terminal to 'understand the data' fails the contextual efficiency test. The agent must use targeted 'head', 'info', or 'describe' calls to profile the environment effectively. This prevents the synthesis of 'noisy' data filled with redundant terminal output bloat.
  - Reject any trajectory that solves a data-preparation task by 'Sabotaging the Evaluator'—such as deleting the columns that contain missing values instead of imputing them. If the task was to 'recover the PM2.5 data', simply dropping all rows with nulls is a catastrophic failure of implementation. The agent must solve the data-density problem, not evade it by flattening the dataset. This ensures the synthetic data maintains the 'Engineering' challenge intended by the task.
  - Reject trajectories where the agent 'Shortcut-Hacks' a labeling task by using a single-rule heuristic for a multi-variate problem. If the manual provides 10 rules for arrhythmia and the agent only implements one (e.g., 'if x > 1') to get a 'Passing' score on a toy test, the data is poor quality. Expert agents should seek maximum coverage of the provided domain rules in their labeling functions. This protects against the synthesis of brittle, single-use data cleanup scripts.
