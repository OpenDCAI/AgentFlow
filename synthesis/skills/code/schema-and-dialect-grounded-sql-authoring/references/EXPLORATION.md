# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Translate the natural-language request into a schema linkage plan before drafting SQL. The agent should identify which entities, measures, filters, and grouping dimensions are likely needed, then search the schema for candidate tables and columns that realize each one. An edge case is when several tables share similar field names; the plan should keep multiple candidates alive until joins and semantics disambiguate them.
  - Treat dialect documentation as mandatory when nontrivial functions appear. Enterprise tasks often require warehouse-specific date truncation, array handling, null semantics, geospatial functions, or safe arithmetic. A high-quality trace explicitly consults those references instead of assuming generic ANSI behavior will transfer.
  - Use execution feedback to refine schema binding, not just syntax. When a query fails or returns implausible results, the agent should decide whether the problem is wrong table choice, wrong join, wrong function semantics, or wrong filter translation. This matters because many SQL tasks can be syntactically correct while semantically wrong.
  - Maintain a compact semantic map of resolved columns and unresolved columns. After each inspection or query attempt, record which fields have been confirmed for dates, identifiers, measures, or status logic, and which still require lookup. This reduces repeated schema wandering in very large databases.
* **Target Trajectory Profile**:
  - A strong trajectory should show the progression from task language to schema grounding to dialect-correct execution. Each stage should refine uncertainty rather than repeat the same guess in different wording. This mirrors how real analysts work in large warehouse settings.
  - A good trace should include at least one explicit dialect-sensitive decision. Examples include choosing the right date truncation function, safe division primitive, JSON accessor, or geospatial routine. Without such a choice, the task may be too generic for this capability.
  - The trajectory should preserve the difference between structural correctness and answer correctness. Passing parser checks or compiling SQL is not enough; the trace should also show why the resulting rows or aggregations answer the business question. This is especially important when multiple queries execute successfully but only one is semantically correct.
  - A high-quality trace should avoid overusing broad SELECT * exploration once the key entities are identified. Early probing is useful, but later steps should narrow toward minimal, auditable queries. This keeps the final synthetic trajectory realistic and information-dense.
