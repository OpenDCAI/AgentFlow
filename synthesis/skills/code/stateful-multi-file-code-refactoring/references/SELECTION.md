# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the trajectory includes successful edits in ALL files identified as affected during the exploration phase. The verification must confirm that the total 'patch' generated covers every callsite and import identified in the Global Dependency Map. If a single file remains in a broken state with an invalid reference, the multi-file refactor is considered a failure. For example, if the agent identifies 4 call-sites but only updates 3, the trajectory must be rejected.
  - Accept only if the final state matches the structural AST constraints defined by the task. The resulting code must not only be syntactically correct but must reflect the intended architectural shift (e.g., a function that was previously a standalone is now a method of a new class). This is verified by ensuring the agent's edits actually move the logic as requested rather than just patching errors. A concrete case is rejecting a refactor that leaves the original function behind alongside a new duplicated version.
  - Accept only if the agent demonstrates 'Trajectory Continuity' by finishing the task within the operational horizon. The trace must show a steady progression toward completion without looping or repeated exploration of the same files. If the agent spends 10 actions 're-searching' the same imports it already found, it indicates a failure of state management. Expert behavior involves systematic movement through the plan from start to finish.
  - Accept only if the agent uses 'Aliasing or Wrapping' correctly to maintain public API compatibility when required. If the task asks to maintain the original usage name while renaming the internal implementation, the agent must have implemented the correct export/import aliases. This ensures the refactor is 'safe' for external consumers of the codebase. A specific check involves verifying that '__init__.py' files were updated to expose the new internal names correctly.
* **Rejection Criteria**:
  - Reject trajectories that 'Lapse in Context' by repeatedly opening files they have already edited without making meaningful progress. This 'Trajectory Divergence' is a signal that the agent has lost track of the current state of the codebase. Any trace that exhibits more than two instances of re-reading a file without a corresponding logical correction should be flagged as low-quality. This prevents the synthesis of 'confused' agents that cannot handle long-horizon dependencies.
  - Reject traces that rely on 'Superficial Shortcuts' such as hardcoding string replacements without verifying the impact on the logic. For example, a global string replace of 'send' to 'send_helper' might break unrelated variables or methods. The agent must use targeted 'edit' commands that respect the structural context of each file. An agent that 'guesses' a line number instead of navigating to the symbol definition represents an unreliable refactoring pattern.
  - Reject trajectories that fail to resolve 'Recursive Dependency' errors introduced by moving code. If the agent moves a function to a new utility file but that utility file now needs to import the original module to function, it may create a circular import. A high-quality trace must proactively identify and break these loops by splitting modules further or passing dependencies as arguments. Any trace that ends with a circular import error in the logs is a failure.
  - Reject any trajectory that solves the task by 'Flattening' the architectural change into a single file. If the task requires moving logic between files, the agent must not solve the logic problem while leaving all code in the original file. This 'One-Shot Laziness' ignores the multi-file refactoring dimension entirely. The agent must prove it can operate across file boundaries safely and intentionally.
