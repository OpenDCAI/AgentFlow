# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Construct a Global Dependency Map before making any edits. This involves using 'grep' or 'find' to locate all occurrences of the target function, class, or variable across the entire repository. For example, if refactoring a base class, the agent must identify every child class and every instance where the class is instantiated as a dependency. An edge case is identifying dynamic imports or string-based references that standard symbol search might miss, requiring broader keyword scans.
  - Identify the 'Anchor' file where the primary structural changes start. The agent should determine which file holds the definitive declaration (e.g., helpers.py) versus which files are merely consumers. This creates a logical hierarchy for the refactoring plan, allowing the agent to decide whether to change the definition first or the consumers first. A concrete example is deciding to add a new parameter to a function definition before updating the callsites to avoid syntax errors in the consumer files during the transition.
  - Audit the existing Import Patterns to determine the required transformation type. Different files might import a function via 'from module import func' versus 'import module', requiring different refactoring strategies (e.g., updating the alias vs. updating the dot-notation path). The agent must categorize these call-sites to ensure its subsequent 'edit' actions are precisely tailored to each file's style. For instance, if a file renames the import locally, the agent must be careful not to conflict with the existing local alias.
  - Verify Visibility and Access modifiers in the repository structure. The agent must check if moving a function from one file to another changes its visibility relative to its consumers (e.g., moving from a private __init__.py to a public utils.py). This prevents 'AttributeError' or 'ImportError' issues that arise when valid code is moved to a location that breaks encapsulation rules. A specific edge case involves checking if a moved class still has access to the protected global variables it previously relied on in its original module.
* **Target Trajectory Profile**:
  - The trajectory must show a 'Compositional Progress' where multiple files are edited in a logical sequence. A high-quality trace demonstrates the agent moving from the definition site to the usage sites, explicitly stating which files remain to be processed in its internal reasoning. This proves the agent is tracking the 'state' of the refactor rather than performing isolated, disconnected edits. For example, the agent should state: 'I have updated the core utility; now I must navigate to the two middleware files that are currently broken.'
  - The trace should maintain a 'State Tracking' mechanism to identify divergence from the initial repo state. The agent should keep a mental or explicit list of all modified files and their current status (e.g., 'needs import update', 'implementation complete'). This is critical for tasks editing more than 5 files, where a standard context window might lead to 'forgetting' earlier files. An edge case is detecting when an edit accidentally introduced a typo in a file the agent thought it had finished.
  - A strong trajectory must explicitly handle 'Intermediate Broken States' without aborting the task. The agent should acknowledge that the code is temporarily unrunnable or has linting errors after the first major change and systematically resolve them across the trajectory. This distinguishes expert multi-file refactoring from naive bug fixing where the goal is 'never break anything'. A concrete example is an agent ignoring a 'Variable not defined' error in a second file because it knows it hasn't successfully moved the definition there yet.
  - Trajectories should prioritize 'Architectural Integrity' by checking for collateral damage in adjacent files. A good trace involves searches for related names or patterns to ensure the refactor didn't leave behind stale code or orphaned imports. For instance, if a class is moved to a new module, the agent should search for any docstrings or comments in other files that might still point to the old location. This reinforces the 'stewardship' aspect of high-level refactoring.
