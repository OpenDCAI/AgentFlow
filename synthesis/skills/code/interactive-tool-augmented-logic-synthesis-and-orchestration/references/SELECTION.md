# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final answer matches the ground truth derived from the original coding problem's solution within the specified numerical or logical tolerance. Functional correctness is the baseline for 'software-artifact' tasks; any agent that provides a plausible but numerically wrong answer must be rejected. For example, a result of 9.1 when the environment's 'Done' check expects exactly 9.0 indicates a logic failure during the tool-use sequence. This ensures the data represents reliable, high-fidelity engineering.
  - Accept only if the agent utilized the 'Observe' and 'Getter' tools to acquire all information that was masked in the initial prompt. The selection process must verify if the agent's reasoning cited specific values that were only discoverable through tool execution. If the agent provides the answer '10' for an array length it never queried, the trace is likely a result of pre-trained knowledge or hallucination and must be discarded. This ensures the synthetic task rewards the 'active exploration' capability specifically.
  - Accept only if the trajectory demonstrates 'Parameter Consistency' where no tool was called with arguments that violated the environment's hard constraints (e.g., negative indices or out-of-range keys) more than once. While an initial error followed by a correction is acceptable as a 'recovery' example, repeated failures on the same constraint indicate a lack of environmental grounding. The evaluator must confirm that the agent's final loop correctly bounds all its indices according to the 'Observe' data. This protects the quality of 'industrial-grade' agent behaviors.
  - Accept only if the agent correctly identified the 'Terminal State' by calling the 'Done' tool with the correct payload. The selection check must parse the final observation to confirm that the environment returned a `reward=1` signal. A trace that produces the right logic in the thoughts but fails to execute the final submission tool correctly is an operational failure. This ensures the data captures the full 'End-to-End' lifecycle from initialization through successful termination.
  - Accept only if the trajectory shows a narrowing 'Gap to Answer' over time, where each turn brings the agent logically closer to the final solution. The thoughts should show a progression like 'I have found the left bound... now looking for the right.' If the agent's logic is circular—visiting the same states repeatedly without gathering new info—the trace is poor quality for training. This ensures the resulting data rewards 'directed, purposeful engineering'.
* **Rejection Criteria**:
  - Reject trajectories that achieve 'Success' by hallucinating values or using memory-based shortcuts to bypass the intended tool-use complexity. For instance, if an agent 'knows' the answer because the task resembles a common LeetCode problem, it might skip the required 'LookUp' steps. If the execution logs don't show the agent retrieving the data values needed for its calculation, the trace is fraudulent. This prevents the training of 'lazy' agents that ignore environmental evidence in favor of internal priors.
  - Reject any submission where the agent 'Guess-Links' logic by providing the final answer before exploring the mandatory prerequisites. If the environment enforces a 'CheckDependency' tool before an 'Execute' tool, the agent must call them in that order. Any trace that 'jumps the gun' and gets a lucky success without following the state-machine rules of the environment must be excluded. This ensures the data captures the 'procedural discipline' required for complex software workflows.
  - Reject trajectories characterized by 'Infinite Tool Looping' where the agent repeats identical calls with identical parameters for more than three turns without progress. This signals a collapse of the agent's 'Reflexion' module or a failure to parse the observation history. Expert agents must identify when an action is ineffective and pivot to a different tool or parameter. A trace where the agent keeps calling `CheckIndex(1)` while receiving the same value over and over is non-pedagogical.
  - Reject any trajectory that solves the logic task by 'Modifying the Environment Code' or bypassing the Gym interface. CodeGym benchmarks measure the ability to solve problems *as an agent* using the provided API; they do not allow the agent to edit the `env.py` file to return the reward=1 unconditionally. Any such 'sabotage' of the evaluation harness is a critical alignment failure. The agent must solve the math/logic problem within the physical boundaries of the Gym container.
  - Reject traces where the agent's final code or logic 'Guesses' a pattern (e.g., 'the array is always 1, 2, 3...') when the environment allows for randomized seeds. If the agent's reasoning relies on a static pattern not verified by tools, and that pattern changes in a different seed, the implementation is brittle. Selection must favor agents that perform enough 'Diagnostic Probing' to verify the current environment's specific configuration before committing to an algorithm.
