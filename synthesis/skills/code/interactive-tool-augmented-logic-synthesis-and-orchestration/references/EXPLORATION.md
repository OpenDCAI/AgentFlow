# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform an 'Atomic Logic Boundary Mapping' by auditing the available tools to determine which specific sub-calculations or state queries they represent. The agent must read each tool's docstring to identify whether it retrieves a value (getter), modifies a state (setter), or performs a terminal check (validator). For instance, in a graph-based task, the agent should identify if 'GetNeighbors' is the only way to traverse the nodes, marking it as the primary discovery tool. A concrete failure is trying to solve the problem using a tool that only returns booleans when a numerical value is needed for the answer.
  - Implement an 'Information Density Probing' routine to sample the environment data at boundary points before committing to a full search. The agent should call the 'Observe' tool or equivalent to find the total data scale and then probe indices like 0, N/2, and N-1 to infer the data distribution status (e.g., checking if an array is sorted). This 'pre-flight check' prevents the agent from starting an O(N) linear search when a more efficient O(log N) approach is possible based on environment cues. An edge case is handled when the agent detects a 'sorted' property after just three samples, allowing it to pivot to binary search tools immediately.
  - Execute a 'Feedback-to-State Correlation' loop that updates the agent's internal mental model after every tool execution. After calling a tool and receiving an observation, the agent must document the transition of the 'known state' versus the 'unknown state' in its internal reasoning. For example, 'Current observation returns Arr[2]=9 and K=8; the search space [left, right] is now narrowed to [0, 2].' This prevents redundant tool calls and ensures that every action is a logical derivation from the accumulated evidence.
  - Monitor for 'Execution Syntax and Constraint Warnings' by intentionally triggering a minimal verification call to determine the environment's strictness. The agent should check if the environment requires specific data types (e.g., integers vs strings) by calling a tool with a standard input and observing the error log if it fails. If a tool returns a 'Timeout' or 'Memory Limit' error, the agent must immediately adjust its plan to reduce the number of redundant calls. A specific action involves catching a 'Value Error' and identifying that an index was out of bounds, prompting a correction of the boundary loop logic.
  - Conduct a 'Workflow Anticipation' pass where the agent predicts the outcome of the next 2-3 moves based on current tool-use success. Before acting, the agent should state its 'Expectation' regarding the returned value and a 'Fallback Plan' if the value differs from the prediction. For instance, 'I expect the next element to be larger; if it's smaller, the array is not sorted and I will switch to linear search.' This level of anticipation ensures the agent is prepared for dynamic environment variance and doesn't get stuck in a repetitive fail-loop.
* **Target Trajectory Profile**:
  - The trajectory must exhibit a clear 'ReAct' (Reason-then-Act) structure where every tool call is preceded by an explicit logical justification based on previous observations. A high-quality trace shows the agent resolving a specific uncertainty—such as 'I don't know the value at index 5, so I will call GetValue(5)'—rather than calling tools in a random or repetitive order. This ensures the synthetic task rewards strategic exploration rather than shallow pattern completion. An edge case is when the agent skips a call because it can mathematically infer the result from existing logs.
  - Strong traces should illustrate at least one 'Error Diagnosis and Recovery' turn where the agent corrects its own plan based on tool feedback. The agent might attempt an invalid index or use the wrong parameter type, receive an error message from the environment, and then explain how it modified its code-logic to fix the error in the current turn. This highlights the agent's ability to operate in 'brittle' software environments that enforce rigid execution protocols. A professional sign of quality is the agent seeing a 'Wrong Arguments' message and immediately checking the tool documentation to reconcile the parameter names.
  - Trajectories must demonstrate 'Compute Stewardship' by achieving the goal with a tool-call count that is within 20% of the oracle solution's efficiency. The trace should avoid 'blind scanning' where the agent queries every single index in a 100-item array when a binary search was feasible. High-quality data captures the agent narrowing its focus surgically based on the 'Observe' feedback. For example, 'The total length is 1000; I will use a logarithmic jump instead of linear stepping to save on tool-use rounds.'
  - The trajectory should preserve evidence of 'Intermediate State Persistence' by summarizing the current solved sub-problems in its thought blocks. For tasks requiring 10+ turns, the agent should occasionally restate the known variables (e.g., 'Values found: {0: 10, 5: 50, 10: 100}') to prevent context drift in its reasoning. This is particularly important for 'DP table' or 'Stack' based tasks where the logical sequence is cumulative. An edge case is the agent realizing its previous stack-state was incorrect and popping elements to reach a known-good configuration.
