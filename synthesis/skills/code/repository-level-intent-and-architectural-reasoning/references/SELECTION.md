# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the trajectory links at least two distinct code artifacts (e.g., a function and its caller) or a document and a code block to form an unbroken reasoning chain. The selection must verify that the agent didn't just 'find' the code but correctly interpreted the 'connection' between the disparate parts to answer the question. If a question is about implementation fidelity, the trace must cite the document's specification and the code's realization. This ensures the data captures the 'multi-hop' understanding required for architectural benchmarks.
  - Accept only if the final answer is explicitly grounded in the provided repository context through the citation of specific files, line numbers, or unique identifiers found during exploration. The selection check confirms that the agent is not relying on generic pre-trained knowledge about similar frameworks like Flask or Django but is addressing the project-specific implementation. For example, if an agent answers a question about a 'plugin hook', it must reference the specific variable name used in the project's `setup.py`. This ensures the synthetic data is high-fidelity and repository-specific.
  - Accept only if the trajectory demonstrates Intent-Aware Retrieval where the agent seeks both the 'How' (code structure) and the 'Why' (design rationale in docs). The evaluator should check for steps where the agent reads a docstring, a LaTeX footnote, or a commit message to justify an implementation choice before finalizing its response. This is the primary indicator of high-level reasoning vs. simple keyword matching. A trajectory that successfully answers a 'Why' question by citing a design rationale in a comment block is considered a high-value training signal.
  - Accept only if the final answer satisfies a completeness check by addressing all sub-parts of a compound question or all constraints of a complex feature. If the question asks for the 'workflow' of a system, the answer must cover initialization, execution, and termination phases as they are implemented in the repo assets. Any answer that stops after identifying a single file or misses a crucial architectural layer must be discarded. This ensures the data reflects the comprehensive understanding expected of an expert software developer.
* **Rejection Criteria**:
  - Reject trajectories that produce Generic Factual Answers which could be written without performing environment-specific research. If an agent explains 'what a decorator is' in general Python terms instead of 'how this specific decorator is implemented in this repo', it has failed the grounding test. This prevents the synthesis of 'empty' data points that don't actually test repository integration. A red flag is an agent that provides a correct definition but never cites a specific directory or file found via `ls`.
  - Reject traces characterized by Hallucinated Logic where the agent claims a feature exists or works in a certain way without displaying the code that proves it. Often, agents will guess how a standard library is utilized based on its name (e.g., 'it probably uses pluggy') without actually verifying the dependency in `requirements.txt` or the `imports` list. These assumptions are functional failures and must be discarded to keep the dataset valid. Every claim in the final answer must be traceable directly to a read observation in the trajectory.
  - Reject any trajectory where the agent 'breaks the fourth wall' by referencing the source paper's taxonomy or mentioning the search for a benchmark answer. The agent must maintain the persona of a professional developer answering a colleague's question natively within an engineering environment. Phrases like 'Based on the HCAST paper' or 'This satisfies the Locational requirement' indicate a failed persona and suggest the agent is not solving the task natively. This keeps the synthetic data realistic and deployment-ready.
  - Reject trajectories that solve a 'Where' question by providing a flat list of files without identifying the specific lines or blocks that implement the target feature. A list of filenames with no explanation of their internal roles is a failure of locational and functional precision. The agent must point to the specific 'main loop' or 'entry point' inside those files to satisfy the requirement. This ensures the synthesized data is useful for training models to perform surgical feature localization in large targets.
