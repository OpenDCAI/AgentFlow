# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Implement a Structural-to-Semantic Repository Audit by building a hierarchical directory map before inspecting specific code segments. The agent should use shell tools to list directories and classify folders based on names like 'core', 'docs', 'assets', or 'plugins' to identify primary technical hubs. For instance, if the goal is explaining authentication, the agent should first locate the 'auth' folder and its primary controller to avoid getting lost in unrelated test assets early in the trace. An edge case is an unconventional project layout where technical logic is hidden in a '/src/utils/experimental' folder, requiring the agent to use keyword-based recursive searches to locate semantic anchors.
  - Execute Multi-Hop Dependency Tracing across both source files and unstructured technical documentation. When the agent identifies a crucial class or symbol in the code, it must proactively search for where that element is defined in technical papers (PDF/TeX) or internal READMEs to understand its intended purpose. For example, if a method in 'models.py' uses a specific constant, the agent should search the LaTeX source files to find the mathematical derivation or paper table that justifies that constant's value. This approach is essential for answering 'Why' questions that represent high-level developer intent which code structure alone might obscure.
  - Perform Hypotheses-Driven Content Recovery using multimodal search tools to handle diverse file formats including source code, PDFs, and LaTeX. The agent should formulate search queries targeting abstract concepts like 'lifecycle hooks' or 'optimization constraints' then use tools like `pdfgrep` or `grep -r` to surface relevant clusters across binary and text assets. A concrete action involves checking if a research finding found in a PDF figure implies a sequence that is realized via a specific decorator in the Python implementation. An edge case occurs when documentation is purely visual, requiring the agent to use OCR or image-description flags to map diagram nodes to software modules correctly.
  - Conduct a Context-Aware Architecture Comparison to identify version guards and environment-specific logic paths. The agent must scan for conditional blocks that branch based on external library versions or hardware properties, recording the design rationale found in nearby comments or docstrings. For instance, it should identify checks for compatibility with legacy versions of a framework (e.g., GDAL < 3.4) and search the 'CHANGELOG' or paper appendices to understand why that specific path was chosen. This enables the agent to provide technically precise answers about 'intent' that account for the repository's evolutionary history.
  - Utilize Context Window Stewardship by isolating and reading only the relevant functional clusters rather than dumping exhaustive file contents. The agent should identify the exact boundaries of a feature—such as the start and end of a plugin discovery loop—and use targeted reads or regular expressions to extract only those lines. This maintains high reasoning focus and prevents the agent's mental state from being saturated by irrelevant boilerplate or redundant imports found in large files. A professional-grade sign of quality is the agent explicitly dismissing 'mock' or 'test' files that share names with production components but reside in disconnected subdirectories.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate an Iterative Refinement Loop where internal reasoning consistently updates the exploration path based on each new discovery. A high-quality trace captures the agent articulating a hypothesis—such as 'The data flow likely starts at the API endpoint'—and then successfully taking a tool action to verify that entry point. This distinguishes grounded investigation from repetitive wandering or blind guessing in a massive repository. For example, the agent statement should be: 'I found the interface in `interfaces.py`; I am now searching for its implementations in the `drivers/` directory to mapping the procedural flow.'
  - A strong trace includes the collection of Corroborating Fragments from at least two distinct asset types—typically a documentation file and a source code file. Since architectural understanding relies on synthesizing intent with implementation, the trace should show the agent combining a design rule found in a README with a concrete usage pattern in a class definition. This mirrors the real-world complexity of software engineering where no single file contains the complete truth about a system's intent. A concrete example is citing Section 4.1 of a PDF to explain the 'alpha' parameter found in `trainer.py`.
  - The trace should explicitly preserve the Semantic Contract of the code by documenting expected input/output behaviors and state changes observed during exploration. As the agent reads logic, it should record what it believes a function is supposed to return and explain how that return value satisfies the requirement found in the technical specs. For example, the agent might thought: 'The paper requires a log-sigmoid; I see the code implements `nn.Sigmoid` followed by a log; this satisfies the contract outlined in Equation 7.' This ensures the final synthesis is technically accurate and evidence-based.
  - High-quality exploration must maintain a zero-hallucination signal by strictly justifying every factual claim with a terminal log or read observation. Every assertion in the agent's thoughts regarding the repository's architecture must correspond to a specific file path and line number extracted during the discovery phase. Traces that contain 'guessed' names or assumptions about framework behavior that were never verified through `grep` or `ls` must be excluded. A professional sign of quality is the agent explicitly noting a 'negative result'—stating they searched for a feature and confirmed its absence to bound the problem scope.
