# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the generated test suite achieves a measurable 'Detection Rate' (DR) that identifies 100% of the provided incorrect human submissions. The verification process must confirm from the sandbox logs that every 'Wrong Answer' submission in the pool was caught by at least one of the synthesized test cases. If an incorrect solution manages to 'pass' the suite, the verifier is deemed insufficiently robust. This is the primary indicator that the agent has successfully bridge the 'cognitive bias' gap identified in leading benchmarks.
  - Accept only if the test suite demonstrates a high 'Diversity Ratio' or 'Distinct Error Pattern Coverage' (DEPC), ensuring tests are not redundant. The selection check must verify that the test cases reveal errors in different ways across the population of incorrect solutions. A suite where 50 tests all reveal the same off-by-one error is less valuable than a 5-test suite that reveals five different logical flaws. This ensures the synthetic data supports training for 'efficient' testing pipelines.
  - Accept only if every synthesized test case is functionally valid according to a ground-truth interpreter or reference solution. The selection must confirm that the 'expected output' in the QA pair exactly matches the result of running the ground-truth code on the generated input. Any test case with a 'Wrong Answer' in its own ground-truth verification must be rejected to prevent the synthesis of fraudulent evaluation data.
  - Accept only if the agent utilized appropriate specialized libraries (e.g., `random`, `math`, `numpy`) and followed the 'Case Script' paradigm to generate data programmatically. A suite that consists only of manually typed strings is considered low-quality for engineering agents. The selection process should check if the agent's logic is generalizable and can be re-run to produce new variants of the same adversarial patterns.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Test-Case Homogenization' where the agent only generates tests that look like the provided sample cases. If the samples are Easy level and the agent fails to generate Hard or Medium level adversarial samples, the capability is incomplete. Professional test engineering requires seeking out the 'blind spots' of standard testing logic. Constant repetition of the same boundary values without structural variation indicates a failure of the ideation module.
  - Reject any submission where the agent 'guesses' the correct outputs for its generated inputs without executing the ground-truth solution. This 'Output Hallucination' is a catastrophic failure of fidelity. The agent must use the 'Interpreter' phase to establish the ground-truth answer for every synthesized input. Any trace that 'invents' a mathematical result to pass a submission check must be permanently excluded.
  - Reject trajectories that achieve 'Success' by modifying the problem constraints or the ground-truth solution to fit its own generated tests. For example, if an agent changes the problem from 'N is prime' to 'N is odd' because its generator is buggy, it is a breach of stewardship. The agent must align the tests to the environment, not the inverse. This filter eliminates 'lazy' agent behavior that bypasses technical difficulty by breaking the task's rules.
  - Reject traces where the generated tests are so large or complex that they violate the environment's 'Time Limit' or 'Memory Limit' during ground-truth verification. A verifier that takes 10 minutes to run is not scalable for reinforcement learning or dynamic evaluation loops. The agent must optimize its 'Python Case Scripts' to generate efficient, reasonably sized inputs that still capture the intended adversarial complexity.
