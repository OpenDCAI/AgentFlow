# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a Multidimensional Specification Analysis by mapping all qualitative constraints in the problem description directly to technical code anchors in correct solutions. The agent should first identify the primary algorithm and then search the ground-truth code for 'defensive logic' such as boundary checks for N=1 or specific if-statements handling empty inputs. This ensures that the generated tests are grounded in the 'ideal' architectural behavior of a correct solution. An edge case is when the problem text refers to a constraint that the baseline solutions implicitly handle but do not explicitly check, requiring the agent to deduce the rule from code comments.
  - Execute a Differential Failure Profiling pass by comparing the execution traces of successful solutions against known human-written bugs. The agent must run both versions side-by-side using a tool like a sandbox runner to locate the exact inputs where their outputs diverge. This 'divergence search' allows the agent to pinpoint common failure modes—such as integer overflows, greedy stability errors, or off-by-one indices—that are otherwise elusive. A concrete action involves analyzing the 'standard error' of a failing submission to see if it crashed due to memory limits, directing the generation of 'stress-test' inputs.
  - Deconstruct Defense Patterns into formal Mathematical Explanations and logical constraints. The agent should identify complex problem-solving strategies (e.g., handling negative cycles in graphs) and decompose them into specific testable properties like 'equivalence classes' or 'extremal values'. It then documents these strategies in a structured log, such as 'Testing for circular pairings in prime-sized tournaments'. This symbolic mapping prevents the agent from generating 'random junk' and instead ensures every test case targets a specific engineering invariant.
  - Conduct an Executable Case-Script Audit to plan the programmatic synthesis of complex input structures. The agent must decide whether a task requires simple random sampling or specialized generators for objects like DAGs, balanced trees, or convex hulls. It should write and run minimal Python 'sanity checks' to verify that its proposed generation logic—such as a random graph generator—correctly adheres to the problem's structural rules (e.g., connectivity or acyclicity). An example is identifying that a problem uses 1-based indexing for nodes, requiring the generation script to shift all generated values by +1.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate a clear transition from 'Constraint Extraction' to 'Input Generation', where every generated test case is justified by a specific observation of a problem limit or a failure pattern. A high-quality trace shows the agent explicitly noting a boundary value like 'N is up to 10^18' and then writing a script specifically to generate that extremal value. This confirms the agent is not just 'vibe coding' but is performing rigorous test engineering based on physical environment limits.
  - A strong trace includes an 'Incremental Potency Verification' loop where the agent checks if its new test cases actually reveal errors in previously passing (but known-buggy) code. The agent should demonstrate a flow: generate a test case, run it against a 'plausible' solution, observe if it detects the bug, and if not, refine the input parameters to be more 'adversarial'. This 'closed-loop' behavior proves the agent can handle the 'homogenization trap' by intentionally seeking lower correlation between tests.
  - The trajectory should preserve evidence of 'Self-Validation Stewardship' where the agent writes code to verify its own test inputs before using them. A professional-grade trace shows the agent executing a `validate_inputs()` function to ensure its generated graph is actually connected or that its generated prime numbers are actually prime. This ensures that the finally synthesized task has a 100% 'Retention Rate'—meaning every test produced is valid and grounded in the ground-truth solution.
  - High-quality exploration must maintain a 'Diversity-to-Potency' balance by documenting the unique coverage provided by each new batch of tests. The agent should use internal reasoning to state: 'Test case A covers small integers, Test case B covers the overflow boundary, and Test case C covers the non-prime modulus.' This documentation defines the 'expert verifier' capability—the ability to build a test suite that is as broad as possible with as few tests as possible to minimize computational overhead.
