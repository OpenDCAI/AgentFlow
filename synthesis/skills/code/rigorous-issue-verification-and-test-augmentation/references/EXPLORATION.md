# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a Hierarchical Candidate Localization to isolate the most relevant files before drafting the test. The agent should first retrieve a wide set of 10 candidate filenames based on issue keywords, then use a second refinement step to select specific functions from those files that likely contain the bug or the existing test scaffolding. An edge case is looking for 'focal functions' (the code being fixed) versus 'test functions' (the code that checks it), as the agent must calibrate its context by reading both. This prevents context window saturation while ensuring the test is placed in the correct project-specific class.
  - Implement a Self-Reflective Action Planning loop to decide which specific code to read and which test to write. The agent must generate a list of atomic actions—Read, Write, or Modify—and then 'reflect' on the plan's validity by checking if the targeted function names actually exist in the current directory tree. For instance, if the plan identifies 'test_login' as an update target, the agent must verify its existence before committing; if invalid, it must replace it with the closest matching name. This mimics professional iterative planning and prevents 'blind' code generation that often leads to syntax or resolution errors.
  - Construct a 'Data-Requirements Mapping' to identify missing environment state or fixtures needed for reproduction. The agent should scan the target test file's 'imports' and 'setup' methods to understand how to instantiate the objects required for the new test case. If a project uses specific testing fixtures (e.g., @pytest.fixture), the agent must ensure its new reproduction test utilizes those same anchors to maintain consistency with the existing suite. An edge case is a project where tests are generated dynamically from templates, requiring the agent to analyze the template structure before adding its own fail-to-pass instance.
  - Execute a 'Reproducibility Baseline Check' by running current tests to confirm they currently PASS or DO NOT catch the bug. Before generating new ones, the agent should run the existing suite and observe that it doesn't fail, proving that the issue is indeed a 'gap' in coverage. This provides a 'compass' for the synthesis phase, where the goal is specifically to move from a 'Pass' (bug exists but not seen) or 'Error' state to a clear 'Assertion Failure' (bug reproduced). For example, if the current test only checks integers, the agent identifies that check as insufficient for the reported float-precision bug.
  - Integrate a Static-Analysis-Led Import Repair protocol to ensure the synthesized test is executable without manual intervention. The agent should generate the test code and then immediately pass it through a linter (like Flake8) to detect 'NameError' or 'ModuleNotFoundError' signals. It then uses shell tools to find the correct module paths within the codebase and patches the imports in the generated test. This ensures that even if the model hallucinates a path, the exploration-led feedback loop corrects it before finalizing the synthesis.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate an explicit 'Fail-before-Fixing' signal by executing the generated test on the original codebase. A high-quality trace shows the agent observing a non-zero exit code or an assertion failure (e.g., 'AssertionError: None != expected') and documenting that the bug is successfully reproduced. This proves the test is issue-grounded rather than a generic or hallucinated script. An edge case is an agent correctly distinguishing between a 'SyntaxError' (bad test) and an 'AssertionError' (good repro).
  - Maintain a 'Cumulative Planning Record' where the agent's actions are justified by its previous reads. The trace should show the agent reading a focal function, identifying a missing 'if' branch for null values, and then stating: 'I have read the vulnerability; I will now write a test case specifically targeting this null-handling branch.' This evidence-to-action chain separates expert engineering from opportunistic code completion. For instance, the agent should cite the specific line number in its thought process that it intends to exercise with the new test.
  - Demonstrate 'Structural Fidelity' by placing new tests within the detected class hierarchies and import styles of the repository. A high-quality trace shows the agent extracting the skeleton of an existing test file—including imports and class definitions—and proposing a specific insertion point (e.g., after the 'test_basic' function). This ensures the synthetic data maintains the 'Software Engineering' aspect of the capability, preventing the creation of disconnected, standalone files that don't integrate with the CI/CD pipeline.
  - Exhibit 'Iterative Plan Refinement' when the agent encounters satisfied/unsatisfied self-evaluation outcomes. The reasoning should document the agent's self-reflection turns (at least 2 for complex issues), where it critiques its own proposed test for being 'too simple' or 'missing an import'. This behavior defines the 'robustness' of the skilled agent—the ability to catch its own mistakes before the evaluation harness does. For example, the agent might thought: 'Wait, I am missing the pandas import for the PolyFit test; let me update the plan to include the import fixing step.'
