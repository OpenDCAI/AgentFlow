# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the synthesized test achieves a verifiable 'Fail-to-Pass' state transition. Specifically, the test MUST fail on the old code version (proving reproduction) and pass on the new code version (proving verification). Any test that passes on the buggy code version is a 'False Positive' and represents a grounding failure. This is the primary metric for determining if the synthesized data reflects real-world engineering value.
  - Accept only if the test demonstrates a high 'Adequacy Score' through line coverage on the relevant code changes. The selection process must verify that the test actually exercises the lines of code added or deleted by the pull request. A test that passes but has 0% coverage on the updated logic is 'suspicious' and should be rejected for this capability. This ensures the synthetic tasks rewards deep logical integration rather than lucky assertion passing.
  - Accept only if the generated code is syntactically correct and successfully integrates with the project's native test runner (e.g., pytest, unittest). The selection must confirm from the logs that the test was collected and executed by the environment's standard configuration. If the implementation requires manual human correction of imports or indentation to run, it is considered a functional failure. A specific check involves confirming that the test handles external fixtures correctly.
  - Accept only if the trajectory includes successful 'Localization' of both focal and test entities. The agent must have found existing files that are materially related to the issue to justify its implementation. A trace that 'guesses' a filename successfully without showing the search observation is lower quality than one with explicit architectural grounding. This confirms the agent can operate at scale in dense, multi-file repositories.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Test-on-Old Pass' behavior, where the agent claims to have found a repro test but the test executes successfully on the buggy code. This indicates the agent failed to capture the 'defect' described in the issue. Such data points are non-pedagogical and encourage the training of agents that write ineffective tests. Any test that doesn't produce an error or failure on the baseline must be discarded.
  - Reject traces where the 'augmented test' solves the issue by 'Over-fitting' to the sample inputs provided in the prompt. If the agent hardcodes the specific values from the issue report into an 'if' statement within the test logic instead of implementing a general validation rule, the data is poor quality. Expert agents should identify the general edge case (e.g., all sequences of length zero) rather than just the specific one reported. This protects against the synthesis of brittle, single-use reproduction scripts.
  - Reject trajectories that 'Sabotage the Environment' by deleting existing tests or modifying the test harness to ignore failures. In the domain of verification engineering, the goal is to expand the proof of correctness, not to hide errors. Any trace that comments out a 'failed' check to make the suite look 'clean' represents a failure of professional engineering integrity and must be permanently excluded from the pool.
  - Reject any submission where the agent demonstrates 'Semantic Hallucination'—using function names or logic that sound plausible but conflict with the real repository structure. For instance, if the agent tries to call 'self.client.get()' in a library that doesn't use Django Test Client, it has failed the fidelity test. This ensures the resulting data rewards the 'Grounding' capability described in recent SWE benchmarks.
