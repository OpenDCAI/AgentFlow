# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Establish a Performance Identification Protocol by executing the initial code in a sandbox to capture absolute metrics for runtime, peak memory, and the integral score. The agent must never rely on static Big-O analysis alone but must trigger a real execution on validated test cases to establish a baseline. For example, a script might be O(N) in theory but plagued by high constant factors or inefficient instruction selection that only surface during a real-world execution run.
  - Execute a Hardware-Aware Instruction and Logic Audit when dealing with low-level or binary targets to identify missed optimization opportunities. The agent should search for specialized CPU instructions like population count, conditional moves, or vector extensions that can replace long generic instruction sequences. A concrete step involves mapping a loop-based algorithm in C to its assembly counterpart and identifying if the compiler missed a specialized hardware-based shortcut. An edge case occurs when a specialized instruction is faster but requires specific memory alignment that the agent must proactively configure.
  - Analyze the 'Efficiency Gap' by comparing the agent's baseline performance against a distribution of reference solutions, human-level percentiles, or industry-standard compiler-generated code. The agent should search for metadata—such as median execution times or compiler flags—to determine if the current code is a 'mediocre' solution requiring a fundamental algorithmic shift or an 'optimized' solution requiring surgical implementational tuning. A high-quality trace explicitly documents that code in the 20th percentile requires a new data structure, whereas code already optimized by a compiler may require instruction reordering or stack canary removal.
  - Deconstruct Logic Boundaries into 'Critical Path' components to isolate specific bottlenecks in control flow and stack management. The agent must identify which modules or functions consume the most CPU cycles, such as heavy input-output routines or deep recursion chains. A professional action involves substituting heavyweight function variants or checked routines with simpler, functionally equivalent versions that reduce execution overhead. For instance, if a standard library function include unnecessary security metadata for a performance-critical internal loop, the agent should plan to use a lighter alternative that satisfies the same semantic contract.
  - Utilize Incremental Probing to measure the impact of specific transformations before committing to a full architectural rewrite. The agent should apply a single optimization, such as replacing a list with a deque or unrolling a loop, and execute a sub-suite of tests to verify the delta in performance metrics. This prevent 'black-box' optimizations where multiple changes obscure which specific edit improved the execution profile. An example is handled when the agent identifies that a measured 5% speedup is within the environment's noise floor, prompting a move toward more impactful transformations.
  - Maintain an Audit Ledger of Divergent Strategies to track which optimization paths (e.g., JIT compilation, vectorization, or algorithmic pruning) have already been explored and rejected. This ensures the long-horizon trajectory does not backtrack into inefficient patterns that were previously proven to be ineffective in the current sandbox. A concrete step is recording that 'Attempting multiprocessing failed to reduce total integral score due to high overhead; I will focus on single-threaded branch elimination next' to maintain a directed search through the optimization space.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate a 'Closed-Loop Refinement' where every major code edit is preceded by a performance observation and followed by a validation run. A high-quality trace shows the agent moving from a functionally correct but slow script to a high-percentile efficient script through a series of justified edits. For example, the agent observes a long execution time, identifies a nested loop, and replaces it with a specialized hardware instruction or a more efficient data structure.
  - A strong trace includes evidence of 'Multi-Dimensional Trade-off Management' where the agent balances speed, memory, and security constraints to optimize the global objective. The agent should demonstrate it knows that a 2x speedup that uses 10x more memory might actually decrease the overall efficiency score. This is signaled by thoughts like: 'I could unroll this loop for speed, but the code size limit requires me to keep it compact, so I will prioritize register allocation instead.' An edge case is the agent deciding to remove stack protectors specifically for a performance-isolated benchmark while acknowledging the security trade-off.
  - The trajectory should preserve a 'Step-by-Step Performance Ascent' where the metrics improve or stabilize across iterations without regression. Instead of a single-shot jump, the trace should capture multiple iterations of refinement, demonstrating that the agent is capable of sustained self-improvement through empirical feedback. A specific sign of quality is the agent seeing an improvement in runtime and then immediately trying to squeeze even more performance out of the new hardware-specific bottleneck identified by the latest log.
  - High-quality exploration must exhibit 'Contextual Hardware and ABI Fidelity' by adapting the solution to the specific processor architecture or calling conventions detected. The agent must demonstrate an understanding of different cache sizes, register widths, or calling protocols (e.g., passing arguments via registers vs. stack) during the implementation. This is evidenced by steps where the agent queries device properties or assembly metadata before finalizing the logic to ensure the optimized program is valid and executable. An example is the agent correctly setting up the RSP and RDI registers before invoking a system call in assembly-level tasks.
