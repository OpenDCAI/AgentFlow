# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final performance metric is strictly superior to the initial performance metric with respect to the given efficiency instruction (time, memory, or speedup). The verification must confirm from terminal logs that the execution time or speedup factor has improved beyond a statistically significant threshold compared to the baseline. If the speedup is assigned a default of 1.0 because the code failed to beat the compiler, the trajectory is deemed a failure for this specific capability.
  - Accept only if the optimized code achieves functional parity via a 100% test-passing rate on an exhaustive test suite with high line and branch coverage. Performance gains are invalid if functional behavior diverges from the original ground-truth source code or if the program crashes under edge cases. The selection process must parse the 'success' counts from the test runner to confirm that every assertion was satisfied without exception. For assembly targets, this includes verifying that input-output behavior matches the original executable perfectly.
  - Accept only if the trajectory demonstrates 'Failure-to-Success' resilience by resolving at least one execution-time friction event like a compilation error, segmentation fault, or runtime crash. The trace must record the agent identifying the specific diagnostic log (e.g., 'invalid instruction' or 'stack corruption') and applying a targeted fix. This confirms the agent can handle the interactive and often brittle nature of low-level optimization and system-level engineering.
  - Accept only if the generated solution follows strict 'Software Stewardship' by maintaining the original ABI, API signatures, and mandatory return types. While the internal implementation is optimized, the external interface must remain compatible with the surrounding codebase to ensure the artifact is reusable. Any edit that renames a mandatory function or corrupts the stack pointer such that the caller crashes must be rejected.
  - Accept only if the trajectory demonstrates 'Selection-Aware Improvement' where the agent compared multiple candidate implementations and selected the one with the highest measured efficiency. High-quality data shows the agent generating variations (e.g., different loop transformations or instruction choices) and picking the one that maximizes the performance percentile. This ensures the data reflects the deliberate model-as-optimizer behavior required for self-improving systems.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Constraint Blindness' where the agent repeatedly ignores performance feedback to produce the same suboptimal or slow code. This indicates a failure of the feedback loop where the agent identifies a bottleneck but fails to propose a logically higher-class algorithm. Loops of identical TLE failures or identical speedup logs despite code changes are grounds for immediate rejection.
  - Reject any submission where the 'Optimized' output is achieved by 'Reward-Hacking', such as modifying the benchmark scorer, the test cases, or the baseline performance metadata. For instance, the agent must not delete assertions to make a failing implementation look successful or artificially inflate baseline execution times in its thoughts. The evaluation must always be grounded in the independent, unmodifiable results of the execution sandbox.
  - Reject traces where the optimization is achieved through 'Syntactic Sabotage' like hardcoding specific results for provided test inputs or implementing a lookup table instead of general logic. If the agent adds 'if input == x: return already_computed_value' solely to pass a latency check, it is a failure of generalization. The speedup must be the result of a generalizable algorithmic or implementational improvement that applies to the entire problem class.
  - Reject trajectories producing 'Invalid Control Flow' or violating low-level conventions, such as corrupting the stack canary, mismanaging registers, or failing to preserve the stack frame. Especially in assembly tasks, implementations that omit safety setup or use incorrect function call conventions cause undefined behavior and are considered failures. A professional agent must prioritize logical and hardware-level correctness as the foundation for any performance gain.
  - Reject submissions that demonstrate a 'Stagnation Plateau' where the agent stops optimizing despite the code remaining significantly below human or compiler efficiency targets. If the agent claims 'no more improvements are possible' when a specialized hardware instruction or a better algorithmic class is clearly applicable, the capability is incomplete. Professional performance engineering requires a persistent search until the performance distribution is saturated.
