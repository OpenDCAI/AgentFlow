# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final implementation passes 100% of the exhaustive test suite including secret test cases, not just the provided sample inputs. The capability depends on the robustness of the solution under diverse conditions; a implementation that fails on large N or specific edge cases is functionally incomplete. For a high-difficulty task, the selection process must verify if the agent's code produced the 'Accepted' signal on the full contest judge. This is the primary indicator of informatics-competition success.
  - Accept only if the solution's empirical execution time and peak memory usage are strictly within the limits provided in the prompt. The evaluator must check the terminal logs or profiler output to confirm that the code didn't just 'run' but ran *efficiently* (e.g., solving N=10^5 in 0.8s for a 1s limit). A correct algorithm implemented in an inefficient way that triggers a TLE is a failure for this specific skill. This ensures the synthetic data captures high-performance engineering rather than generic logic.
  - Accept only if the trajectory demonstrates 'Iterative Refinement' when faced with negative feedback. The selection filter should reward agents that interpret a judge's error (like TLE or WA) and successfully adjust their code to fix it. A trace that makes zero errors is acceptable but less valuable than one that shows the 'correction loop' where a CE or RTE was resolved. This confirms the agent can handle the interactive and hostile nature of competitive environments.
  - Accept only if the implementation avoids 'Hardcoded Hacks' or 'Sample-Specific Logic'. The code must be generalizable and based on the underlying algorithm; for example, using a general modular exponentiation rather than a set of if-statements for sample values. The selection process must ensure that if the input values are changed within the specified constraints, the code still functions correctly. This prevents the inclusion of lucky or deceptive traces that 'cheat' the evaluation.
* **Rejection Criteria**:
  - Reject traces characterized by 'Constraint Blindness' where the agent repeatedly ignores TLE/MLE feedback to produce the same slow or hungry code. This indicates a failure of the feedback loop and results in repetitive data that does not teach optimization. A professional agent must recognize when a specific algorithmic class (like O(N^2)) is exhausted and pivot to a more advanced structure. Loops of identical TLE failures are grounds for immediate rejection.
  - Reject any trajectory that solves the task by 'Environment Compromise' or attacking the grader to force a success. This includes actions like modifying the hidden judge scripts, attempting to read the secret test files from the server, or manipulating the timeout signals. Proper informatics stewardship requires solving the algorithmic problem within the provided sandbox constraints. Any such 'adversarial' behavior is a critical alignment failure.
  - Reject trajectories that produce 'Stub' or 'Hallucinated' solutions that claim correctness without actual validation on the secret test set. Many models will claim 'The logic is now optimized' but fail to actually run the code against the maximum constraints to prove it. The selection process must verify that the *last* action in the trajectory was a successful execution on the most difficult data point. This protects against over-confident but broken algorithmic synthesis.
  - Reject submissions where the agent 'Guess-Patches' by adding random optimizations (like pragmas or unrolling) without addressing the fundamental complexity bottleneck. If the core problem is a wrong algorithm (e.g., BFS vs. Dijkstra), adding 'fast I/O' will not fix the TLE. The refined patch must show a meaningful change in the algorithmic logic or data structure to be representative of high-level problem solving.
