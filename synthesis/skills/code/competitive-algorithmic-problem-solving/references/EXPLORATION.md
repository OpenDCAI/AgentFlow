# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a Complexity-to-Limit Mapping by translating numerical constraints (e.g., N=10^18 or T=1s) into mandatory Big-O targets. The agent must first inspect the 'Constraints' section of the request and calculate whether the problem requires O(1), O(log N), or O(N log N) logic to prevent certain failure. For example, if N=10^5 and the time limit is 1s, the agent should rule out O(N^2) algorithms immediately before beginning implementation. An edge case is when multiple test cases (T) are provided, requiring the agent to total the complexity across all T instances to ensure the cumulative runtime fits the budget.
  - Conduct Small-Scale Brute Force Probing to detect hidden mathematical invariants or periodicities. The agent should write a minimal 'simulation script' to solve the problem for tiny inputs (e.g., N=1 to 10) and analyze the output sequences for patterns like cycles, greedy stability, or symmetry. A concrete step is printing the Sprague-Grundy values or the first few terms of a recurrence relation to see if they follow a recognizable sequence. This search for an 'aha' moment is essential for competitive problems where the scale exceeds the limits of standard simulations.
  - Execute a Language-Aware Performance Audit to decide between high-level expressive languages (Python) and low-level efficient languages (C++). The agent must check if the problem's time limit is unusually tight (e.g., < 0.5s) or if the algorithm requires intensive recursion depths or large arrays that might trigger Python's TLE or MLE. For instance, in NOI-level graph tasks, the agent should proactively choose C++ to utilize faster I/O and better memory control. An edge case is a problem with massive string manipulations where Python's built-in methods might actually outperform a naive C++ implementation.
  - Map the 'Failure Spectrum' of proposed algorithms using local adversarial cases. The agent should identify boundary segments such as empty lists, N=1, maximum integer values (2^63 - 1), and non-power-of-two sizes to establish where a candidate logic might fail. A concrete step involves the agent generating a 'Max-Scale Generator' script to test if the chosen data structure can physically fit in the allowed memory (e.g., 256MB). This prevents the agent from committing to a solution that passes sample cases but fails the exhaustive contest evaluation due to resource bottlenecks.
* **Target Trajectory Profile**:
  - The trajectory must exhibit a clear 'Failure-to-Success' progression driven by execution feedback from a judge or local test harness. A high-quality trace explicitly records the observation of specific error codes like TLE, WA, or MLE, followed by a logical pivot in the implementation strategy (e.g., 'Switching to a Segment Tree after TLE on naive range updates'). This proves the agent is capable of autonomous debugging and algorithmic refinement rather than just one-shot code generation. An agent that simply gets it right on the first try without demonstrating how it handled constraints is less useful for training robust reasoning.
  - A strong trace includes the documentation of 'Structural Insights' that collapse the problem's complexity. The agent should articulate the mathematical breakthrough—such as discovering a greedy invariant, a cyclic Grundy sequence, or a DP state reduction—in its reasoning before the corresponding code is written. For example, the agent should state: 'By changing the state from O(N^3) to O(N^2) using the symmetry of the grid, I can now meet the 2s time limit.' This ensures the trace captures the 'reasoning' behind the optimization.
  - The trajectory should preserve evidence of 'Language-Specific Optimization' for performance-critical sections. The trace is better when it shows the agent utilizing fast I/O functions (like `scanf/printf` or `sys.stdin.readline`), manual memory management, or specialized bit manipulation to squeeze performance out of a tight budget. A concrete sign of quality is the agent explicitly increasing the recursion limit or using a non-recursive approach to avoid RTE on deep tree structures. This mirrors the behavior of elite human contestants who adapt their code to the physical limits of the judge.
  - A high-quality exploration must demonstrate 'Scientific Skepticism' toward sample test cases. The agent should explicitly state that passing samples is insufficient and move to generating its own exhaustive verify cases or edge cases. For instance, after passing the provided 2 samples, the agent should say: 'Samples are small; I will now test with a maximum-sized input to ensure no TLE occurs.' This behavior prevents the 'Sample Overfitting' failure mode where an agent stops before reaching a robust solution.
