# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final completion utilizes the correct internal identifier as defined in the repository's source code files. The verification process must confirm that the function or class name used in the completion exists in at least one other file in the project. If the agent completes the line using a name that is neither a standard library call nor a project-defined entity, it is a grounding failure.
  - Accept only if the parameter assignments in the completion align with the data types and counts specified in the internal API's signature. The selection process must check the definition found during exploration and compare it to the usage in the synthesized code to ensure logical consistency. For example, if the internal function `process(data, mode)` is used, the completion must provide exactly two arguments corresponding to these semantics.
  - Accept only if the trajectory demonstrates a successful transition from an incorrect or ambiguous draft to a verified project-specific implementation. The evaluator should see a clear 'Evidence Acquisition' terminal turn where the agent retrieves the actual API definition before finalizing the code. A solution that 'guesses' the correct identifier perfectly on the first try without exploration is often indicative of contamination and should be scrutinized.
  - Accept only if the resulting code integrates seamlessly into the surrounding indentation and syntax hierarchy of the current file. The verification must confirm that the inserted code does not cause a syntax error and matches the local coding style (e.g., snake_case vs camelCase) used in the rest of the project. A patch that breaks the flow of the existing function or introduces illegal Python/Java constructs is an engineering failure.
* **Rejection Criteria**:
  - Reject trajectories that solve the task by defaulting to a generic `getattr` or `dummy` function when a specific internal API is clearly identifiable. If the repository contains a function `fetch_db_records` and the agent generates `getattr(self, 'fetch_records')` to avoid naming resolution, it has failed the core capability of understanding project-specific knowledge. Professional agents must commit to identified structural truths.
  - Reject traces characterized by sentence-level loops where the agent repeatedly generates the same line of code or a variation of it. This behavior often occurs when the model is unable to resolve a dependency and falls back on repetitive token prediction. Any trace that pings the same tool with the same query more than twice without progress should be rejected as an exploration loop.
  - Reject trajectories where the 'fix' involves the deletion of existing code or the masking of required parameters to make a completion 'pass'. stewardship requires adhering to the existing API contracts provided by the repository; an agent that omits a mandatory argument because it couldn't find a local variable to fill it is committing an implementation failure. The agent must either find the variable or report it as an underspecified requirement.
  - Reject any submission where the final answer is achieved by 'copy-pasting' if the task was specifically first-use completion where no similar snippet exists. The goal is to test the 'Inference' of internal APIs from functional descriptions and names; if an agent simply copies a 10-line block found in another file that is an identical match, it is missing the intended difficulty of the benchmark. This ensures the data rewards inferential reasoning over simple duplication.
