# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a Recursive Static API Inventory to extract all function signatures, class definitions, and file paths across the repository. The agent must traverse the directory structure using structural parsers to build a comprehensive map of all internal callable units. An edge case involves correctly identifying nested class methods or static class members to ensure the full-qualified names are stored for accurate cross-file referencing.
  - Generate Prototypical Usage Patterns for every internal API to simulate how they typically appear in developer code. The agent designs a set of imitation-based transformation rules that represent the API in module-qualified, instance-based, and direct-call formats. For example, a Python method defined in `utils.py` should be stored both as `utils.my_func()` and `my_func()` to ensure retrieval robustness against different import styles.
  - Profile Functional Semantic Intents by generating natural language docstrings for the implementation body of each internal function. The agent uses a summarization model to convert the technical implementation logic into a concise description of the function's purpose or data transformation. This allows the agent to find a function like `compute_score_weights` even if its name is obfuscated or if the agent only has a high-level goal like 'calculating importance values'.
  - Bootstrap with Code-Draft Query Generation by producing a preliminary completion to surface potential identifier fragments and data flows. The agent generates a 'noisy' initial completion and extracts any proposed function calls or variable names to serve as seeds for identifying the true internal target. A concrete example is taking a hallucinated name like `fetch_metadata` and using identifier similarity to locate the actual project function `get_meta_info`.
  - Conduct an In-File State and Type Audit to identify local variables and objects that can be used as arguments for discovered APIs. The agent scans the current context for variable declarations, parameter lists, and class attributes to determine what 'knowledge seeds' are available to satisfy internal API signatures. This prevents the agent from suggesting a completion that requires an object type not present in the current execution scope, ensuring implementation feasibility.
* **Target Trajectory Profile**:
  - The trajectory must exhibit a clear intent-to-logic traceability where the final code choice is explicitly justified by a found API definition. A high-quality trace shows thoughts like 'My draft used a nonexistent function X; based on the functional description, I found the real API Y in folder Z'. This confirms the agent is using evidence-based reasoning rather than simply extending text patterns.
  - A strong trace includes evidence of cross-file context recovery where the agent navigates away from the current cursor to find necessary implementation constants. The documentation should capture the agent identifying a missing constant in an API signature, searching for it in a separate `config` or `settings` file, and integrating it into the final completion. This highlights the repository-level understanding required for complex enterprise codebases.
  - The trajectory should preserve evidence of self-correction when initial identifier guesses are found to be invalid during retrieval. High-quality exploration captures the agent rejecting a tempting but incorrect identifier returned by a search because it lacks the required parameters or has a mismatched return type. For instance, the agent might identify `get_user` but reject it in favor of `get_user_profile` after realizing the latter returns the specific metadata needed for the current operation.
  - High-quality exploration must maintain a strict focus on project-specific logic while ignoring irrelevant standard library boilerplate. The agent should utilize tools to filter out public modules like `os` or `json` from its retrieval hits, focusing its context window primarily on custom code developed within the repository. A concrete sign of quality is the agent explicitly stating that it is prioritizing internal utilities discovered in the `src/` directory over generic online patterns.
