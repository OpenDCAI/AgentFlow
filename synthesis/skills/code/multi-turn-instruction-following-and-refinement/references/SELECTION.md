# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final code passes the test cases for both the CURRENT turn and ALL PREVIOUS turns in the conversation. The verification must use the cumulative test suite (T1, T2, ..., Tn) to confirm that no regressions were introduced. If a Turn 3 implementation makes the Turn 1 and Turn 2 tests fail, the trajectory is a failure. This is the primary indicator of instruction-following consistency.
  - Accept only if the implementation satisfies 'Non-Functional Constraints' like Annotation Coverage or Code Standards if they were part of the instruction chain. The selection check must verify if type hints, docstrings, or PEP-8 rules are preserved even when the primary task is a functional extension. For example, if Turn 4 required full docstrings, a Turn 5 functional update that omits them must be rejected. Expert refinement requires maintaining high-quality code standards throughout the lifecycle.
  - Accept only if the trajectory demonstrates 'Feedback Utilization Efficiency' by resolving the errors reported in the previous turn's logs within a single subsequent turn. If the user provided feedback that an 'Edge Case' failed, the next action in the trace must specifically target that case. Selection should favor agents that use the 'Error Message' as a precise guide for the fix rather than blindly rewriting the function. This ensures the data reflects the 'Dynamic Conversation' strengths of the agent.
  - Accept only if the agent correctly handled 'Context Usage Verification' by identifying and using the relevant repository context provided in the initial turn. If the project context included a specific class or helper, the agent's code must use those artifacts where appropriate instead of reinventing them. A trace that ignores the 'boltons' class structure to write a standalone Python script should be rejected for failing the repository-level alignment test. This confirms the agent's ability to operate at scale.
* **Rejection Criteria**:
  - Reject trajectories that exhibit 'Instruction Forgetting,' hallmarked by the removal of a previously successful feature to make room for a new one. This is common when an agent tries to keep the code 'simple' and deletes necessary validation or documentation logic. Any trace that regresses on a previously passed test case must be discarded immediately. This ensures the synthetic data maintains the 'Persistence' property of expert-level interaction.
  - Reject traces characterized by 'Superficial Compliance' where the agent acknowledges the feedback but doesn't actually change the code logic to fix the error. For example, the agent might say 'I have added the case-insensitivity' but the code still uses `s == dirty`. This 'Reasoning-Code Mismatch' indicates a failure of instruction grounding. Every logic update must be verifiable through the provided test suite.
  - Reject trajectories that 'Pollute the Context' by repeating the entire conversation history in every thought block or generating massive redundant comments. While context is important, excessive verbosity indicates a failure of information management. Selection should favor trajectories that are concise, target-focused, and only reference previous turns to justify specific logical decisions. This prevents the training of agents that become bogged down by long-context bloat.
  - Reject any submission where the agent 'Hardcodes' a solution to a specific test case rather than implementing a general rule. For instance, if the feedback says 'it fails for input 0', an agent that adds `if input == 0: return 0` instead of a general non-negative check is failing the engineering test. This 'test-driven-hacking' behavior produces low-quality data that does not generalize to real-world software maintenance.
