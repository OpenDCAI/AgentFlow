# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a 'Instructional Linearization' by mapping all instructions from the current and previous turns into a flat checklist of verifiable constraints. The agent should explicitly list every functional (e.g., input types, exception types) and non-functional (e.g., complexity limits, style rules) requirement encountered so far in its reasoning chain. For example, if the current turn asks for a performance fix, the agent must check if Turn 1 required specific error messages that must be preserved. This prevents 'context drift' where later instructions accidentally override earlier, still-valid ones.
  - Conduct a 'Historical Code Diff' to identify the specific lines of code that satisfied previous instructions before attempting any new changes. The agent must read its own previous responses and compare them to the current task to determine which code blocks are 'protected' by past requirements. If Turn 2 added a case-insensitivity check, the agent must mark those specific comparison lines as mandatory to retain. This ensures that the refinement process is additive rather than destructive, as seen in expert iterative development.
  - Audit the environment for 'Verifiable Feedback Seed' by identifying existing test cases or log-reporting utilities that could trigger for the previous turns' logic. The agent should scan for test files that already cover Turn 1 or Turn 2 and plan to run them together with the new turn's assertions. For instance, if Turn 1 implemented a specific API response format, the agent should find the test validating that format to ensure its new security patch doesn't break the response structure. This 'closed-loop' exploration uses executable evidence to anchor the multi-turn state.
  - Execute a 'Constraint-Conflict Analysis' to resolve potential contradictions between new feedback and old requirements. The agent must proactively identify if a new instruction (e.g., 'make the code more compact') might violate a previous instruction regarding 'Annotation Coverage' or 'Code Documentation'. A concrete step is for the agent to weigh the 'Functionality Extension' against the 'Code Standard' rules provided earlier. This prevents the agent from entering a loop of oscillating between two contradictory states over multiple turns.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate 'Instruction Accumulation Fidelity' where the agent explicitly references the historical instruction set in its CoT before generating code. A high-quality trace shows thoughts like: 'Turn 1 required X, Turn 2 requires Y; I will now combine them into Z.' This proves the agent is maintaining a persistent session state rather than treating each prompt as an isolated one-shot task. The absence of this 'memory check' often leads to regression errors in complex multi-file scenarios.
  - A strong trace includes an 'Incremental Validation Step' where the agent performs a mental or executable check of the previous turn's success criteria after implementing the current turn's request. The agent should verify that its new 'Exception Handling' logic didn't delete the 'Edge Case' logic from two turns ago. For example, the trace should record: 'The new validation logic is added; I will now double-check that the empty-string handling from Turn 1 is still present.' This cross-checking behavior defines the 'robustness' of the multi-turn capability.
  - The trajectory should exhibit 'Contextual Stewardship' by adapting the solution to use repository-specific patterns discovered in previous turns. The agent should reuse helper functions or constants it identified or created in Turn 1 while solving the task in Turn 3. This is signaled by thoughts like: 'I will use the `_check_valid_size` helper I implemented earlier to satisfy this new bound check.' This prevents 'fragmented logic' where an agent implements the same rule in multiple ways because it forgot its own previous implementation.
  - High-quality exploration must maintain a 'Zero-Forgetting Ledger' by explicitly noting which previous instructions are still being followed in the current turn. The agent should use comments or internal reasoning to map code lines to specific turns (e.g., '# Satisfies Turn 2: Case insensitivity'). This documentation ensures the synthesized data is useful for training models to solve the 'Instruction Forgetting' problem. An edge case is handled when the agent identifies that a previous instruction is no longer applicable due to a fundamental architectural shift and justifies its removal.
