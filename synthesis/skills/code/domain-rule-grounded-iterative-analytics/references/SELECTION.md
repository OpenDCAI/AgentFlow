# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the agent's trajectory contains an explicit successful retrieval and interpretation of the domain manual or SOP documentation. The selection must verify that the agent's code uses variables, constants, or formulas that were uniquely defined in the unstructured files. If the agent solves a 'fraud' task using a generic threshold (e.g., 0.5) instead of the specific threshold mentioned in the manual, the result is considered a grounding failure. This ensures the data captured reflects the 'hybrid reasoning' required by the benchmark.
  - Accept only if the final analytical code achieves functional parity with the industry-specific standards provided and executes successfully on the provided dataset. The verification must confirm that the agent used efficient data manipulation patterns (e.g., vectorized operations) and correctly handled the final structural transformations. If the code produces the right number but uses an extremely slow 'row-by-row' iteration pattern for 100k+ rows, it should be flagged as low-quality. Expert data agents should always favor performant, scalable analysis logic.
  - Accept only if the agent follows 'format-guidance' constraints regarding rounding, delimiters, unit systems, and output structures. The selection process must verify if the agent correctly rounded to the specified decimal places or provided a unified measurement system as requested in the prompt. This mimics real-world analytics where result reporting is as critical as the calculation itself. For instance, a trace that provides '42.12/kg' when the spec asks for absolute standardized units (e.g., 'lbs') should be rejected for failure to follow reporting instructions.
  - Accept only if the trajectory demonstrates 'Iterative Validation' by checking intermediate outputs or sample rows during the analysis. The agent should show itself printing the head of a filtered dataframe or validating a join to ensure that its logic (informed by the manual) worked as expected. This 'closed-loop' behavior is essential for catching planning errors before they aggregate into the final answer. An agent that runs one giant script and produces a number without any verification steps is considered too brittle.
* **Rejection Criteria**:
  - Reject trajectories that demonstrate 'One-Shot Code Hallucination' where the agent writes a massive block of code before reading the context documents or SOPs. This behavior suggests the agent is guessing the data structure or the business rules rather than grounding them in the environment. Such data points are not useful for training multi-step reasoning. Any agent that 'jumps the gun' and provides a final answer without visible manual-lookup steps must be excluded.
  - Reject traces where the agent relies on 'Semantic Hallucinations'—using a code formula that sounds plausible but is contradicted by the provided manual. Financial, regulatory, and domain-specific rules are often arbitrary or idiosyncratic to a specific business. If the manual states that 'fee = volume * 0.05' and the agent uses '0.03' because that is a more common market rate, the trace has failed the fidelity check. This prevents the synthesis of data that rewards general knowledge over evidence-based reasoning.
  - Reject any trajectory where the agent 'shortcuts' the multi-step requirement by hardcoding values found in a previous exploratory step or truncating the required regulatory transformations. The goal is to capture the *entire* analytical pipeline from unstructured source text to final structured result. If the agent finds a conversion factor and just applies it statically to a single manual sample, the pedagogical value is lost. The final code must cleanly process the whole target dataset using the rules.
  - Reject submissions that fail the 'Zero-Shot Generalization' test by hardcoding logic that only works for the specific merchant, medical center, or time-range referenced in the prompt. The data engineering generated during the trajectory should be logically sound and parameter-aware, applicable to the whole dataset. This prevents the training of agents that construct brittle 'hacks' instead of resilient, abstract data interpretation logic.
