# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the trajectory includes genuinely visual evidence that is necessary for solving the problem. That evidence can be an image in the issue, a visual snapshot failure, or a rendered-output comparator, but it must contribute information not recoverable from plain text alone. If the image is ornamental, reject the trace for this capability.
  - Accept only if the suspected edit site is explicitly linked to the visual pipeline. The trace should identify the renderer, component, tokenizer, style map, or layout code that generates the faulty output, not just a nearby file with related names. This requirement prevents accidental inclusion of ordinary bug-fix traces mislabeled as multimodal.
  - Accept only if validation includes a front-end relevant signal. Suitable signals include snapshot diffs, browser-rendered checks, DOM-plus-style assertions, or issue-provided reproduction pages. If the trajectory ends with only unrelated unit tests or build success, it is not sufficient for this capability.
  - Accept only if the final patch preserves neighboring visual behavior. The trace should mention at least one sibling component, adjacent token class, or nearby rendering case that must remain unchanged. This matters because front-end fixes often break closely related styles if edited too broadly.
* **Rejection Criteria**:
  - Reject trajectories where the image or screenshot is incidental and the bug is fully recoverable from text. A visual benchmark item should force the agent to use multimodal evidence, not merely tolerate its presence. Otherwise the data will overstate multimodal difficulty.
  - Reject traces that confuse visual observation with backend state. If the path never inspects or reasons about rendering logic, token classes, layout constraints, or UI-specific tests, it is probably not a true visual front-end issue. This applies even when the repository itself is a front-end project.
  - Reject trajectories that rely on global style overrides as a first resort. Global theme edits can make snapshots pass while obscuring the actual semantic cause, such as wrong element classification or incorrect renderer branching. Such traces are poor-quality synthesis seeds because they reward brittle fixes.
  - Reject traces that cannot distinguish between expected and actual rendered outputs. When the issue only states 'looks wrong' and the trajectory never sharpens that into missing text, wrong placement, clipping, or style mismatch, the problem remains under-specified. Advancing such a trace would produce noisy or ambiguous synthetic questions.
