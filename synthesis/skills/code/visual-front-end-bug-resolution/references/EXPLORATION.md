# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Begin by identifying which part of the problem statement is visually essential and which part is only textual scaffolding. The agent should note whether the decisive evidence is a screenshot, a diagram, a rendered DOM state, a style mismatch, or a visual regression artifact. If the issue could be solved without understanding the image, it probably belongs to a different capability and should be filtered out.
  - Map each visual symptom to the rendering stack that could plausibly generate it. That means tracing from the user-visible artifact back through components, templates, tokenizers, style maps, layout logic, or drawing routines until candidate code regions emerge. A useful edge case is when the same symptom could come from either CSS or semantic token classes; the trajectory should preserve both until one is ruled out.
  - Use available reproduction assets as first-class evidence rather than as decoration. Open issue-linked images, reproduction snippets, storybook examples, or snapshot tests to determine exactly what the expected versus actual rendering difference is. If no explicit visual comparator exists, the agent should infer the minimum rendered invariant from adjacent examples before moving to patching.
  - Collect both structural and visual confirmations. Structural confirmation comes from code paths, props, classes, or drawing branches; visual confirmation comes from snapshots, screenshots, or renderer outputs. A high-quality trace keeps these aligned so the final patch is not merely cosmetically plausible but causally tied to the observed visual defect.
* **Target Trajectory Profile**:
  - A strong trajectory should preserve one explicit chain from visual symptom to render path. The agent should be able to say which image region or rendered property is wrong, which component or rule produces it, and how the code change will alter that visual output. This keeps the task grounded in front-end causality rather than generic JavaScript repair.
  - A good trace should distinguish between content absence and style misclassification. Missing labels, hidden nodes, clipped elements, wrong placement, and wrong colors may all appear as 'visual bugs' but imply different root causes. The trajectory is higher quality when it states exactly which subtype is being tested, because selection and synthesis depend on that distinction.
  - The trajectory should include a render-aware validation plan. That plan might use snapshot tests, screenshot diffs, DOM assertions tied to classes, or reproduction snippets executed in the project harness. An edge case is when only DOM text changes are asserted; if the bug is about spatial placement or color, DOM-only validation is not sufficient.
  - The trajectory should remain narrow enough that the final patch is plausibly local. Visual issues often tempt broad style-sheet edits or global theme changes, but a benchmark-quality trace should identify the minimal renderer, parser, or component region responsible. Otherwise the synthesized task becomes too diffuse and underdetermined.
