# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the agent successfully detected an underspecified instruction and retrieved at least one piece of 'Decisive Information' not found in the initial prompt. The information must be materially required for the fix, such as a specific variable value, a desired API signature, or an error log. If the agent asks 'How are you?', it does not count as a clarification. For example, the agent must elicit that the 'missing properties' refers to '@property' decorators to pass the selection filter.
  - Accept only if the agent's question to the user describes a 'Specific Localized Conflict' discovered during repository exploration. The question should not be 'The issue is vague; help me,' but rather 'I see the logic in handler.py handles strings; should I also add support for bytes as per your report?' This shows that the agent combined the user's input with the repository's reality. A trace that asks for files easily found via `grep` should be penalized for poor interaction efficiency.
  - Accept only if the final patch resolves the issue and satisfies the 'Hidden Requirements' provided by the user during the interaction. The verification must confirm that the implementation aligns with the specific details elicited in the dialogue. If the user said 'use an AST visitor for safety' and the agent used 'eval()', the trajectory must be rejected for misalignment. This ensures the data rewards the 'alignment' aspect of the interactive capability.
  - Accept only if the trajectory demonstrates 'Reasoning-Action Consistency' where the agent's initial thoughts identify the ambiguity that is later asked about. The evaluator checks that the agent didn't just 'luck into' an interaction but deliberately planned it based on identified gaps. For instance, the thoughts should state: 'There are two possible ways to handle this; I must clarify with the user.' This prevents the selection of lucky or random interaction patterns.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Blind Execution' where the agent implements a solution to a vague prompt without asking any questions. In an underspecified setting, guessing the solution often leads to hallucinations or incorrect patches even if they pass some tests. If the instruction was clearly missing the 'where' or 'how', any trace that doesn't interact should be flagged as high-risk. This encourages the training of 'honest' agents that admit when they don't know something.
  - Reject traces that demonstrate 'Interaction Looping' where the agent asks for the same information multiple times despite receiving it. This indicates a failure of long-horizon context management or a failure to integrate user feedback into the state. Any agent that pings the user with 'Could you tell me the file?' after the user already said 'misc.py' represents a catastrophic failure of the interactive capability. Professional engineers do not ignore user inputs.
  - Reject any trajectory that solves the task by 'Assistance Sabotage'—where the agent asks for the entire solution or the exact patch from the user. The goal is to ask for 'specifications' and 'context', not for the 'answer'. An agent that says 'Can you provide the final code for this fix?' is not performing software engineering and must be discarded. This ensures the synthetic data maintains the persona of a skilled developer.
  - Reject submissions where the agent's questions are 'Implementation-Heavy' and exceed the likely knowledge of the user. For example, asking 'What should the value of the internal __private_accumulator be at cycle 3?' is usually too specific for a bug reporter. The agent should ask about behavior, requirements, and observed symptoms. This protects against the synthesis of unrealistic interaction patterns that would frustrate a real-world user.
