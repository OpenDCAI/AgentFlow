# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform an 'Instructional Scent Audit' by comparing the user's prompt against a standard 'Well-Specified Template' (containing error logs, file paths, and versioning). If the incoming request lacks at least two of these anchors, the agent must flag the task as 'Underspecification-High' before executing any terminal commands. For example, a request like 'fix the login' without a traceback should trigger an immediate search for the login controller to see if the ambiguity can be resolved internally or requires a question.
  - Conduct a 'Navigational vs. Informational' gap analysis by attempting a 1-minute repository search for the terms mentioned in the prompt. If the agent can find the file but cannot deduce the 'expected behavior' from the code itself, it marks the gap as 'Informational'. Conversely, if the agent knows what to do (e.g., 'fix a typo') but cannot find the file in a massive project, it marks the gap as 'Navigational'. An edge case is finding multiple files with similar names, which requires asking for the specific module to avoid editing the wrong component.
  - Implement an 'Exploration-First Query' protocol where you search the codebase until you reach a 'Binary Decision Point' that cannot be solved by reading. The agent should find the relevant code and identify exactly two or three possible ways to fix it, then ask the user to choose the desired path. For instance, if a method is missing an argument, the agent should ask: 'Should this argument have a default value of None or should it raise an error if missing?' This ensures the question is actionable and technical rather than a vague 'what do I do?'.
  - Identify 'Implicit Dependency Traps' where a vague request might affect multiple modules with different configurations. If the user asks for a 'UI change', the agent should check if the project has multiple themes or localizations and ask which ones are affected. A professional trajectory documents this search in the thoughts, stating: 'I found three different CSS files for the login; I must ask the user which specific screen displays the bug.'
* **Target Trajectory Profile**:
  - The trajectory must demonstrate a 'Detection Turn' where the agent explicitly pauses in its reasoning to identify missing information. A high-quality trace shows thoughts like 'The prompt mentions a crash but no traceback; I will look for logs, and if not found, I will ask the user for the error message.' This proves the agent is acting as a proactive steward rather than a passive code-generator. An edge case is when the agent finds the info in a hidden 'hints' file and documents that interaction was no longer necessary.
  - Maintain a 'Question-to-Action' mapping where the user's answer directly leads to the next tool-use step. A successful trace shows the agent receiving an answer (e.g., 'The error happens in view.py line 40') and immediately navigating to that specific location. This prevents 'interaction waste' where an agent asks a question but then continues to wander aimlessly through the repository. For example, the agent should say 'Based on the user's feedback about Python 3.10, I am checking the typing module imports.'
  - Preserve 'User-Centric Burden Management' by consolidating several small questions into a single, comprehensive inquiry turn. A professional trajectory demonstrates an agent performing several minutes of code research and then asking one post with three bulleted questions rather than pinging the user three times. This reflects the design of interactive agents that respect user time while gathering critical specifications. An edge case is asking a follow-up question only when an unexpected error appears during the implementation phase.
  - Demonstrate 'Semantic Integration' by explicitly commenting on how the user's feedback changed the planned implementation. The reasoning should state: 'Initially I thought this was a logic error, but the user's log shows it is an environment mismatch; I will now update the requirements.txt instead of the source code.' This proves the agent is not just 'hearing' the information but 'leveraging' it for higher resolve rates. A strong trace uses the user's exact terminology in the final commit message or patch comments.
