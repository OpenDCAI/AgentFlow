# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final state of the database reflects 100% adherence to schema constraints and referential integrity rules. The verification process must confirm that all primary keys are unique and all foreign key references point to existing valid IDs in parent tables. If the agent adds a character row with an ActorID that doesn't exist in the Actor table, the trajectory is a failure. This ensures the data captured represents high-fidelity integration engineering.
  - Accept only if the extracted and integrated values match the semantics and granularity of the existing database content. The selection check must verify that newly added data (e.g., a 'Birthplace') follows the same detail level (e.g., 'City, Country') as the pre-existing rows discovered during exploration. A trace that adds 'USA' when the database consistently uses 'City, State, USA' represents a failure of professional database alignment. This protects the quality of the synthesized analytics-ready data.
  - Accept only if the trajectory demonstrates the use of specialized IE tools (NER, RE, AE, Classifier) orchestrated in a logical sequence derived from the schema. A successful trace shows the agent identifying the entity first (NER), then its attributes (AE), then its relations (RE), mimicking professional information extraction pipelines. If the agent attempts to extract a relation before it has anchored the head entity, it is a logic failure. This verifies the agent's ability to plan complex extraction workflows.
  - Accept only if all numerical and date-based values are correctly normalized according to the database's explicit format requirements. The evaluator should check that strings like '170 million' were converted to '170000000' if the column type is Integer, and that dates were converted to the standard 'YYYY-MM-DD' format if required. A trace that leaves raw text formats in an integer column is an engineering failure. This ensures the synthetic data supports training for 'data engineering' precision.
* **Rejection Criteria**:
  - Reject trajectories that achieve integration by 'Hallucinating' missing data not present in the provided documents. If an agent adds a 'Birthplace' for an actor because the schema requires it, but the text never mentions the birthplace, the implementation is unfaithful to the source material. Professional stewardship requires inserting NULL or a default value for missing text evidence rather than inventing facts. This prevents the training of deceitful data agents.
  - Reject traces characterized by 'Single-Table Blindness' when the task clearly involves inter-table dependencies. If the agent is asked to 'add a movie' and only updates the Movie table while ignoring the required linking to the Actor and Character tables described in the prompt, it has failed the orchestration requirement. This is especially important for complex schemas where data is distributed across multiple linked entities. Any trace that leaves foreign key columns as NULL when the text provided the linkable data must be discarded.
  - Reject any submission where the agent 'Guess-Links' entities without performing a database lookup or primary key verification. Elite database population requires grounding every update in the current state of the store. An agent that 'assumes' an ActorID is 100 without searching for the name in the Actor table first represents a high-risk engineering pattern. This ensures the resulting data rewards systematic retrieval and grounding.
  - Reject trajectories that solve integration challenges by 'Modifying the Schema' to fit the extraction results. If an agent changes a column from 'Integer' to 'Text' because it couldn't figure out how to parse a price string, it is a catastrophic failure of engineering stewardship. The agent must align the data to the software environment, not the inverse. This filter eliminates 'lazy' agent behavior that bypasses technical difficulty by breaking the repo's structure.
