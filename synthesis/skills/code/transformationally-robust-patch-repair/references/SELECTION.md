# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the task instance contains a semantics-preserving code transformation that materially changes superficial cues. Identifier renaming alone can count when it disrupts obvious memorization anchors, but stronger traces also include structural changes such as helper extraction or control-flow rewriting. If the transformed instance is still trivially recoverable from a memorized diff, it is too weak.
  - Accept only if the trajectory demonstrates semantic localization under transformation. The agent should recover the true patch site by reproducing failure and reasoning over behavior, not by matching raw text to a known historical patch. This condition is what makes the trace genuinely decontaminated.
  - Accept only if the transformed environment retains executable validation. The same repository, after transformation, must still provide failing-before and passing-after evidence for the target behavior. Without this, the resulting example tests decontamination only in appearance, not in software-execution reality.
  - Accept only if the final patch is robust to the transformed presentation and does not simply undo the transformation. The objective is to repair behavior in the transformed codebase, not to revert it back toward a memorized original form. Trajectories that reconstruct old names or old structure as the main move should be rejected.
* **Rejection Criteria**:
  - Reject trajectories where the transformation is cosmetic but irrelevant. If renaming or reformatting does not actually interfere with lexical retrieval or patch memorization, the instance does not meaningfully test transformation robustness. Such tasks collapse back into ordinary repair.
  - Reject traces that succeed by finding or importing the original patch context. Any reliance on historical diffs, exact prior filenames, or contamination shortcuts defeats the intended capability. The trajectory must stand on current transformed repository evidence alone.
  - Reject trajectories that fix the transformed code by undoing the transformation wholesale. Restoring old helper names, flattening extracted functions, or reverting control flow without clear behavioral need is not the target skill. It measures reconstruction of original appearance, not semantic debugging.
  - Reject traces that cannot articulate the invariant preserved across transformations. If the agent cannot explain what behavior stayed the same while syntax changed, it likely has not truly solved the semantic generalization problem. Those traces are too brittle for high-quality synthesis.
