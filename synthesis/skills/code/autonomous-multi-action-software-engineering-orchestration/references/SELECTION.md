# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final artifact reaches a 'Verified Success' state in the native execution environment or simulator. Code must compile without hardware timing violations, physics models must converge, and simulators must achieve 100% trajectory transition accuracy.
  - Accept only if generated code uses the correct hierarchical block structures strictly compliant with the target framework’s esoteric dialect (avoiding hallucinated block or class names).
  - Accept only if the trajectory demonstrates 'Execute-Analyze-Correct' capability, utilizing a domain-specific error log to locate a functional flaw and applying a deliberate correction.
  - Require strict structural dependency linkage. If data must pass across sub-modules or MultiApps, ensure variable names uniformly map between consumer and setter components.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Hallucinated Tool Usage' where the agent invokes generalized pseudo-code approaches when a stringent framework or theorem solver was heavily enforced.
  - Reject 'Infinite Error Looping' traces where an agent attempts to fix the same syntax warning iteratively via brute-force code thrashing, reflecting systemic failure of reasoning reflection.
  - Reject trajectories guilty of 'Contextual Sabotage'-for instance, altering testing benchmarks, relaxing physics tolerance thresholds significantly, or returning placeholder values to bypass complex evaluation failures.
  - Reject output generating mere non-executable 'proposal texts' over concrete artifacts. A fully implemented, compliant, and compiled script structure must comprise the final answer.
