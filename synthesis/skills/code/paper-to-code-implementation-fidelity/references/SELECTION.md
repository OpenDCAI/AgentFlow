# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the implemented code achieves 100% adherence to the research formulas and instructions provided in the paper. The verification process must confirm that all technical terms (e.g., 'Label Smoothing', 'Entropy Bonus') are correctly reflected in the implemented code logic and that no 'placeholder' or 'identity' functions were used to bypass mathematical complexity. Any implementation that returns a constant or a naive approximation instead of the full solver is considered a failure.
  - Accept only if the final execution artifacts (e.g., result JSONs or terminal logs) produce numerical outcomes within the established 'Gold Range' of the benchmark. The selection check must parse the metrics from the agent's run to confirm they are statistically significant and aligned with the reported research baseline. An implementation that finishes without errors but produces random or zero-valued metrics indicates a fundamental logical gap and must be discarded.
  - Accept only if the trajectory demonstrates 'Feedback Utilization Efficiency' by resolving identified errors within 1-2 turns of receiving specific guidance (Level 2 or 3 feedback). The refined state must move from an 'Incorrect' or 'Misaligned' state to a 'Success' state by incorporating the expert's diagnostic signals. This is the primary indicator of the agent's ability to act as a collaborative research developer rather than a static code generator.
  - Accept only if the agent correctly handled 'Repository Level Alignment' by utilizing pre-defined repository modules and following established coding styles. The selection process ensures that the agent used the existing `config` objects, imported internal base-classes, and avoided reimplementing functions available in the `/utils` directory. This verifies that the implementation is 'ready-for-review' and maintains the structural integrity of the parent research repository.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Logical Stubbing' or 'Shortcut Implementation' where the agent bypasses complex math with standard library defaults that don't match the research specs. If the paper specifies a custom 'Fisher-matrix' regularizer and the agent uses a generic 'Weight Decay', it has failed the fidelity test. Expert research implementation requires committing to the technical density of the publication artifacts regardless of the coding difficulty.
  - Reject trace submissions where the agent 'Guess-Patches' repetitive errors without citing specific paper formulas or logs. If an agent tries multiple tensor reshapes without confirming the actual mathematical dimensions in the LaTeX description, it indicates a failure of evidence-based reasoning. We discard any trajectory where the agent's 'Revision' turns are not preceded by a 'Reflection' turn that explicitly identifies the root cause of the previous failure.
  - Reject any submission where the success is achieved by 'Tampering with the Evaluation Harness'. Following the Historical Error Log, any agent action that modifies unit test assertions, relaxes numerical tolerances in `eval.py`, or hard-codes the expected test result into the source file is a catastrophic integrity breach. The agent must align the code to the science, not the judge to the code. This includes bypassing accuracy checks by returning pre-computed baseline values.
  - Reject trajectories characterized by 'Scientific Impatience' where the agent prematurely terminates a research run or skips a required implementation turn because the log 'seemed slow'. Research code implementation often requires long-horizon execution (e.g., training a small model for 1 epoch); an agent that kills a process without a documented 'failed hypothesis' observation is considered unreliable for professional reproduction workflows.
