# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a Symbol-to-Code Traceability Mapping before drafting implementation logic. The agent must extract every mathematical symbol from the LaTeX formulations (e.g., $\alpha$ for learning rate, $\tau$ for temperature) and explicitly link them to implementation variables in the code skeleton or configuration files. This prevents literal implementation errors where symbols represent internal layer dimensions in paper diagrams but specific hyper-parameters in the code. A concrete action involves checking if the paper uses 1-based indexing for iterations which requires a -1 offset in Python loops.
  - Conduct an Implicit Knowledge and Domain Context Probe to identify 'hidden' requirements not explicitly described in the paper. The agent should search the environment for standard domain libraries (e.g., `transformers`, `gudhi`, `scipy`) or project-level READMEs that specify the default activation functions, initialization schemes, or stability epsilons. This addresses 'missing knowledge' failures where implementations fail due to oversights in domain conventions. For instance, discovering that 'normalization' in a specific repo refers to layer-norm rather than batch-norm is critical for implementation fidelity.
  - Execute a Repository-Wide Signature and Utility Audit to avoid re-implementing existing features. The agent should use `BROWSE` and `SEARCH` tools to look for core utility functions like `pooling_op`, `get_optimizer_params`, or `weighted_sum` that are already defined in other modules. This ensures the new implementation integrates seamlessly with the codebase rather than creating redundant logic blocks. An edge case appears when a user asks to implement a specific loss, but a 'base_loss' class already exists that must be inherited to ensure correct gradient accumulation.
  - Implement a Differential State Audit between technical narratives and provided test harnesses. The agent should compare the high-level descriptions in the paper with the 'After-patch' unit tests to identify requirements that are implicit in the narrative but hard-coded in the evaluation (e.g., specific tensor shapes or precision types like `bfloat16`). This helps the agent prioritize scientific alignment over simple functional success. For example, a paper might describe a 'probability pool', while the test suite expects a 'log-probability' input, necessitating a log-transformation during implementation.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate an 'Explicit Evidence-to-Action' chain where every major code edit cites a specific equation, section, or instruction from the paper. A high-quality trace captures the agent noting: 'Paper Section 3.2 defines the threshold as scaled max-probability; I will now implement the scaled_min_p logic.' This documentation proves the agent is grounding its engineering decisions in the scientific intent rather than performing generic code-pattern completion. This eliminates random guessing based on variable name similarity.
  - A strong trace includes evidence of 'Multi-turn Iterative Refinement' where the implementation converges toward success based on hierarchical feedback signals. The agent should show itself implementing a draft, observing a specific failure (e.g., a 'T2' alignment error or a 'T4' integration error), and applying a surgical fix that directly addresses the diagnostic insight. For instance, the agent might initially use a standard mean-pool but, after receiving feedback about a 'weighted-pooling' requirement in Equation 6, correctly switches to a `scatter_add` implementation.
  - The trajectory should preserve evidence of 'Context Window Stewardship' by selectively reading only the relevant implementation files and paper sections. High-quality exploration avoids dumping massive research repos into the context and instead uses targeted calls like `RETRIEVE` to find the exact functional boundary of the target algorithm. A professional sign of quality is the agent explicitly dismissing irrelevant 'sample' or 'legacy' files that share names with production components but reside in disconnected research subdirectories.
  - Trajectories must exhibit 'State-Persistence and Re-entry' logic when handling long-running research tasks. The agent should demonstrate it knows how to track its progress across multiple interaction turns, noting which parts of a complex methodological pipeline are complete and which are pending (e.g., 'Dataset loading is verified; now implementing the GRPO advantage calculation'). This prevents circular reasoning and ensures that later turns do not introduce regressions into previously verified modules, particularly in 10+ turn interactive sessions.
