# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Decompose the mathematical operator into a hardware-aware execution plan by analyzing input/output shapes and identifying parallelizable dimensions. The agent should determine if the task is better suited for a tiled approach (shared memory) or a streaming approach based on the data reuse profile. For example, a matrix transpose requires careful tiling to ensure coalesced writes, whereas element-wise addition can be streamed with simple vectorized pointers.
  - Implement an iterative scaling loop involving both sequential reflection and parallel sampling to debug complex kernel errors. The agent should run initial attempts to capture logs, then use those logs to refine the kernel logic in a sequential 'Reflexion' cycle to fix syntax or index errors. In parallel, it should generate diverse kernel variants with different block sizes to discover configurations that might yield higher performance on specific hardware like the MI300X.
  - Perform a Register Pressure and Memory Bandwidth Audit to identify the specific hardware bottlenecks of the operator. The agent must calculate the bytes-to-flops ratio and determine if the kernel is bound by compute (ALU) or memory (DRAM) availability. A concrete step involves inspecting whether the kernel holds too many large tiles in registers concurrently; if so, the agent must plan to reduce block sizes or use more efficient pointer arithmetic to prevent local memory spilling.
  - Utilize code-similarity retrieval instead of natural language search to find relevant 'knowledge seeds' for the kernel design. The agent should search existing repositories for Triton or CUDA code that handles similar memory access patterns (e.g., searching for 'block pointer' patterns for a GEMM task) rather than just looking for name-based matches. This grounded retrieval provides the agent with validated hardware-specific idioms that can be adapted to the new task.
* **Target Trajectory Profile**:
  - The exploration must preserve a clear progression from functional correctness to empirical performance optimization through the use of a feedback loop. A high-quality trace shows the agent first implementing a kernel that passes unit tests with a 1e-5 tolerance, then specifically analyzing the execution latency to justify subsequent edits. For instance, the agent should document that 'the initial kernel is 10% slower than the baseline, so I will now implement memory coalescing to saturate bandwidth.'
  - Trajectories should exhibit 'Contextual Hardware Tuning' by adapting parameters to the specific GPU architecture detected in the environment. The agent must demonstrate an understanding of different cache sizes or SIMD widths when setting block sizes (`tl.constexpr` in Triton) for MI300 vs MI250 hardware. This is evidenced by steps where the agent queries the device properties before finalizing the grid launch parameters to ensure optimal occupancy and throughput.
  - The trace must maintain a 'Deductive Optimization Ledger' that explains exactly which code change led to a measured performance gain or loss. Every optimization attempt should be preceded by a hypothesis—such as 'unrolling this loop will reduce branch overhead'—and followed by an observation of the actual impact on latency. This scientific approach distinguishes expert kernel development from trial-and-error code generation that lacks architectural reasoning.
  - High-quality exploration must explicitly handle 'Debugging Traps' where the agent identifies and escapes unproductive reflection loops. If the same error trace persists across multiple sequential iterations, the agent should proactively discard the current approach and explore an alternative kernel strategy (e.g., switching from a 2D tile to a 1D vector). This behavior ensures the agent remains stable during long-horizon optimization tasks without getting stuck in repetitive failures.
