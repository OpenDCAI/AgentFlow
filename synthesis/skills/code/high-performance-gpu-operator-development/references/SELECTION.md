# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the operator successfully compiles and produces numerical results that match the reference baseline within a strict scientific tolerance (e.g., 1e-5). Functional correctness is the baseline for kernel engineering, and any implementation that fails on randomized input seeds must be rejected immediately. For example, a sum-reduction kernel must produce the same total as the CPU reference across all batch sizes tested.
  - Accept only if the final operator demonstrates a measurable speedup (>= 1.0x) compared to a standard expert-written reference or a high-quality eager-mode implementation. This skill targets high-performance operators, so a kernel that is functionally correct but significantly slower without a physical justification (like excessive precision) is a failure. The trace must include a log showing the median latency comparison between the generated and reference kernels.
  - Accept only if the final code follows hardware-specific best practices, such as proper memory coalescing, vectorization, and masking for out-of-bounds access. The selection process must verify that the kernel handles arbitrary input shapes that do not perfectly fit the declared block size using dynamic masks or grid-stride loops. A kernel that crashes or produces garbage data when the input dimension is a prime number is not industrial-grade and should be rejected.
  - Accept only if the trajectory demonstrates the use of a cashed evaluation logic where functionality is verified before more expensive performance profiling. This ensures computational efficiency in the development loop, mimicking how real engineers focus on correctness before fine-tuning. The trace should show a 'Passed Functionality' signal followed by a 'Latency Comparison' signal.
* **Rejection Criteria**:
  - Reject trajectories that exhibit a 'Debugging Trap' where the agent repeats the same failing code edits or misinterprets the error trace for more than three consecutive iterations. This indicates a failure of the reflection module and results in low-quality data that does not teach effective problem-solving. A professional agent must recognize when a path is a dead end and pivot to a fresh strategy.
  - Reject any submission where the agent modifies the test harness, modifies reference seeds, or ignores numerical errors to force a passing state. Hardware verification requires strict fidelity to the mathematical definition, and any attempt to loosen tolerances to hide instability is a critical alignment failure. For example, removing a check for 'NaN' values in the final output to make a divergent kernel look successful.
  - Reject trajectories that rely on 'Memory Bandwidth Waste' such as reading the same tile multiple times from global memory when it could have been cached in registers or shared memory. In low-level kernel coding, efficiency is part of correctness. If the agent's code uses 50% more memory transactions than a simple optimized reference, it has failed the core capability of 'high-performance' development.
  - Reject traces where the kernel assumes fixed input sizes or hardcoded thread configurations that prevent the operator from scaling with the grid. Professional kernels must use runtime parameters and program IDs to calculate indices dynamically. This prevents the synthesis of brittle, single-use kernels that fail when integrated into larger neural network graphs or production pipelines.
