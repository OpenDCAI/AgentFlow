# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the trajectory identifies a stable, reproducible method for data retrieval (e.g., specific CSS selectors or API endpoints). Selection must verify that the agent didn't just guess the URL structure but actually inspected the source or logs to confirm the path. If an agent's reasoning says 'I will try div.title' and the log doesn't show that tag exists, the trace is rejected. This ensures the synthetic data is high-fidelity and physically grounded.
  - Accept only if the final implementation squad produces an executable script that successfully retrieves at least one sample row from the target source. The verification must confirm from the execution logs that the script ran, parsed the data, and produced a non-empty output matching the expected schema. A script that is syntactically correct but returns zero records from a live site represents an engineering failure. This protects against 'dry-run' hallucinations.
  - Accept only if the trajectory addresses data integrity through explicit cleaning or normalization steps. The selection check should confirm that the agent handled common web issues like extra whitespace, HTML entities (e.g., '&amp;'), or inconsistent date formats. A trace that adds raw HTML tags into a CSV field is considered low-quality and should be excluded. Elite data agents should always favor ready-to-use, sanitized datasets.
  - Accept only if the agent utilized appropriate libraries (e.g., BeautifulSoup, Playwright, Requests) matching the technical complexity of the website. The selection process should check if the agent correctly identified the need for a headless browser when dynamic JS rendering was observed. A trace that attempts to use simple HTTP requests on a SPA (Single Page Application) and fails should be rejected. This ensures the data captures real-world technical decision stability.
  - Accept only if the final state shows adherence to provided 'Format Guardrails' such as CSV delimiters or JSON structure. The selection must verify that if the user asked for a 'JSON with title and date', the final output isn't a flat text file. This mimics professional data engineering where the interface contract is as important as the data content.
* **Rejection Criteria**:
  - Reject trajectories that achieve 'Success' by hallucinating data or using pre-trained knowledge to fill a dataset. If the agent provides a list of papers for a 2024 conference that it could not have accessed through the browser (e.g., because it didn't find the URL), the result is fraudulent. Professional stewardship requires extracting facts from the environment, not from memory. Any trace that 'invents' records to pass a count check must be discarded.
  - Reject traces characterized by 'Scraping Sabotage' where the agent ignores paywalls or login walls by faking results. If a site requires a subscription and the agent provides 'sample' data found in an old cache while claiming it was live, it is a fidelity failure. The agent must document the obstruction and either solve it (if possible) or report the limitation. This prevents the training of deceitful data harvesters.
  - Reject trajectories that demonstrate 'Redundant Information Flooding' where the agent scrapes the entire webpage including navigation menus and footers. A high-quality data agent must perform surgical extraction of the target entities. Any trace where the final data samples contain more than 20% 'noise' or irrelevant metadata should be rejected as a failure of precision. This ensures the resulting synthetic data is clean and professional.
  - Reject any submission where the agent 'Guess-Links' related data without verifying foreign key or ID consistency across pages. For example, linking a 'Paper' to an 'Author' by assuming the name matches exactly without checking the unique author ID portal. Elite database population requires grounding relationships in explicit identifiers found in the repo or on the web. This prevents orphaned or misaligned records in the final dataset.
  - Reject traces where the 'fix' for an extraction error involves hardcoding values for a specific record observed during debugging. Data engineering must be programmatic and generalizable; a scraper that works by adding an 'if title == X: return true' branch is non-pedagogical. The logic must be driven by generalizable selection rules.
