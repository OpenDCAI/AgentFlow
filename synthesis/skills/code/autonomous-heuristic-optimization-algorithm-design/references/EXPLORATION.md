# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Map the numerical score trajectory by establishing a 10-step 'Score Ascent' diagnostic script. The agent must wrap the current solution in a loop that executes it across diverse input seeds and records the resulting scores to identify if the current logic has hit a hard performance plateau. For example, if adding complexity to an SA neighbor search yields zero score improvement over 50 iterations, the agent should mark the current move set as 'saturated'. An edge case occurs when scores are highly variable, requiring the agent to use statistical means rather than point values to judge improvement.
  - Perform an 'Algorithmic Leverage Census' to identify which component—State Representation, Neighborhood Moves, or Evaluation Function—is the primary bottleneck. The agent should temporarily modify one of these areas into a more powerful (but perhaps slower) version to see if it significantly increases the potential score. If changing the evaluation metric to include a distance-lookahead increases the score by 20%, the agent should plan to implement an efficient version of that logic. A concrete failure is spending an hour optimizing C++ code execution speed when the underlying algorithm is an O(N^3) approach that a simpler O(N^2) would easily beat.
  - Conduct a 'Physical Constraint Audit' to determine the exact boundary of the Time Limit Exceeded (TLE) risk for high-iteration strategies. The agent should run a stress test with a 'no-op' version of its loop to see how many iterations are physically possible within the environment (e.g., 2 million moves per second in C++ vs 50,000 in Python). This allows the agent to decide whether to prioritize complex math within fewer steps or simple path-finding across millions of steps. An edge case is an environment with shared CPU resources which might fluctuate, requiring the agent to implement a safety buffer of 10% in its time-budget calculations.
  - Execute a 'Neighborhood Diversity Sweep' by implementing and testing multiple distinct move operators simultaneously. The agent should define standard moves like 'swap', 'insert', and 'reverse', but also search for domain-specific moves like 'block-migration' or 'node-ejection'. It must then measure the success rate of each move type (how often it is accepted in an SA cycle) to discard ineffective operators. For instance, in a routing task, if '2-opt' moves are accepted 5% of the time while '3-opt' moves are only accepted 0.01% of the time, the agent should prune the 3-opt logic to save execution time.
* **Target Trajectory Profile**:
  - The trajectory must exhibit 'Feedback-Led Code Growth' where the size and complexity of the script increase in direct response to score findings. A high-quality trace shows the agent starting with a 20-line greedy script, then adding a 100-line SA framework, and finally implementing a 50-line hyperparameter tuner based on observed TLE errors. Each code block must be preceded by a thought process that cites a preceding execution result as the motivation for the expansion. An edge case involves the agent realizing a complex approach is slower and intentionally reverting to a more efficient, smaller implementation.
  - A strong trace includes evidence of 'Incremental Heuristic Tuning' where the cooling schedule or beam width is refined across at least three distinct turns. The agent should document the observation of a 'premature convergence' (where scores stop improving too quickly) and respond by lowering the SA cooling rate or increasing the Beam Search width. This demonstrates the agent's ability to manage performance at the hyperparameter level, which is a key part of algorithm engineering. For example, the agent might state: 'The score plateaued at 500ms; I will slow the cooling from 0.99 to 0.999 to more broadly explore the search space.'
  - The trajectory should preserve a 'Counter-Intuitive Discovery' turn where the agent corrects a strategy that was logically sound but empirically weak. The trace is better when it shows the agent testing a standard 'textbook' move, seeing it perform poorly due to specific problem geometry, and then implementing an 'ad-hoc' trick that works better. This proves the agent is acting on empirical evidence rather than just reciting coding rules. An example is the agent choosing a random-walk over a greedy search because the latter gets stuck in massive local optima in a specific test case.
  - High-quality exploration must document the 'Language Pivot Decision' if switching from an expressive but slow language to an efficient one. The agent should justify the move from Python to C++ or Rust by citing a TLE result on a large instance where the algorithmic logic is already sound. This behavior separates elite problem-solvers from those who try to optimize inefficient codebases. A concrete sign of quality is the agent providing a 'translation ledger' where it maps its previous Python logic to the new C++ syntax to ensure functional parity.
