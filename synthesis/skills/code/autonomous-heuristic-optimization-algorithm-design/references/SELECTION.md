# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final performance metric (e.g., AtCoder Performance or similar relative score) is within 20% of the provided expert human baseline for the problem. This ensures that the synthesized code represents a 'competitive' solution rather than a naive one. The evaluator must check that the agent attained a high enough score to solve difficult instances, not just sample ones. If the expert score is 100,000 and the agent produces 5,000, the implementation is insufficient regardless of its complexity.
  - Accept only if the trajectory demonstrates a 'Score Progression Verification' where at least two improved versions of the code were executed and scored. The final version must be numerically superior to the initial version in the logs. This confirms the agent followed the iterative refinement loop essential for this capability. A trace that correctly gets a high score on the very first try is considered 'lucky' or 'contaminated' and is lower value than one showing a documented climb from 1000 to 2000 points.
  - Accept only if the generated code adheres to all hard constraints—such as CPU time limits and memory caps—across the entire evaluation suite. The selection process must parse the terminal logs to confirm that zero TLE or MLE errors occurred in the final 'Submission' phase. A solution that is optimal but requires 10 seconds for a 2-second problem is an engineering failure. This verifies the agent's ability to optimize the 'implementation throughput' as well as the algorithmic score.
  - Accept only if the agent's reasoning explicitly links a specific 'Neighborhood Move' or 'Objective Function' edit to a measured delta in the score. The evaluator should see messages like 'Adding the distance-penalty corrected the overlapping route issue and increased the score by 1500 points.' This ensures the causality of the refinement is transparent. This prevents the selection of agents that add 'random' code that doesn't actually contribute to the optimization objective.
* **Rejection Criteria**:
  - Reject trajectories that achieve high scores through 'Hacking the Verifier' or modifying the evaluation scripts to ignore errors. If the agent changes a 'check_feasibility.py' file to always return True, it is a catastrophic alignment failure. Professional engineering requires solving the problem within the provided rules. Any trace showing modification of the scoring harness itself must be permanently excluded.
  - Reject traces characterized by 'Blind Iteration' where the agent runs the same code multiple times with tiny, meaningless changes while the score remains unchanged. This indicates a failure of the 'Reflexion' or 'Ideation' modules and results in uninformative data. A high-quality trace must show a steady improvement hypothesis before each major run. If the agent makes 10 runs with the same result, it indicates it is stuck in a reasoning loop.
  - Reject trajectories where the finally submitted code is a 'Stub' or 'Naive Baseline' that passes but ignores the score-based optimization requirement. In score-based contests, 'working' is the floor, not the ceiling. Any implementation that doesn't show evidence of meta-heuristics (like SA, Hill Climbing, or Beam Search) for a recognized hard optimization task should be discarded. This ensures the synthetic data maintains the 'expert engineer' persona.
  - Reject submissions where the agent 'guesses' input shapes or data types instead of using the provided generation tools or README docs. IoT and Algorithm contests often have very specific input blocks; an agent that treats them as generic lists will fail on boundary cases. The selection check must confirm the agent performed a 'Read-Before-Code' on the input generation logic. Traces that produce 'KeyError' or 'IndexError' halfway through the final evaluation are engineering failures.
