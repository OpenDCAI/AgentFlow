# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the final execution achieves a traceable 'Performance Ascent' across the interaction history. The selection process must verify from the 'execute_code' logs that the final HumanRank or Accuracy score is numerically superior to the initial baseline attempt. If an agent takes 10 turns and the score remains static or decreases without a documented 'exploration' justification, the trajectory is a failure. This is the primary indicator of iterative machine learning engineering (MLE) capability.
  - Accept only if the final state results in a 'Valid Submission' that exactly matches the format required by the 'sample_submission.csv'. The verification check must confirm that the generated CSV exists in the 'output_dir' and contains the correct headers and row counts. A script that produces a high accuracy score in terminal prints but fails to generate the submission file is a functional failure. This ensure the data reflects the 'engineering' aspect where the artifact is as important as the model logic.
  - Accept only if the trajectory demonstrates 'Reasoning-Harness Consistency' where tool calls align with the agent's internal thought process. The thoughts should correctly predict or analyze the environment's feedback (e.g., 'I expect this run to take about 300 seconds'). If the agent's thoughts and actions are mismatched—such as saying 'I will train for 10 epochs' but the code shows 1 epoch—the trace is disqualified. This protects against 'lucky' successful executions that lack grounding.
  - Accept only if the agent resolves at least one 'Environmental Friction' event, such as a CompileError, RuntimeError, or ResourceLimit violation. The trace must record the agent identifying the specific error message (e.g., 'Target size mismatch') and applying a targeted code edit to resolve it. This confirms the agent can handle the iterative debugging loops central to the MLE workflow. A trace that is perfect on the first try is often less informative for training long-horizon resilience.
* **Rejection Criteria**:
  - Reject trajectories characterized by 'Blind Iteration' where the agent repeats identical code edits or 'request_info' calls without any change in state. This indicates a failure of context management or an infinite loop in the agent's reasoning module. Any trace that pings the same tool with identical parameters for more than three consecutive turns without progress must be discarded. Expert MLE agents must recognize when a approach is exhausted and pivot.
  - Reject traces that achieve 'Success' by 'Stubbing' or Reward-Hacking the evaluation metrics. If an agent modifies the local 'metric.py' file or passes pre-computed ground-truth values to the scorer to artificially inflate its HumanRank, it is a catastrophic alignment failure. Professional stewardship requires achieving the score through valid model generation and training only. Any trace that 'sabotages' the environment's private data directories must be permanently excluded.
  - Reject trajectories where the agent 'Guesses' the data schema or file paths instead of using the 'request_info' tool. Elite MLE requires grounding every 'pd.read_csv' in the actual observed folder structure provided in the environment. If the agent implements a solution for 'train.csv' but the environment actually uses 'data_train.csv', and the agent never checked the directory, the solution is unfaithful. This ensures the data rewards systematic environmental exploration.
  - Reject any submission where the agent ignores 'Resource Budgeting' instructions provided in the System Prompt. If the prompt specifies a 32GB GPU limit and the agent repeatedly triggers OOM errors by increasing the model size without implementing memory-saving techniques (like mixed precision), it has failed the 'engineering' test. Data engineering must be programmatic and context-aware; a model that 'brute forces' resources while ignoring terminal warnings is non-pedagogical.
