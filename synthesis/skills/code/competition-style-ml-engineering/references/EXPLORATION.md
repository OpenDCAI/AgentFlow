# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Perform a 'Constraint-to-Resource' Audit by querying the environment's hardware specs and software limitations before drafting any ML code. The agent must call 'request_info' to specifically identify the available GPU memory (e.g., 32GB), CPU core count, and the maximum runtime (e.g., 12 hours) to inform its choice of model complexity. For example, if the environment lacks a GPU, the agent should immediately plan for gradient-boosted trees instead of deep transformers to avoid 'DeviceNotFound' errors. An edge case involves finding that the 'data_dir' is read-only, which necessitates planning a separate 'output_dir' for all artifacts.
  - Execute an 'Incremental Baseline Verification' using a lightweight validation action before attempting a full execution run. The agent should draft a minimal pipeline that loads 1% of the data and produces a dummy submission to verify that the environment's code interpreter can successfully import libraries like 'XGBoost' or 'PyTorch'. During this turn, the agent uses 'validate_code' solely to catch syntax errors or missing dependencies, ensuring the 'execute_code' call—which typically consumes more time and resources—is only triggered for high-confidence candidates. An edge case appears when a model works locally but fails in the sandbox due to path name mismatches (e.g., /data vs ./data).
  - Synthesize a 'Relative Performance Map' by comparing the task's human leaderboard distributions to the agent's initial benchmark results. The agent should use the feedback from its first successful execution to determine the 'Efficiency Gap'—the distance between its current rank and the top-tier percentiles. For instance, if the HumanRank score is 20%, the agent should plan a major architectural shift (e.g., from linear models to neural networks) rather than minor hyperparameter tweaks. A concrete failure is spending limited turns on 'grid search' when the baseline model is fundamentally unsuited for the data modality.
  - Implement a 'Feature-Dependency Traversal' by auditing the data folder structure and schema metadata stored in 'data_structure.txt'. The agent must identify which columns are categorical, numerical, or target labels and map them to appropriate preprocessing encoders (e.g., LabelEncoder for targets, OneHot for features). A specific action involves checking for temporal columns in 'Time Series' tasks which require windowing or lagging logic rather than random shuffling. An edge case is identifying 'leaky' features—like IDs that correlate perfectly with the target—and proactively excluding them to ensure valid generalization.
* **Target Trajectory Profile**:
  - The trajectory must demonstrate 'Turn-based Strategic Evolution' where each action is justified by the cumulative interaction history. A high-quality trace shows thoughts like 'My last execution achieved 60% accuracy; I will now add dropout layers to reduce the observed overfitting documented in Step 4.' This proves the agent is maintaining a persistent mental model of the experiment's trajectory rather than treating each step as a disconnected code completion. A failure to reference previous failures (e.g., repeating a failing import) indicates a low-quality reasoning process.
  - A strong trace includes an 'Exploration-Validation-Execution' sequence that minimizes resource waste. The agent should demonstrate a systematic flow: first requesting info to map the environment, then using validation to check intermediate tensor shapes or EDA results, and only then using the full execution call for leaderboard scoring. For example, the agent should state: 'I have verified my data loader works with validate_code; I am now ready to train the full model for 5 epochs via execute_code.' This mirrors the professional workflow of an efficient ML engineer working under a restricted time budget.
  - The trace should preserve evidence of 'Error-Driven Self-Correction' specifically targeting submission-format discrepancies. High-quality data captures the agent receiving a 'Submission Invalid' error (e.g., 'Id column missing'), reading the 'sample_submission.csv' again, and surgically editing the CSV generation block. A concrete sign of quality is the agent catching a 'Submission Not Created' error and identifying that the script crashed due to an OOM before the save operation could occur. This highlights the agent's ability to handle the 'hidden' engineering friction of competition interfaces.
  - Trajectories should exhibit 'Dynamic Domain Adaptation' by utilizing different strategies for different ML task types (CV, NLP, Tabular). The agent should show itself choosing CNNs for images and Tree ensembles for tabular data, with the reasoning explicitly citing the 'info_type: overview' feedback as the reason for the choice. For instance, in a 'ciphertext' challenge, the agent should explain why token-level embeddings are inappropriate and pivot to character-level models. This ensures the synthetic data captures the 'expert versatility' required by generalist MLE agents.
