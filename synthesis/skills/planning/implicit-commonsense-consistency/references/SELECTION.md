# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept a trajectory only if it contains verifiable evidence that the capability is doing real work. First, check that the key decision points are causally linked to the environment state, retrieved evidence, or unstated hazard constraints. For example, if the same final answer would still be valid after deleting the supposedly critical step, the trajectory should fail selection.
  - Accept only seeds where the planner's intermediate record can be audited. Every major action should be explainable by an immediately preceding observation, symbolic state update, or implicit constraint check, and the trajectory should not jump from problem statement straight to final answer. For example, a good seed shows the search result that motivated the next booking or the environmental realization that the stove was left 'ON'.
  - Verification of Dual-Constraint Logic: Accept a trajectory only if it demonstrates adherence to BOTH Process Safety (how the task is done) and Termination Safety (how the room is left). You must audit the final state of the environment to ensure no appliances are on, no doors are left open, and no items are placed on heat sources. If a plan is locally safe but leaves a hazard in the terminal state, it fails the implicit commonsense selection metric.
  - Accept only trajectories that contain at least one non-trivial failure boundary. You should be able to articulate what would go wrong if a step were skipped, reordered, or replaced by a tempting shortcut. For example, reusing an uncleaned container, scheduling local activities after departure, or pouring toxic substances without a restorative step provides the needed boundary.
  - Accept only if the trajectory supports robust question writing. There must be enough information density to phrase a question that targets a realistic plan that is not only constraint-matching but also globally sensible under unstated commonsense expectations, and the resulting answer must be tightly bounded. For example, if many equally valid answers remain because the environment does not constrain the outcome enough, the seed should be rejected or further refined.
* **Rejection Criteria**:
  - Reject any seed that is hard only because the wording is confusing. If the difficulty disappears once names are normalized or the prose is cleaned up, then the capability is not being tested at the planning level. For example, a task with odd object labels but no real dependency chain is not acceptable.
  - Shortcut-Induced Hazard Blindness: Reject any trajectory that achieves the goal successfully (Task Success = True) but violates a safety or logical constraint. The agent must not be rewarded for efficiency if it creates a Fire, Slip hazard, or a teleporation error. A concrete failure is an agent that 'cleans the room' by throwing everything into a pile near a heat source, violating spatial safety rules.
  - Reject any trajectory that hides crucial information outside the recorded exploration. The approved seed must not depend on unstated assumptions, private knowledge, or unavailable tool outputs that never appeared in the trace. For example, if a plan silently assumes a flight exists or an appliance possesses an auto-shutoff feature without showing that evidence, it must be discarded.
  - Reject trajectories with redundant or decorative steps. If a middle action can be removed without changing feasibility, constraint satisfaction, or the reasoning burden, then the trace is not sharp enough for synthesis. For example, random extra searches, needless moves, rhetorical safety language without action, or filler text should be stripped before acceptance.
  - Reject any seed whose answer cannot be scored cleanly. The final plan or answer must be checkable against explicit state transitions, retrieved facts, or physical environment states, not merely judged by tone or stylistic plausibility. For example, 'nice itinerary' or 'careful plan' without auditable timeline and safety criteria is insufficient for this capability.
