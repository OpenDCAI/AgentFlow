# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept a trajectory only if the dependency graph shows a parallelism ratio greater than 1, proving multiple tasks are indeed executed concurrently. This is verified by comparing timestamps to confirm the start time of Action 2 is definitively earlier than the resolution end time of Action 1. A purely sequential plan applied to an inherently independent pair of sub-tasks must be flatly rejected indicating optimization failure.
  - Accept only if all dependent variables in the DAG are strictly traceable back to a successfully executed upstream task ID output block. Every instance of a token like '$n' must possess a corresponding task '$n' that verifiably produces an output usable for that specific argument restriction type. If a task actively references a non-existent ID or attempts to feed a string payload into a numerical math constraint field, the entire seed is discarded.
  - Accept only if the dynamic refinement phase seamlessly diagnoses a subtask failure and structurally patches the working graph to reach success. You must computationally verify that the decision to update the node routing is completely grounded in the literal content of the prior execution logs generating a block. For example, replacing a 'Generate Image API' node with a 'Search Existing Web Image' node because the server returned a 'Rate Limited' error.
  - Accept only if the complex planning overhead is observationally offset by the execution speedup or the enhanced robustness of the completed graph. The trajectory must quantitatively highlight that the time saved via parallel execution is definitively larger than the latency the core LLM spent generating the DAG schema. An edge case where 10 microscopic parallel operations take 0.1s each but the planner expended 20s to compile the text represents an inefficient architecture and is rejected.
* **Rejection Criteria**:
  - Reject any trajectory containing circular processing dependencies or syntactically invalid graph relationships directly halting execution. The selection validation pipeline must audit the dependency arrays to ensure the graph rigidly adheres to acyclic topological sorting rules. An objective example is a plan that gets permanently frozen because Task 1 is waiting on Task 2, while Task 2 recursively waits on Task 1's output buffer.
  - Reject seeds where the agent acts out repetitive blind tool looping without fundamentally structurally altering the internal DAG in response to explicit feedback. This directly indicates the core planner failed to realize its preliminary mapping was logically flawed and degenerated to blind, sequential task retrying. For example, firing the exact same failing parallel web parameter search three consecutive times without branching the request is an immediate flag for rejection.
  - Reject trajectories that intentionally early-stop or actively hallucinate missing branch data by ignoring unprocessed dependencies enclosed within the DAG. If the agent proposes a macro plan possessing four parallel search tasks but summarizes its concluding answer prematurely after only two fetch completions, the analytical engine has broken down. A concrete operational instance involves contrasting four digital products but only waiting to collect two database records before hallucinating the remaining metrics.
  - Reject any constructed graph layout introducing severe dependency concentration bottlenecks where non-causal nodes wait completely unnecessarily. This categorically prevents the training synthesis of linear plans where highly parallelizable auxiliary components universally wait sequentially on an irrelevant central gateway task. A realistic failure is a development plan where 10 independent website graphic rendering functions indiscriminately wait upon a single background database scripting task.
