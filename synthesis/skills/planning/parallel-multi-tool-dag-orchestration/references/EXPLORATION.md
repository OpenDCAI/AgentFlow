# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Search for task environments where the terminal goal requires multiple distinct data points that can be fetched from non-overlapping sources. Analyze the tools to see if the output of Tool A is strictly required for the input of Tool B, or if they are independent knowledge seeds that can be fetched asynchronously. For example, when comparing two cities, probing the population of City A has zero dependency on the weather of City B, making them parallelizable seeds.
  - Identify bottleneck operations that act as synchronization points where parallel branches must eventually merge to form a composite result. Record the data flow by explicitly tracking how variables are passed from concurrent tool responses into the aggregated arguments of a subsequent joining tool. A concrete example is a travel plan where 'Hotel availability' and 'Flight price' are explored in parallel but must both be present before a 'Total Cost Calculation' tool is called.
  - Probe for dynamic replanning scenarios where the path of the execution graph must change based on a tool's observation or failure. If a parallel branch yields corrupted logs or an error, intentionally halt the raw execution and structurally alter the DAG by inserting specific bridging subtasks or fallback nodes. For instance, if searching for a company returns 'Acquired by X', the agent must halt the planned parallel probes for the original company and rebuild a new DAG for the parent entity.
  - Map out the temporal sensitivity of different tools by logging their average response times to identify which longest-running tasks should be dispatched first. If Task A (Deep Web Search) takes 5 seconds and Task B (Math) takes 0.1 seconds, the planner should orchestrate the DAG so Task A starts immediately before lighter operations. An edge case involves moving a complex, high-latency download earlier in the DAG so it can run silently in the background while the LLM computes simpler text-based tasks.
* **Target Trajectory Profile**:
  - The target trajectory must clearly separate the structural planning phase (DAG creation) from the parallel execution phase (Concurrent Dispatch). Look for trajectories that output a structured list of tasks with incremental IDs (e.g., $1, $2, $3) where the later tasks rely on earlier variables. A good profile explicitly shows at least two concurrent tool calls that do not share a causal link firing simultaneously.
  - Each step in the trajectory must use explicit placeholder variables to represent future data dependencies in a machine-readable format. Instead of outputting prose like 'use the result from the search', the trajectory must use specific parameter syntax like '$1' or '$id' to enforce graph edges. A failure case would be a trajectory where the agent idles waiting for 'Observation 1' before proposing 'Task 2', even though Task 2 requires no prior inputs.
  - The trajectory should exhibit a clear transition from an 'Initial Plan' through a 'Check & Refine' result to an 'Updated Plan' if a runtime node fails. The trace must record the agent evaluating output data and intentionally adding or removing nodes to bypass an issue rather than just repeating a broken step over and over. An example of this is replacing a failing 'Web Scrape' parallel task with a split 'Manual Data Entry' and 'API Search' combination branch after an initial system timeout.
  - The log must demonstrate 'Join Integrity' where the agent successfully aggregates information from multiple completed parallel branches to produce the final calculation or decision. This is highly visible when placeholder tokens are dynamically replaced with actual environment values during the final join state. If the trajectory shows an execution attempt with un-substituted variables or an entirely skipped parallel branch, it fails the graph profile metric.
