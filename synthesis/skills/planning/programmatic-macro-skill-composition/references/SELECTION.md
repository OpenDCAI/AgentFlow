# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept a trajectory only if the programmatic macro-skill survives an 'Execution-Based Verification' where the agent successfully solves a new task variation using the skill. You must verify that when the rewritten trajectory prefix is executed, the environment state reaches the intended sub-goal without manual intervention. For instance, if the agent calls `sort_listings('Price')`, the accessibility tree must show that the price-ordered list appeared.
  - Accept only if the 'Skill-Validity Ratio' is positive, meaning that every action wrapped inside the macro-skill resulted in a demonstrable change to the world state. If a macro contains 'Click' actions that do not change the URL, open a menu, or update a form, the skill is bloated and must be discarded. A valid seed must have zero 'noop' actions or redundant clicks hidden inside its code structure.
  - Accept only if the 'Parameter Handoff' is grounded in the instruction, verifying that the strings or IDs passed to the macro match the user's specific entities. You must trace the variable flow to ensure the 'laptop' in the question is the same variable passed to the `search_product(query)` function. If the function hard-codes a value that wasn't in the prompt, it represents a failure of the composability logic.
  - Accept only if the induced skill demonstrates 'Granularity Consistency,' meaning it contains at least 2 and no more than 10 actions to remain task-oriented. Extremely long programs become hard to debug and verify, while single-action programs offer no efficiency gain. A concrete indicator of a good skill is an 'Order Refund' macro that combines selecting an order, choosing a reason, and clicking submit.
  - Accept only seeds where the final plan achieves 'Step Efficiency Improvement' of at least 15% across several multi-part tasks. The selection unit must verify that the agent's total action count is lower across a test suite when the new skill library is active. This ensures the capability is solving the 'scaling-up' bottleneck rather than just adding complexity to the library.
* **Rejection Criteria**:
  - Reject any trajectory where the programmatic skill depends on 'Private State Assumptions' not visible in the accessibility tree or the history. If a macro assumes a button 'id=123' exists without first navigating to the page where that button appears, the logic is brittle and will fail. This prevents the synthesis of 'magical' plans that only work because of unstated environment assumptions.
  - Reject seeds with 'Procedural Fuzziness,' where the boundaries between distinct sub-tasks are blurred in a single macro. For example, a skill that both 'Searches for a product' and 'Updates the user profile' is logically incohesive and should be rejected in favor of two separate modular skills. This ensures the action space remains clear, composable, and versatile per the ASI framework.
  - Reject any trajectory where the agent 'hallucinates' the success of a macro without receiving the proper observation. If the agent calls `process_order()` and then immediately sends the 'Done' message without waiting for the page to load or the confirmation to appear, the trace is a failure. This ensures the data requires strict evidence-based state tracking during the execution phase.
  - Reject trajectories that achieve goals through 'Trivial Primitives' when a higher-level macro already exists in the library for that specific task. If the agent chooses to click 5 times instead of using a `login()` skill it already knows, it indicates a failure to maintain a persistent and scalable planning artifact. Repeatedly building the same logic from scratch is a rejection-worthy planning anti-pattern.
