# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Error Correction Rate (ECR) Verification: Accept a trajectory only if the agent successfully resolves a non-trivial execution error (e.g., a 400 Bad Request or a Compilation Error) within its multi-turn interaction. You must verify that the final state of the environment reflects 'Success' and that the sequence leading to it was logically motivated by the prior failure feedback. If the agent repeats the exact same error twice in a row, the seed must be rejected.
  - Error Recognition Rate (ERR) Validation: Accept only if the agent's internal monologue explicitly acknowledges and identifies the nature of the technical failure observed in the logs. The selection unit must check if the agent specifically mentioned 'invalid date format' or 'missing user_id' before attempting the fix. If the agent proceeds to the correct answer without acknowledging why the first attempt failed, it indicates a failure of the reflection capability.
  - Feedback-to-Action Monotonicity: Accept a trajectory only if each iteration shows a measurable improvement in the environment score or a step closer to syntactic compliance. In optimization tasks, the sequence of scores (e.g., 1.2M, 1.3M, 1.45M) must confirm that the heuristic refinements are converging toward the goal. For boolean tasks, the number of reported errors in the log must decrease as the agent refines the script.
  - Zero-Shot Generalization Proof: Accept only if the refined strategy solves the task even when the initial environment state contained 'outdated' or 'fuzzy' instructions that were corrected via feedback. The agent must show it can ignore a wrong 'suggested param' in the documentation if the real-time execution proves it is incorrect. This ensures the capability is grounded in empirical reality rather than unverified prompt assumptions.
* **Rejection Criteria**:
  - Stuck-Looping Development Cycles: Reject any seed where the agent submits identical or fundamentally uncorrected logic to the environment across two or more consecutive turns. This 'Feedback Blindness' indicates a failure in System 2 reasoning where the agent ignores the log feedback. A concrete failure is an agent that continues to use the wrong API name despite the server returning 'API_NOT_FOUND' repeatedly.
  - Teleportation of Refined Knowledge: Discard any trajectory where the agent 'guesses' the perfect parameter configuration on its very first step when the environment description was intentionally incomplete or incorrect. This suggests data leakage or a failure in the 'Trial-and-Error' modeling. The capability requires a visible 'discrepancy' that forces a reflection event to be scorable.
  - Feedback-Contradictory Reasoning: Reject any trajectory where the agent's 'Thought' block correctly identifies the error (e.g., 'I need an integer') but its 'Execute' block repeats the mistake (e.g., sending a string). This 'Execution Inertia' proves the agent is merely summarizing text without controlling its action program. A valid seed must show perfect alignment between the reflection strategy and the corrective action.
  - Unverified Success Hallucination: Reject any trajectory where the agent claims the task is complete (Final Answer) despite the preceding observation log showing an unresolved execution error. This includes scenarios where the agent parrots its own input as a 'success' while the tool output says 'Forbidden'. Any mismatch between the 'Observation' and the 'Final Answer's' claim of success results in an immediate rejection.
