# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Execute Single-Observation Reachability Scans by analyzing the initial environment state to identify all interactive elements available without requiring a state transition. You must systematically inventory all buttons, menus, and fields that can be reached in the CURRENT view, such as icons in a toolbar or items in an already-open sidebar. For example, if both the 'Font Size' and 'Font Color' dropdowns are visible, mark them as a priority pair for grouped-action exploration.
  - Identify Atomic GUI Action Chains that consistently appear as a unified task segment for a human user. Trace the interaction history for 'Focus -> Input -> Submit' or 'Open Menu -> Select Item -> Confirm' sequences that often clutter an agent's trace with redundant reflection. A concrete step involves forcing the explorer to plan these as a single 'Macro-Action' when the environmental response (like a pop-up) is 100% predictable based on local software rules.
  - Map Latency-Intensive Reasoning Hubs by identifying parts of the trajectory where the agent typically spends 3x more time in reflection than in action. You must target operations where the visual confirmation is trivial (like a text box filling up) and replace them with 'Fast-Prowl' execution sequences that allow the agent to move to the next logical step immediately. For instance, after typing an SSH username, the agent should immediately move to the password field if it is currently visible in the UI tree.
  - Verify Control Marker Stability by checking if the Resource IDs and coordinates of future batch steps remain constant across the initial transition. The agent must verify that performing Action A (e.g., clicking a 'Settings' tab) results in a deterministic appearance of Action B's target (e.g., a 'Security' link) in a known location. A practical case is confirming that a right-click menu always renders at the cursor offset, allowing the selection action to be batched with the click.
* **Target Trajectory Profile**:
  - The trajectory must exhibit an Action-to-Reflection ratio significantly higher than 1:1, specifically showing multiple GUI operations grouped under a single planning block. Concretely, the trace should show the agent performing the entire 'Add User' workflow (typing name, typing password, clicking OK) in one go rather than stopping to reflect after every keypress. This approximates the 'WES+' efficiency metric where agents take fewer than 2.7x steps than humans.
  - Include Inter-Action Validation Checkpoints where a local executor (OS-level check) verifies if the next target in the batch exists before firing. The logs must show that the system actively checked for the 'Save' button's ID between typing the filename and clicking save, without returning control to the central LLM planner. This ensures that the batching is 'speculative' yet safe, allowing for an early-exit if an unexpected dialog box (like 'Overwrite File?') appears.
  - Demonstrate Path-Efficiency Optimizations where the agent chooses the 'Shortest Human-Like Path' over the generic 'Model-Discovered Path.' The trajectory should explicitly avoid trial-and-error by using keyboard shortcuts (e.g., 'Ctrl+S' instead of 'File -> Save') or context-menus discovered in the initial scan. For example, using the 'Paragraph' shortcut icon on a toolbar to change line spacing instead of navigating three levels of nested menus.
  - Preserve Grounded Speculation by linking every future action in a batch to a coordinate or semantic anchor found in the VERY FIRST observation. The trajectory must document that the agent 'knows' where the second button will be because it saw it in the sidebar or predicted its location based on a standard software layout. A failure case to avoid is one where the agent clicks a coordinate that was never present in the initial accessibility tree.
