# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the 'Step Efficiency Ratio' (texp/tactual) shows that the agent used no more than 1.5x the steps of a documented human expert for the same GUI task. You must compare the agent's total step count against the OSWorld-Human gold baseline to ensure the batching logic resulted in real temporal savings. If an agent takes 50 steps for a 5-step human task, the batching logic failed selection regardless of task success.
  - Accept only if the 'Grouped-Action Consistency' check confirms that all targets in a multi-action phase were available for interaction without a significant environment reload. The selection unit must verify that no 'State-Interrupt' (like a new URL load or a screen wipe) occurred between the actions in the batch. For instance, 'Clicking Search' then 'Typing' is only acceptable as a batch if the search bar is a static element that doesn't refresh the page on focus.
  - Accept a trajectory only if the 'Cumulative Latency' of the batched sequence is at least 40% lower than the equivalent sequential execution recorded in failure logs. You must verify that the reduction in LLM 'Prefill' and 'Reflection' calls resulted in a faster end-to-end task completion. A concrete marker is a task finishing in under 5 minutes that previously took 15 minutes due to per-step planning.
  - Accept only if every action in the batch is preceded by a documented 'Pre-condition Verification' marker in the execution log. The agent must show that it didn't blindly fire actions; it performed a lightweight check (e.g., 'Target [ID:202] is Enabled') right before the click. If the trace shows a click on an invisible or disabled element during a batch, it represents a breakdown in safety logic.
* **Rejection Criteria**:
  - Reject any trajectory that exhibits 'Inertial Navigation,' where the agent continues a batch of clicks even when an error or unexpected popup has appeared. If the executor sees a 'Password Incorrect' warning but continues to try and 'Click Logout' from its pre-planned batch, the speculative logic is fundamentally broken. This ensures agents remain responsive to 'reactive' environment changes while attempting efficiency.
  - Discard seeds featuring 'Coordinate Guessing' where the agent plans to click a GUI element that was never revealed in the current or previous accessibility trees. This prevents the training of agents that rely on 'Rote GUI Memorization' (assuming 'File' is always at [0,0]) rather than real-time grounding. Every coordinate must be justified by an OS-level Resource ID or a pixel-detection bounding box.
  - Reject any batch that includes 'Stochastic Dependencies,' where Step 2 requires reading and parsing text that is only generated after the conclusion of Step 1. For example, batching 'Run Query' and 'Summarize Result' is impossible because the summary content is unknowable until the query finishes. A valid batch must only include 'Mechanically Predictable' UI transitions like menu expansions or dialog appearances.
  - Reject trajectories with 'Redundant Reflection Loops' where the agent stop to reflect on metadata that hasn't changed (e.g., confirming it's still on the home page after every scroll). This 'Planning Bloat' is the primary cause of CUA latency and must be pruned. If removing a planning step doesn't change the outcome or safety of the trajectory, the trace is rejected as inefficient.
