# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the 'Simulation Logic' is perfectly consistent with the proposed plan or code being verified. You must verify that the manual trace accurately follows the instructions of the plan and does not magically skip steps to reach the correct answer. For example, if a plan omits a swap step, the simulation must also omit it to correctly identify the subsequent failure.
  - Accept only if the 'Bug Discovery Utility' is demonstrable, meaning the simulation actually uncovered a non-trivial error that would have caused the final answer to be incorrect. A valid seed should show a 'before and after' comparison where the refined plan is measurably superior in satisfying the constraints. If the simulation always produces 'Success' without finding any issues, the task might be too trivial for this capability.
  - Accept only seeds where the 'Self-Correction Reasoning' matches the actual diagnostic output from the simulation trace. The agent's thinking block must explicitly link the failure observed in the dry-run to the specific part of the logic that requires modification. A concrete indicator is the agent identifying that a 'tri(n+1)' call in a recursive formula requires a future value that the current loop cannot provide.
  - Accept only if the 'Step-by-Step Transparency' of the simulation is high enough to be verified by a human expert. Each state update—such as a list growing or a variable changing—must be recorded in the trajectory to prove the agent is performing the 'systematic perception' of the logic. If the agent jumps from 'Input X' straight to 'Simulation shows I need to fix Y' without the middle trace, the seed is rejected.
* **Rejection Criteria**:
  - Reject any trajectory that exhibits 'Confirmation Bias Hallucination,' where the agent claims the simulation was successful despite the trace clearly violating the environment's rules. This often happens if the agent ignores an error in its manual dry-run because it 'knows' what the final answer should be. For instance, if the plan says 'add 2' but the simulation says 'add 3' to match the example, the logic is broken.
  - Reject seeds where the 'Simulation Input' is identical to the 'Recall Example' provided earlier in the plan. Re-testing the logic on the exact same example from which the logic was derived does not prove robustness; the simulation must use a different (though related) sample to test generalization. A concrete failure is using '2+2' to verify an addition tool when '2+2' was already used as the 'Recalled Example'.
  - Reject trajectories with 'Trivial Refinement,' where the agent suggests a fix that is purely cosmetic and does not change the underlying planning logic. If the 'Revised Plan' is just the original plan written in more sophisticated prose without altering the actual sequence of actions, the capability is not doing real work. An example is changing 'get the numbers' to 'acquire the integers' without changing the range bounds found to be wrong.
  - Reject any seed where the 'Simulation Trace' relies on external tool feedback (like a compiler) before the capability is explicitly in the 'External Debugging' phase. This skill is about internal mental simulation for plan verification; if the agent depends on a Python Interpreter to find the error in its head, it represents a failure of the internal simulation mechanic.
