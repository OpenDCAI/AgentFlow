# Phase 1: Environment Exploration Guide
* **Exploration Strategy**:
  - Conduct a 'Relational Schema and Weight Audit' to identify the available link properties that could serve as costs or capacities. The agent must list all edge attributes (e.g., 'distance', 'cost', 'latency') to determine which physical variable best represents the user's abstract goal like 'cheapest' or 'fastest'. For example, if a user asks for 'the most efficient path', the agent should proactively check if 'efficiency' is a pre-calculated column or if it must be derived from 'distance/time' ratios first. An edge case is a graph where the intended 'weight' is stored as a string that requires conversion to a float before the algorithm can ingest it.
  - Perform 'Pathfinding Parameter Mapping' to translate linguistic constraints into numeric search bounds. This involves extracting starting points, target destinations, and the requested number of alternatives (e.g., mapping 'a few options' to a k-path value of 3 or 5). For instance, in a navigation task, the agent must check if 'avoiding Zone 1' can be implemented as a node-filter before running the Dijkstra algorithm. A concrete edge case is identifying if a 'shortest' path refers to the number of hops (unweighted) or the sum of specific weights (weighted), necessitating a clarifying look at the edge types present.
  - Deploy 'Topology-Based Influence Classification' to select between different centrality metrics based on the specific nuance of the question. The agent should evaluate whether a user wants 'hub' nodes (high Degree Centrality), 'bridge' nodes (high Betweenness Centrality), or 'long-term prestige' nodes (PageRank). For example, if a request asks for 'the person who can stop a rumor fastest', the agent should prioritize Closeness or Betweenness over simple connection counts. An edge case is a network where one node has a massive degree but very low PageRank, which the agent should identify to explain why that node isn't actually 'globally important'.
  - Execute 'Structural Partition Planning' to determine the optimal community detection method for grouped-discovery requests. The agent must verify if the user expects overlapping groups (like families) or disjoint partitions (like clusters) and select algorithms like Louvain or Label Propagation accordingly. For instance, before grouping users, the agent should check the graph density to see if a simple connected-components check is sufficient or if it needs modularity-based optimization. A failure mode to avoid is applying a community detection algorithm to a bipartite graph without first deciding whether to project it into a homogeneous graph of a single node type.
* **Target Trajectory Profile**:
  - The trajectory must record an explicit 'Relational Logic Translation' step where natural language concepts are mapped to graph primitives. The trace should show the agent thinking: 'User wants most influential -> selecting PageRank with 0.85 damping factor' or 'User wants fastest route -> mapping to the time_seconds edge property'. This transparency distinguishes the agent's graph-theoretic reasoning from simple keyword matching. An edge case is when the agent corrects its plan after discovering that a chosen edge weight property is mostly null, switching to a hop-count (unweighted) approach instead.
  - A high-quality profile demonstrates 'Graph Projection' or 'Subgraph Selection' to focus the algorithm on relevant nodes. The trace should show the agent filtering the full dataset (e.g., 'Using only nodes of type: Station') to build the relational object for analysis. For example, if asked about 'the link between two cities', the agent should be seen isolating the connected component containing those cities before running a path search. This proves the agent is managing memory and logical scope efficiently in the data sandbox.
  - The trajectory must preserve the 'Algorithmic Anchor Points' like node IDs and cost values in the observation logs. Even if the final answer is a name, the underlying code should show the integer IDs and float scores (e.g., 'Node 123 has PageRank 0.045') used to derive the ranking. This ensures the output is verifiable and grounded in the actual graph topology. An edge case is a pathfinding result where the agent must report both the node sequence and the cumulative cost to prove the path is indeed the 'shortest' as requested.
  - A robust profile concludes with a 'Topological Interpretation' that explains the graph result in domain terms. Instead of just returning a list of IDs, the agent should interpret the meaning of a 'high betweenness' score as a 'bottleneck' or 'gatekeeper' in the textual summary. For example, the agent might log: 'Station X has the highest closeness; it is the most central location for reaching all other stations.' This bridges the gap between raw graph math and the user's analytical need.
