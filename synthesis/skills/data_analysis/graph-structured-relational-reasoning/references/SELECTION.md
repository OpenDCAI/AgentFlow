# Phase 2: Trajectory Selection Criteria
* **Acceptance Metrics**:
  - Accept only if the task requires traversing or analyzing the relational linkage between entities (multi-hop) rather than simple attribute filtering. The question must be unsolvable by looking at a single row; it should require identifying paths, clusters, or importance that emerge from the 'links' themselves. For example, 'Find all users in Zone 1' is a filter (reject), but 'Find the user who connects Zone 1 to Zone 5' is a graph task (accept).
  - Accept only if the agent justifies the algorithm choice based on the topological characteristic requested (e.g., path, community, or influence). Reviewers should see a direct link between 'influence' and 'centrality algorithms' or 'grouping' and 'community detection'. This confirms the agent is performing active graph-algorithmic reasoning. A successful selection shows exactly why Louvain was chosen over Connected Components for a grouping task.
  - Accept only if the trajectory includes a code-based discovery of the graph's properties and types. The trace must document tools like `df.info()`, `nx.info()`, or `list_relationship_types` to prove the agent understands the network structure it is operating on. This prevents 'blind' algorithm application where the agent doesn't even know if the edges are directed or undirected.
  - Accept only if the final answer is derived from a formal mathematical algorithm result rather than manual counting or intuition. For a centrality or community query, the agent must be seen executing code that outputs a ranking or a group assignment. This ensures the capability measures programmatic graph analysis accuracy. An edge case is accepting a 'No path' answer only if the agent's code actually confirms the absence of a route through a BFS or Dijkstra search.
  - Accept only if the algorithm's input parameters (weights, k, source/target) are correctly grounded in the provided dataset. If the question asks for the 'fastest' route and the agent uses 'distance' as the weight, the trajectory must be rejected for poor grounding. Successful selection requires' reading the data dictionary' to find the most representative edge property for the user’s metric.
* **Rejection Criteria**:
  - Reject trajectories where the agent treats the graph as a flat table and uses simple group-bys to answer topological questions. If the agent calculates 'most connected' by just counting occurrences of an ID in a column without building a graph object or using a degree centrality algorithm, it is not exercising relational reasoning. This skill mandates utilizing pathfinding or connectivity logic.
  - Reject cases where the agent hallucinates a graph relationship that is not supported by the data schema. For example, if the data has 'User' and 'Product' but the agent assumes 'User-to-User' links exist without evidence, the trace is a grounding failure. Relational reasoning must be based strictly on the edges defined in the analytical environment.
  - Reject trajectories that ignore edge directionality when it is central to the problem. In a financial transaction graph (directed), finding a 'loop' requires following arrows; if the agent treats it as an undirected web, the resulting 'community' or 'path' is mathematically invalid. High-quality selection requires a 'Directed vs. Undirected' check during the exploration phase.
  - Reject tasks where the main challenge is simply naming a node property rather than graph math. If the question is 'Who is the neighbor of Alice?', it belongs under basic data retrieval. The task must provide sufficient depth (e.g., 'What is the most strategic hub between Alice and Bob?') to warrant a graph-theoretic approach.
  - Reject examples where the agent fails to verify the existence of path weights before selecting a weighted algorithm. Applying Dijkstra to a graph where the weight column is missing or non-numeric represents a fundamental execution failure. The agent must proactively check the 'type' and 'null-rate' of weight properties.
